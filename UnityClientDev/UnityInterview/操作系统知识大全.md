## 1.1 🟢 什么是操作系统

### OS 的核心功能

操作系统是**管理硬件资源、为应用程序提供服务**的系统软件。核心职责：

| 功能 | 说明 | Unity 关联 |
|------|------|-----------|
| **进程管理** | 创建/调度/销毁进程与线程 | Unity 主进程 + 渲染线程 + Job Worker |
| **内存管理** | 虚拟内存、分页、分配与回收 | Mono/IL2CPP 的堆管理、NativeArray |
| **文件系统** | 文件读写、目录管理、权限控制 | AssetBundle 加载、资源热更 |
| **设备管理** | 驱动程序、IO 调度 | 触屏输入、手柄、传感器 |
| **网络** | TCP/IP 协议栈、Socket | Unity 网络同步、Netcode |

### Linux 内核架构

```
用户空间
    ↓ 系统调用接口（System Call Interface）
内核空间
  ├── 进程管理（process management）
  ├── 内存管理（memory management）
  ├── 虚拟文件系统 VFS（virtual file system）
  ├── 网络协议栈（network stack）
  └── 设备驱动（device drivers）
    ↓
硬件层（Hardware）
```

### 内核架构分类

| 架构 | 代表系统 | 特点 | 优点 | 缺点 |
|------|---------|------|------|------|
| **宏内核** | Linux | 所有内核服务运行在内核态 | 效率极高，无特权级切换 | 任一模块崩溃可能系统崩溃 |
| **微内核** | Mach, L4 | 内核只保留 IPC、内存映射 | 稳定性强、模块化 | 多次用户态/内核态切换，性能差 |
| **混合内核** | Windows NT, macOS XNU | 吸收宏内核高效 + 微内核模块化 | 平衡性能与稳定性 | 设计复杂 |

> **"Linux 是宏内核但支持可加载内核模块（LKM），驱动可以动态插入/移除内核——Unity 的 Native Plugin 机制某种程度上也类似这种可插拔设计。"**

## 1.2 🟡 用户态与内核态

### 特权级划分

CPU 通过**特权级**保护内核不被用户程序随意访问：

```
┌────────────────────────────────────────┐
│  Ring 0（内核态）                       │  ← 所有硬件资源都可访问
│  - 内核代码                              │
│  - 设备驱动                              │
├────────────────────────────────────────┤
│  Ring 3（用户态）                       │  ← 受限访问
│  - 应用程序                              │
│  - Unity 游戏进程                        │
│  - 需要通过系统调用请求内核服务            │
└────────────────────────────────────────┘
```

### 用户态 → 内核态切换的开销

| 步骤 | 操作 | 耗时 |
|------|------|------|
| 1 | 保存用户态上下文（寄存器、栈指针） | ~数十ns |
| 2 | 切换到内核栈 | ~数十ns |
| 3 | 执行系统调用内核代码 | 视具体调用 |
| 4 | 恢复用户态上下文 | ~数十ns |
| **合计** | **单次系统调用** | **~100-200ns** |

> **⚠️ 面试陷阱**：频繁的系统调用（如大量小文件读写）会因上下文切换累积显著开销，这正是 IO 多路复用和批量 IO 存在的意义。

### Unity 场景

```
Unity 游戏进程（用户态）
  ├── 每帧 Update → 普通代码（用户态）
  ├── Resources.Load → 最终调用 read() 系统调用（切换到内核态）
  ├── Socket.Send → 调用 sendto() 系统调用（切换到内核态）
  └── Thread.Sleep → 调用 nanosleep() 系统调用（切换到内核态）
```

## 1.3 🟡 中断与系统调用

### 中断机制

中断是 **CPU 暂停当前任务、响应外部事件**的机制：

| 类型 | 触发者 | 举例 |
|------|--------|------|
| **硬件中断** | 外部设备 | 网卡收到数据、磁盘 IO 完成、键盘按键 |
| **软中断（异常）** | CPU 内部 | 除零错误、缺页中断、溢出 |
| **系统调用（陷阱）** | 用户程序主动 | `read()`、`write()`、`fork()` |

### 中断处理流程

```
硬件/软件事件
    ↓
CPU 检测到中断
    ↓
保存当前进程上下文
    ↓
查找中断向量表 → 跳转到对应中断处理程序
    ↓
执行中断处理（如：将网络数据拷贝到内核缓冲区）
    ↓
恢复被中断的进程上下文
    ↓
继续执行原进程
```

### Unity 中的中断关联

| 中断类型 | Unity 场景 |
|---------|-----------|
| 网络中断 | 收到服务器同步数据包，触发 OnMessage 回调 |
| 磁盘中断 | AssetBundle 异步加载完成，触发回调 |
| 定时器中断 | 协程 `yield return WaitForSeconds` 的底层机制 |
| 缺页中断 | 访问尚未加载到物理内存的资源页面 |

> **"Unity 的协程看起来像异步，但本质上是编译器状态机 + 主循环每帧检查 yield 条件的分帧执行机制，不涉及 OS 线程切换或时间片。"**

## 2.1 🔴 进程 vs 线程

### 核心概念

**进程（Process）**：程序的一次执行实例，拥有独立的地址空间、文件描述符、堆栈等资源。

**线程（Thread）**：CPU 调度的基本单位，共享所属进程的地址空间和资源。

```
进程 A（独立地址空间）
┌──────────────────────────┐
│  代码段   数据段   堆    │  ← 进程 A 独享
│  ┌────────────────────┐  │
│  │ 线程 A1 │ 线程 A2  │  │  ← 共享进程资源
│  │ ┌──────┐┌──────┐  │  │
│  │ │栈    ││栈    │  │  │  ← 每个线程独立栈
│  │ │寄存器││寄存器│  │  │     (PC, SP, 寄存器)
│  │ └──────┘└──────┘  │  │
│  └────────────────────┘  │
└──────────────────────────┘

进程 B（独立地址空间，与 A 隔离）
┌──────────────────────────┐
│  代码段   数据段   堆    │
│  ┌────────────────────┐  │
│  │ 线程 B1            │  │
│  └────────────────────┘  │
└──────────────────────────┘
```

### 进程 vs 线程对比表

| 对比维度 | 进程 | 线程 |
|----------|------|------|
| 地址空间 | 独立（互不影响） | 共享（线程间通信简单） |
| 资源开销 | 大（创建需分配独立资源） | 小（仅栈和寄存器） |
| 切换成本 | 高（切换页表、刷新 TLB） | 低（仅保存/恢复寄存器） |
| 通信方式 | IPC（管道、共享内存、消息队列） | 直接读写共享变量 |
| 可靠性 | 一个进程崩溃不影响其他进程 | 一个线程崩溃导致整个进程崩溃 |
| Unity 场景 | 每个 Unity 编辑器实例 = 一个进程 | 渲染线程、主线程、Job Worker |

### 进程的五种状态

```
创建 → [就绪（Ready）] ←──────────────┐
              ↓  调度                  │ 抢占/时间片到
         [运行（Running）]             │
              ↓  调用阻塞IO            │
         [阻塞（Waiting）] ──IO完成──→ [就绪]
              ↓                       │
         [终止（Terminated）]          │
```

### Unity C# 代码关联

```csharp
// Unity 线程模型
void Start()
{
    // ===== 主线程（Main Thread）=====
    // - 所有 Unity API 调用必须在主线程
    // - Update/FixedUpdate/LateUpdate
    
    // ===== 渲染线程（Rendering Thread）=====
    // - GPU 命令提交，开发者不能直接控制
    
    // ===== Job Worker 线程 =====
    // - Unity Job System 自动管理
    // - 不能调用 Unity API（Transform, GameObject 等）
    
    // 耗时计算 → Job System → 结果回传 → MainThread 回调
}

// Job System 示例（多线程安全）
struct HeavyComputationJob : IJob
{
    public NativeArray<float> input;
    public NativeArray<float> output;
    
    public void Execute()
    {
        // 此代码在 Worker 线程执行，不能调用任何 Unity API
        for (int i = 0; i < input.Length; i++)
            output[i] = MathF.Sqrt(input[i]) * MathF.Sin(input[i]);
    }
}
```

> **"进程是资源分配的最小单位，线程是 CPU 调度的最小单位——面试最基础的操作系统题。Unity 中子线程不能调用 API 是因为 Unity API 不是线程安全的。"**

## 2.2 🔴 进程调度算法

### 五大调度算法

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| FCFS（先来先服务） | 按到达顺序调度 | 公平简单 | 平均等待时间长（护航效应） |
| SJF（短作业优先） | 优先执行最短任务 | 最短平均周转时间 | 长作业可能饿死 |
| 时间片轮转（RR） | 固定时间片轮流执行 | 响应快，交互性好 | 时间片选择是关键 |
| 优先级调度 | 高优先级优先 | 重要任务优先 | 低优先级可能饿死 |
| 多级反馈队列（MLFQ） | 多队列+不同时间片 | 综合各种策略优势 | 实现复杂 |

### 时间片轮转图解

```
时间片 = 4ms

进程  执行时间    到达时间
 P1     10ms       0ms
 P2      4ms       1ms
 P3      3ms       2ms

执行顺序：
|←P1(4ms)→|←P2(4ms)→|←P3(3ms)→|←P1(4ms)→|←P1(2ms)→|
0         4         8         11        15        17
```

### Unity 关联

Unity 的 PlayerLoop 本质上是一个时间片轮转调度器——每个系统（Physics、Update、Rendering）在帧循环中获得固定的执行顺序。Job System 使用**工作窃取（Work-Stealing）**算法，类似多级反馈队列的思想。

> **"时间片太短导致上下文切换开销大，太长导致交互响应慢。Unity Job System 的工作窃取本质上是负载均衡的调度策略。"**

## 2.3 🔴 死锁

### 死锁的四个必要条件（缺一不可）

| 条件 | 说明 | 比喻 |
|------|------|------|
| 互斥 | 资源一次只能被一个进程使用 | 一把钥匙只能一个人拿 |
| 持有并等待 | 进程持有资源的同时等待其他资源 | 拿着钥匙还想要另一把 |
| 不可剥夺 | 资源不能被强制拿走 | 对方不给不能抢 |
| 循环等待 | 存在等待环路 P1→P2→P3→P1 | A等B，B等C，C等A |

### 死锁处理策略

| 策略 | 做法 | 优缺点 |
|------|------|--------|
| 预防 | 破坏四个条件之一 | 简单但资源利用率低 |
| 避免 | 银行家算法，分配前检查安全性 | 需预先知道最大需求 |
| 检测+恢复 | 定期检测死锁，强制回滚 | 需检查开销和回滚机制 |
| 忽略 | 假装不会发生（鸵鸟算法） | Windows/Linux 实际采用 |

### C# 死锁示例与修复

```csharp
object resourceA = new object();
object resourceB = new object();

// 经典死锁
void Thread1()
{
    lock (resourceA)
    {
        lock (resourceB) { /* ... */ }
    }
}
void Thread2()
{
    lock (resourceB)
    {
        lock (resourceA) { /* ... */ } // 死锁!
    }
}

// 修复方案 1：按固定顺序加锁（破坏循环等待）
object lockA = new object(), lockB = new object();
void SafeLock()
{
    lock (lockA)  // 始终先 A 后 B
    {
        lock (lockB) { /* 安全 */ }
    }
}

// 修复方案 2：超时机制（破坏不可剥夺）
void SafeTimeout()
{
    bool gotA = false, gotB = false;
    try {
        Monitor.TryEnter(A, 1000, ref gotA);
        Monitor.TryEnter(B, 1000, ref gotB);
    } finally {
        if (gotB) Monitor.Exit(B);
        if (gotA) Monitor.Exit(A);
    }
}
```

> **"面试高频：说说死锁的四个条件和解决方案。最常见的解法是破坏循环等待——给所有锁编号，始终按编号从小到大加锁。"**

## 2.4 🟡 进程通信（IPC）

### 六种 IPC 方式对比

| 方式 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| 管道（Pipe） | 内核缓冲区，单向流动 | 简单 | 单向、容量有限 | 父子进程通信 |
| 命名管道（FIFO） | 有名字的管道，无亲缘关系也可用 | 解除亲缘限制 | 仍是单向 | 不相关进程 |
| 消息队列 | 内核中的消息链表 | 异步、可指定消息类型 | 有内核拷贝开销 | 结构化消息 |
| 共享内存 | 多个进程映射同一块物理内存 | 最快（零拷贝） | 需同步机制保护 | 高性能数据共享 |
| 信号量 | 计数器，控制并发访问 | 可用于同步和互斥 | 编程复杂 | 资源计数控制 |
| Socket | 网络通信，跨机器 | 跨网络 | 开销最大 | 网络通信、Unity 客户端-服务器 |

### Unity 关联

```
Unity 客户端 ←──Socket/TCP──→ 游戏服务器
     ↑                            ↑
     │ UnityWebRequest            │ 自定义协议
     │ （HTTP 层面）              │ （二进制序列化）
```

> **"Unity 客户端和服务器之间最常用 Socket 通信。共享内存是最快的 IPC 方式（同一台机器），但 Unity 跨进程通信通常用命名管道或网络 Socket。"**

## 3.1 🔴 虚拟内存

### 为什么要有虚拟内存？

若所有进程直接操作物理内存：
1. **安全问题**：进程 A 可以任意读写进程 B 的内存
2. **内存碎片**：多进程运行后物理内存变得支离破碎
3. **容量限制**：进程大小受物理内存限制

### 虚拟内存的核心思想

每个进程拥有**独立的、连续的虚拟地址空间**（64 位系统每个进程 128TB），通过**页表（Page Table）**映射到物理地址。

```
进程 A 虚拟地址空间                     物理内存
0x0000 ──────────────┐                 ┌─────── Page Frame 0
  ...               ├─ 页表映射 ──────→ ├─────── Page Frame 1
0xFFFF ──────────────┘                 ├─ ...
                                       └─────── （部分在磁盘 Swap 上）
进程 B 虚拟地址空间
0x0000 ──────────────┐
  ...               ├─ 不同的页表 ─────→ 不同的物理页
0xFFFF ──────────────┘
```

### 页表工作原理

- **虚拟地址** = 虚拟页号（VPN）+ 页内偏移（Offset）
- **物理地址** = 物理页框号（PFN）+ 页内偏移
- **页大小**：通常 4KB（Linux 默认）

### TLB（Translation Lookaside Buffer）

页表查询需要访问内存（很慢），TLB 作为**页表缓存**加速转换：

| 情况 | 流程 | 耗时 |
|------|------|------|
| TLB 命中 | 直接得到物理地址 | ~1ns |
| TLB Miss | 走页表查询（多级页表），再填入 TLB | ~10-100ns |

### 缺页中断（Page Fault）

当访问的虚拟地址没有对应的物理页时：

```
CPU 访问虚拟地址
    ↓ 页表标记为"不在内存"
触发缺页异常
    ↓
OS 接管
    ↓
找到空闲物理页（或换出一个页到 Swap）
    ↓
从磁盘读数据到物理页
    ↓
更新页表，刷新 TLB
    ↓
重新执行触发异常的那条指令
```

### 虚拟内存三大作用

1. **进程隔离**：每个进程有独立地址空间，互不干扰
2. **内存超配（Lazy Allocation）**：申请内存时不立即分配物理页，真正访问时才通过缺页中断分配
3. **内存共享**：共享库（如 libc.so）映射到多个进程虚拟空间，但只占一份物理内存

### Unity 关联

| 概念 | Unity 对应 |
|------|-----------|
| 进程隔离 | 每个 Unity 编辑器实例独立进程 |
| 虚拟内存 | Mono/IL2CPP 堆使用虚拟地址空间 |
| 缺页中断 | 大型资源首次访问时的性能卡顿 |
| Lazy Allocation | `new` 对象时不一定立即分配物理内存 |

> **"面试必答：虚拟内存的三大作用是进程隔离、内存超配和内存共享。Unity 的大型资源首次加载卡顿，部分原因是触发了缺页中断从磁盘加载数据。"**

---

## 3.2 🔴 分页与分段

### 分页（Paging）

将虚拟地址空间和物理内存都切成**固定大小**的页（通常 4KB），通过页表映射。

| 特点 | 说明 |
|------|------|
| 页大小固定 | 4KB，对所有进程一致 |
| 无外部碎片 | 任何空闲页框都可使用 |
| 有内部碎片 | 最后一页可能未满 |
| 页表可能很大 | 32 位系统需多级页表 |

### 分段（Segmentation）

按程序的**逻辑单元**划分（代码段、数据段、栈段），每段大小不同。

| 特点 | 说明 |
|------|------|
| 段大小可变 | 按逻辑单元划分 |
| 有外部碎片 | 段之间可能有空洞 |
| 无内部碎片 | 段内紧凑 |
| 符合程序视角 | 代码、数据、栈自然分离 |

### 段页式（现代系统方案）

先分段（逻辑划分），再对每段内部分页（物理管理）。**Linux 主要使用分页**，但在某些架构保留分段的概念。

> **"现代操作系统以分页为主。面试中问'分页和分段的区别'，核心回答：分页是固定大小（无外部碎片），分段是可变大小（符合逻辑视角）。"**

---

## 3.3 🟡 页面置换算法

当物理内存不足时，OS 需要选择一个页面换出到磁盘：

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **FIFO** | 淘汰最早进入内存的页 | 实现简单 | Belady 异常（增加页框反而缺页率上升） |
| **LRU** | 淘汰最近最久未使用的页 | 性能接近最优 | 需记录访问时间戳，开销大 |
| **Clock** | 近似 LRU，用访问位环形扫描 | 开销小，实际常用 | 精度略低于 LRU |
| **OPT** | 淘汰未来最久不会被访问的页 | 理论最优 | 无法实现（需预知未来） |

### LRU 原理图解

```
访问序列：1 2 3 4 1 2 5 1 2 3 4 5
内存大小：3 个页框

时刻  访问  内存状态    淘汰  缺页？
 1     1   [1, -, -]    -     ✅
 2     2   [1, 2, -]    -     ✅
 3     3   [1, 2, 3]    -     ✅
 4     4   [4, 2, 3]    1     ✅
 5     1   [4, 1, 3]    2     ✅
 6     2   [4, 1, 2]    3     ✅
 7     5   [5, 1, 2]    4     ✅
 8     1   [5, 1, 2]    -     ❌
 9     2   [5, 1, 2]    -     ❌
...
```

### Linux 改进：双 LRU 链表

```
Active List（活跃链表）：存放经常被访问的热点页
    HEAD → [最近活跃] → ... → [久未活跃] → TAIL

Inactive List（非活跃链表）：存放最近较少访问的页
    HEAD → [最近加入] → ... → [最久未访问] → TAIL

预读页 → 加入 Inactive List 头部
    ↓
若再次被访问 → 从 Inactive 升级到 Active List
    ↓
若一直未访问 → 沿 Inactive List 尾部被淘汰
```

> **"LRU 是面试必考算法。手写 LRU Cache（哈希表+双向链表，O(1) 操作）是常见编程题。Linux 实际使用改进的双 LRU 链表防止预读失效和缓存污染。"**

## 3.4 🟡 malloc 与内存分配

### 进程的内存布局（从低到高地址）

```
高地址
┌─────────────────┐
│   内核空间        │  ← 用户态不可访问
├─────────────────┤
│   栈（Stack）     │  ← 向下增长，局部变量、函数调用帧
│   ↓              │
│  （空洞）         │
│   ↑              │
│  文件映射区/mmap  │  ← 动态库、mmap 映射的文件
│   ↑              │
│   堆（Heap）      │  ← 向上增长，malloc 申请的内存
├─────────────────┤
│   BSS 段         │  ← 未初始化全局/静态变量
│   数据段         │  ← 已初始化全局/静态变量
│   代码段（Text）  │  ← 只读，程序指令
└─────────────────┘
低地址
```

### malloc 分配策略（glibc ptmalloc2）

| 申请大小 | 分配方式 | 释放行为 |
|---------|---------|---------|
| < 128 KB | `brk()` 系统调用，移动堆顶指针 | `free()` 后**不立即归还系统**，加入内存池缓存 |
| ≥ 128 KB | `mmap()` 系统调用，申请匿名映射 | `free()` 后**立即调用 `munmap()` 归还**操作系统 |

> 128KB 是 glibc 默认阈值（`M_MMAP_THRESHOLD`），可通过 `mallopt(M_MMAP_THRESHOLD, n)` 调整。Android Bionic libc 行为可能不同。

### 为什么 free 后内存不一定归还系统？

```c
void *p = malloc(100);   // 分配 100 字节（brk 方式）
free(p);                 // 释放，但只是放回 malloc 的内存池
// 进程占用的虚拟内存没变！
// 下次再 malloc，会优先复用内存池里的碎片
```

只有当**堆顶连续空闲内存足够大**时，glibc 才会调用 `brk()` 缩减堆。

### 内存碎片问题

| 类型 | 原因 | 解决方案 |
|------|------|---------|
| **内部碎片** | malloc 分配块比实际需要的大（对齐和最小粒度） | 使用 jemalloc/tcmalloc |
| **外部碎片** | 大量小的空闲块零散分布 | Slab 分配器、伙伴系统 |

### Unity 关联

| C# 概念 | 底层机制 |
|---------|---------|
| `new object()` | CLR 堆分配 → 最终调用 `malloc`/`VirtualAlloc` |
| `GC.Collect()` | 触发垃圾回收，但**不会归还内存给 OS** |
| `NativeArray<T>` | 使用 `UnsafeUtility.Malloc` → 可直接管理原生内存 |
| 大对象堆（LOH） | ≥ 85000 字节的对象直接分配在 LOH，不参与常规 GC |

> **"Unity 开发者常困惑'为什么内存不降'——因为 Mono 的 GC 释放对象后，内存只是回到 CLR 堆，并不归还 OS。真正的内存释放需要等进程结束或使用 `System.GC.Collect()` + 特定运行时配置。"**

## 4.1 🟡 VFS 虚拟文件系统

### "一切皆文件" —— Linux 的设计哲学

Linux 中，普通文件、目录、设备（`/dev/sda`）、管道（`pipe`）、套接字（`socket`）都被统一抽象为**文件**，通过统一的文件接口（`open/read/write/close`）操作。

### VFS 层：统一接口抽象

VFS（Virtual File System）是 Linux 内核的文件系统抽象层，为所有文件系统提供**统一接口**：

```
用户程序
   |
   |  open() / read() / write() / close()  <-- POSIX 接口
   |
   v
+------------------------------------------+
|      VFS（虚拟文件系统）                  |  <-- 统一抽象层
|  +------------------------------------+  |
|  |  super_block: 文件系统元信息         |  |
|  |  inode: 文件元数据                  |  |
|  |  dentry: 目录项缓存                |  |
|  |  file: 打开的文件实例              |  |
|  +------------------------------------+  |
+----------+-------------------------------+
           | 根据文件系统类型分发
     +-----+----------+--------------+
     v     v          v              v
  EXT4   XFS      NTFS(Windows)   FAT32
  驱动    驱动       驱动           驱动
     |     |          |              |
     +-----+----------+--------------+
                   |
              块设备层 -> 具体磁盘设备
```

### VFS 的四个核心对象

| 对象 | 作用 | 类比 |
|------|------|------|
| `super_block` | 记录文件系统整体信息（块大小、总块数、空闲块） | 硬盘的"目录本" |
| `inode` | 记录单个文件的元数据（权限、大小、数据块位置） | 文件的"身份证" |
| `dentry` | 记录文件名到 inode 的映射，维护目录树结构 | 文件的"名牌" |
| `file` | 进程打开文件后的运行时实例（偏移量、状态标志） | 文件的"借书证" |

### 面试提示

> **"VFS 的核心价值是解耦——不管底层是 EXT4 还是 NTFS，用户程序看到的都是同一套 read/write 接口。Unity 跨平台能用同一套文件 API 操作不同操作系统，底层就是靠 VFS 这层抽象。"**

**Unity 关联**：Unity 的 `StreamingAssets` 目录在不同平台底层走的是不同文件系统（Android 走 AAssetManager，iOS 走 POSIX，Windows 走 NTFS），但开发者用 `UnityWebRequest` 或 `File.ReadAllBytes` 接口完全一致——这就是 VFS 思想的应用。

## 4.2 🟡 inode 与 dentry

### inode：文件的"身份证"

```c
// Linux inode 包含（注意：不包含文件名！）
struct inode {
    unsigned long   i_ino;        // inode 编号（全局唯一标识）
    umode_t         i_mode;       // 文件类型 + 权限（rwxrwxrwx）
    loff_t          i_size;       // 文件大小（字节）
    struct timespec i_atime;      // 最后访问时间
    struct timespec i_mtime;      // 最后修改时间
    struct timespec i_ctime;      // inode 最后修改时间
    unsigned int    i_nlink;      // 硬链接数
    uid_t           i_uid;        // 所有者
    gid_t           i_gid;        // 所属组
    // ... 数据块指针（存储文件实际内容的磁盘块位置）
};
```

### dentry：文件的"名牌"

- 记录**文件名 -> inode 编号**的映射关系
- **存在于内存**（内核维护的路径缓存），不在磁盘上
- 目录树结构由 dentry 链接起来
- 路径解析（如 `/home/user/file.txt`）就是**逐级查找 dentry** 的过程

### inode vs dentry 核心区别

| | inode | dentry |
|---|---|---|
| 存储位置 | **磁盘** + 内存缓存 | **仅内存**（内核缓存） |
| 包含信息 | 文件元数据 + 数据块位置 | 文件名 + inode 号 |
| 与文件关系 | 一个文件**只有一个** inode | 一个文件可有**多个** dentry（硬链接）|
| 生命周期 | 跟随文件存在 | 跟随目录缓存（可被回收） |

### 文件名 -> inode -> 数据块 查找流程

```
路径解析示例：/home/user/game.dat

Step 1: 从根目录 dentry 开始
        根 dentry -> inode#2 -> 读取目录数据 -> 找到 "home" 的 inode#100

Step 2: 查找 home 目录
        dentry("home", inode#100) -> 读取目录数据 -> 找到 "user" 的 inode#200

Step 3: 查找 user 目录
        dentry("user", inode#200) -> 读取目录数据 -> 找到 "game.dat" 的 inode#500

Step 4: 读取文件数据
        inode#500 -> 数据块指针 -> 读取磁盘块 -> 得到文件内容
                    |
              12个直接指针 + 间接指针（支持大文件）
```

### inode 中的数据块指针结构（ext4）

```
inode 数据块指针布局：
+----------------------------------------------------------+
| 直接指针 x12  | 一级间接 | 二级间接 | 三级间接           |
| 每个指向4KB块 | 指向指针块| 指向二级  | 指向三级           |
|               | (1024个) | 指针块   | 指针块             |
+---------------+----------+----------+--------------------+
| <= 48KB       | <= 4MB   | <= 4GB  | <= 4TB             |
| 小文件直接命中 | 中等文件  | 大文件   | 超大文件           |
+---------------+----------+----------+--------------------+
```

### 符号链接 vs 硬链接

| | 硬链接（Hard Link） | 软链接（Symbolic Link）|
|---|---|---|
| 本质 | 新建一个指向**同一 inode** 的 dentry | 新建一个**独立文件**，内容是目标路径字符串 |
| inode | 共用同一个 | 有自己独立的 inode |
| 跨文件系统 | 不支持 | 支持 |
| 目标删除后 | 仍可访问（inode 引用计数 > 0）| 变成死链接（dangling symlink）|
| 类比 | 同一个人的两个名字 | 一张写着地址的纸条 |

```csharp
// C# 查看文件元数据（对应 inode 信息）
using System.IO;

class InodeInfoDemo
{
    void ShowFileInfo(string path)
    {
        FileInfo fi = new FileInfo(path);
        Console.WriteLine($"文件大小: {fi.Length} bytes");           // i_size
        Console.WriteLine($"创建时间: {fi.CreationTime}");          // i_ctime
        Console.WriteLine($"修改时间: {fi.LastWriteTime}");         // i_mtime
        Console.WriteLine($"访问时间: {fi.LastAccessTime}");        // i_atime
        Console.WriteLine($"只读属性: {fi.IsReadOnly}");            // i_mode 权限位
    }
}
```

```cpp
// C++ 获取 inode 信息（Linux）
#include <sys/stat.h>
#include <iostream>

void ShowInodeInfo(const char* path) {
    struct stat st;
    if (stat(path, &st) == 0) {
        std::cout << "inode 编号: " << st.st_ino << std::endl;
        std::cout << "硬链接数:   " << st.st_nlink << std::endl;
        std::cout << "文件大小:   " << st.st_size << " bytes" << std::endl;
        std::cout << "权限:       " << std::oct << st.st_mode << std::endl;
        std::cout << "用户ID:     " << st.st_uid << std::endl;
    }
}
```

### 面试提示

> **"inode 不存储文件名——文件名存在目录的数据块中（dentry 在内存中的缓存）。所以 ls 命令本质上是读取目录 inode 的数据块，遍历其中的目录项。"**

> **"硬链接为什么不能跨文件系统？因为 inode 编号只在同一个文件系统内唯一，跨文件系统的 inode 号可能重复。"**

## 4.3 🟢 文件存储与磁盘调度

### 文件分配方式

| 方式 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 连续分配 | 文件占用连续的磁盘块 | 顺序读取极快，随机访问快 | 外部碎片，文件难以扩展 |
| 链式分配 | 每块末尾存下一块指针 | 无外部碎片，动态增长 | 随机访问需遍历，指针占空间 |
| 索引分配 | 索引块存储所有数据块地址 | 支持随机访问，无外部碎片 | 索引块本身占空间（inode 方案） |

### 空闲空间管理

| 方法 | 说明 | 适用场景 |
|------|------|---------|
| 位图（Bitmap） | 每个块用 1 bit 标记空闲/占用 | ext4、NTFS，简单高效 |
| 空闲链表 | 将所有空闲块串成链表 | 早期文件系统 |
| 空闲区段表 | 记录连续空闲区段的起始和长度 | Btrfs、ZFS |

### 磁盘调度算法

| 算法 | 原理 | 寻道特点 |
|------|------|---------|
| FCFS（先来先服务） | 按请求到达顺序服务 | 公平但磁头来回跳，总寻道长 |
| SSTF（最短寻道时间优先） | 服务离当前磁头最近的请求 | 总寻道短，但可能饿死远端 |
| SCAN（电梯算法） | 磁头单向扫描，到头反转 | 顾及两端，有"偏心"效应 |
| C-SCAN（循环扫描） | 单向扫描，到头直接返回起点 | 延迟更均匀，服务器常用 |

```
磁盘调度示意（磁头当前位置=53，请求队列：98,183,37,122,14,124,65,67）

FCFS:   53->98->183->37->122->14->124->65->67
        总寻道 = 45+85+146+85+108+110+59+2 = 640

SCAN:   53->65->67->98->122->124->183 -> 37->14
        磁头先往大号方向，到头反转往小号方向
        总寻道更优，且无饿死
```

**Unity 关联**：游戏资源加载中的磁盘寻道——当 AssetBundle 散落在磁盘不同位置时，SCAN 类调度可能导致加载延迟。最佳实践是将频繁访问的资源**顺序存储**（类似连续分配），减少寻道开销。Unity 的 Addressables 系统支持将资源打包成连续块来优化加载速度。

### 面试提示

> **"磁盘调度算法本质是在吞吐量和公平性之间权衡。SCAN 算法像电梯，Nginx 的负载均衡也类似这种思想——有序地服务请求，而不是来一个处理一个。"**

## 5.1 🟡 IO 控制方式

### 四种 IO 控制方式演进

| 方式 | CPU 参与度 | 原理 | 性能 |
|------|-----------|------|------|
| 程序查询（Polling）| 极高 | CPU 循环检查设备状态寄存器 | 最差，CPU 忙等 |
| 中断驱动 | 中等 | 设备完成后发中断通知 CPU | 较好，CPU 可做其他事 |
| DMA | 极低 | 设备控制器直接访问内存，CPU 只需初始化 | 最佳，大块数据传输 |
| 通道（Channel）| 最低 | 专用 IO 处理器，可执行 IO 程序 | 大型机常用 |

### 键盘敲入 A 字母的完整 IO 流程

```
Step 1: 物理层 -- 用户按下 A 键
    +-- 键盘控制器检测到按键
    +-- 产生扫描码（Scan Code）= 0x1E（A 键按下）

Step 2: 中断触发
    +-- 键盘控制器 -> 中断控制器（PIC/APIC）-> IRQ1 信号
    +-- 中断控制器 -> CPU 发送 INTR 信号
    +-- CPU 在当前指令执行完毕后检查中断标志

Step 3: 硬中断处理（上半部，极快，微秒级）
    +-- CPU 保存现场（压栈当前寄存器）
    +-- 跳转到键盘中断处理程序（ISR）
    +-- ISR 从键盘控制器读取扫描码（I/O 端口读操作）
    +-- 将扫描码放入键盘缓冲区（ring buffer）
    +-- 标记软中断（TASKLET）
    +-- 恢复现场，返回被中断的进程

Step 4: 软中断处理（下半部，稍慢）
    +-- 扫描码转换为键盘码（Key Code，与布局无关）
    +-- 键盘码 + 当前修饰键状态（Shift/Ctrl 等）-> 字符 'A'
    +-- 字符放入 tty（终端）设备的输入缓冲区

Step 5: 用户程序读取
    +-- Shell（bash）执行 read() 系统调用，从 tty 读取字符
    +-- Shell 收到 'A'，做回显（echo），调用 write() 输出到终端
    +-- 用户看到屏幕上出现字母 A
```

### 为什么要分"上半部"和"下半部"？

| | 上半部（Top Half） | 下半部（Bottom Half） |
|---|---|---|
| 执行时机 | 中断发生后立即执行 | 延迟到安全上下文执行 |
| 时间要求 | 极快（微秒级） | 可以稍慢（毫秒级） |
| 能否睡眠 | ❌ 绝对不能 | ✅ 可以 |
| 做什么 | 读取硬件数据到缓冲区 | 协议处理、字符转换等耗时操作 |

### IO 控制方式对比表

```
+------------------+-----------+---------+----------+-----------+
|                  | 程序查询   | 中断驱动 | DMA      | 通道      |
+------------------+-----------+---------+----------+-----------+
| CPU 参与度       | 极高(忙等) | 中等    | 极低     | 最低      |
| 数据搬运者       | CPU       | CPU     | DMA 控制器| 通道处理器|
| 适合数据量       | 极小      | 小~中   | 大块     | 大量/连续 |
| CPU 利用率       | 极低      | 中等    | 高       | 最高      |
| 实现复杂度       | 最简单    | 简单    | 中等     | 复杂      |
| Unity 类比       | --        | --      | GPU DMA  | --        |
+------------------+-----------+---------+----------+-----------+
```

**Unity 关联**：GPU 的 DMA 传输是 Unity 渲染管线的关键——纹理、网格数据通过 DMA 从系统内存传输到显存（VRAM），CPU 只需调用 `Graphics.CopyTexture` 或在 CommandBuffer 中提交命令，实际搬运由 DMA 完成。

### 面试提示

> **"中断的上半部/下半部分离是操作系统设计的经典范式——把时间敏感的操作和耗时操作分开，保证中断响应速度。这和 Unity 把物理计算放 Job System 是同一思想。"**

## 5.2 🔴 阻塞/非阻塞/异步 IO

### 五种 IO 模型总览

| IO 模型 | 说明 | 特点 |
|----------|------|------|
| 阻塞 IO | 调用阻塞直到完成 | 简单但浪费线程 |
| 非阻塞 IO | 立即返回，轮询检查状态 | 需忙等（Busy Waiting）|
| IO 多路复用 | select/epoll/kqueue 监控多个 fd | 单线程处理大量连接 |
| 异步 IO（AIO）| 调用立即返回，完成时回调 | 最高效，最复杂 |
| IO 完成端口（IOCP）| Windows 异步 IO 模型 | .NET 异步 IO 底层 |

### 阻塞 IO（Blocking IO）

```
调用 read()
    |
    v
[线程阻塞休眠] <--- 等待数据从磁盘/网络到达
    |                   （CPU 切换到其他线程）
    v
数据就绪，拷贝到用户缓冲区
    |
    v
线程被唤醒，read() 返回
```

- 线程在整个 IO 期间被挂起，不能做其他工作
- 最简单的模型，适合少量慢速连接
- 一个连接占一个线程：10000 连接 = 10000 线程（内存爆炸）

### 非阻塞 IO（Non-blocking IO）

```
调用 read()
    |
    +-- 数据未就绪？立即返回 EAGAIN（不等待）
    |
    v
[忙等轮询] 一次又一次调用 read()
    |
    +-- 数据未就绪？再返回 EAGAIN
    |
    +-- 数据就绪了！read() 返回数据
```

### 异步 IO（Asynchronous IO）

```
调用 aio_read()  <-- 告诉内核："帮我读，完了通知我"
    |
    v
立即返回（不等待）
    |
    |   ... 内核在后台完成 IO + 数据拷贝到用户缓冲区 ...
    |
    v
IO 完成回调 / 信号 / 完成端口通知
    |
    v
数据已经在用户缓冲区了，直接处理
```

### 三种 IO 模型对比

| | 阻塞 IO | 非阻塞 IO | 异步 IO |
|---|---|---|---|
| 等待数据时 | 线程阻塞 | 立即返回，轮询 | 立即返回 |
| 数据拷贝 | 应用程序阻塞 | 应用程序阻塞 | 内核自动完成 |
| 线程效率 | 低（阻塞浪费） | 低（轮询浪费） | 高（完全异步） |
| 编程复杂度 | 简单 | 中等 | 复杂 |
| 适用场景 | 简单脚本 | 配合 select/epoll | 高性能服务器 |

```csharp
// C# 阻塞 IO vs 异步 IO 对比
using System.IO;

class IOComparisonDemo
{
    void ReadBlocking()
    {
        string content = File.ReadAllText("big_data.txt");
        Console.WriteLine(content.Length);
    }

    async Task ReadAsync()
    {
        string content = await File.ReadAllTextAsync("big_data.txt");
        // 底层：IOCP(Windows) / epoll(Linux)
        Console.WriteLine(content.Length);
    }
}
```

```cpp
// C++ 异步 IO（Windows IOCP）
#include <windows.h>

void AsyncIOExample() {
    HANDLE hFile = CreateFile(
        L"data.bin", GENERIC_READ, FILE_SHARE_READ,

```

> **"阻塞 IO 是'傻等'，非阻塞 IO 是'反复问好了没'，异步 IO 是'好了叫我'。面试要说清三者的本质区别：线程在等待阶段的行为。"**

## 5.3 🔴 IO 多路复用

### 问题：如何高效处理多个 Socket 连接？

```
最朴素方案：每个连接一个线程
  10000 个连接 = 10000 个线程 -> 10GB 内存！-> 不可行

IO 多路复用：一个线程监视多个 Socket
    某个 Socket 就绪时才通知应用处理 -> 一个线程处理数万连接
```

### select -- 最古老的方案

```c
fd_set read_fds;
FD_ZERO(&read_fds);
FD_SET(fd1, &read_fds);
FD_SET(fd2, &read_fds);
select(max_fd + 1, &read_fds, NULL, NULL, NULL);
```

**四个致命缺点**：1024 fd 上限、每次全量拷贝、O(N) 遍历、返回后仍需遍历。

### epoll -- 革命性改进

```c
int epfd = epoll_create(1);
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev); // 注册一次
int n = epoll_wait(epfd, events, MAX, -1); // 直接返回就绪 fd
```

### select / poll / epoll 对比

```
+------------------+---------------+---------------+-------------------+
|                  | select        | poll          | epoll             |
+------------------+---------------+---------------+-------------------+
| 数据结构          | fd_set(位图)  | pollfd 数组   | 红黑树+就绪链表    |
| fd 上限          | 1024          | 无限制        | 无限制            |
| 每次调用拷贝      | 全量拷贝      | 全量拷贝      | 不需要（持久存储） |
| 就绪检测复杂度    | O(N) 遍历     | O(N) 遍历     | O(1) 就绪链表     |
| 触发方式          | 水平触发      | 水平触发      | 水平 + 边缘触发   |
| 适用并发量        | < 1000        | < 10000       | 10万+            |
+------------------+---------------+---------------+-------------------+
```

### 水平触发（LT）vs 边缘触发（ET）

| | 水平触发（Level Trigger） | 边缘触发（Edge Trigger） |
|---|---|---|
| 触发条件 | 缓冲区有数据就一直通知 | 状态变化时通知一次 |
| 读取方式 | 可分多次读 | **必须一次性读完** |
| 性能 | 较低 | 较高 |
| 编程复杂度 | 低 | 高（需配合非阻塞 IO） |

### Reactor 三种方案

| 方案 | 架构 | 代表 | 优缺点 |
|------|------|------|--------|
| 单 Reactor 单线程 | Reactor 负责全部 | Redis 6.0之前 | 简单但无法利用多核 |
| 单 Reactor 多线程 | Reactor + 线程池 | -- | 利用多核，但 Reactor 是瓶颈 |
| 主从 Reactor 多线程 | Main + 多 Sub Reactor + 线程池 | Nginx, Netty | 工业级首选 |

### Unity 关联

Unity Transport Package 底层：Windows=IOCP, Linux=epoll, macOS=kqueue

### 面试提示

> **"select/poll/epoll 三个关键词：1024限制、无限制但仍遍历、红黑树+O(1)返回。"**

> **"边缘触发必须一次性读完数据——这是面试常考的坑。"**

## 5.4 🟡 零拷贝技术

### 传统文件传输问题

```
传统 IO 数据流向：

磁盘 -> (DMA) -> Page Cache -> (CPU) -> 用户缓冲区 -> (CPU) -> Socket缓冲区 -> (DMA) -> 网卡

总结：4次上下文切换 + 2次 CPU 拷贝 + 2次 DMA 拷贝
```

### mmap + write（减少 1 次 CPU 拷贝）

```
buf = mmap(file, len);   // Page Cache 映射到用户地址空间
write(socket, buf, len); // 1次 CPU 拷贝

总结：4次上下文切换 + 1次 CPU 拷贝 + 2次 DMA 拷贝
```

### sendfile + SG-DMA（真正的零拷贝）

```
sendfile(socket_fd, file_fd, NULL, len);
Page Cache -> SG-DMA 直接读取到网卡

总结：2次上下文切换 + 0次 CPU 拷贝 + 2次 DMA 拷贝
```

### 零拷贝技术对比

```
+------------------+-----------+----------+----------+-----------+
|                  | 传统IO    | mmap     | sendfile | SG-DMA    |
+------------------+-----------+----------+----------+-----------+
| CPU 拷贝次数      | 2次       | 1次      | 1次      | 0次       |
| DMA 拷贝次数      | 2次       | 2次      | 2次      | 2次       |
| 上下文切换次数    | 4次       | 4次      | 2次      | 2次       |
| 经过用户态        | 是        | 是       | 否       | 否        |
+------------------+-----------+----------+----------+-----------+
```

**Unity 关联**：大型 AssetBundle 的加载可通过零拷贝技术优化，Unity 内部利用 mmap 或类似机制避免不必要的内存拷贝。

### 面试提示

> **"零拷贝不是说完全没有数据拷贝，而是说没有 CPU 参与的数据拷贝。DMA 芯片在搬运数据，CPU 完全空闲。"**

## 5.5 🟡 Reactor vs Proactor

### Reactor（同步非阻塞 IO）

```
注册 socket 到 epoll -> 等待事件 -> 事件就绪通知应用 -> 应用自己 read/write
```

### Proactor（异步 IO）

```
发起 aio_read() -> 内核后台完成 IO -> 完成后通知应用 -> 数据已在缓冲区
```

### 对比

| | Reactor | Proactor |
|---|---|---|
| IO 模型 | 同步非阻塞 | 异步 IO |
| IO 操作由谁做 | 应用程序 | 操作系统 |
| 通知时机 | fd 就绪 | IO 完成 |
| Linux 实现 | epoll | io_uring / libaio |
| Windows 实现 | -- | IOCP |

### Unity 关联

Unity 网络库：Windows=IOCP(Proactor), Linux/Android=epoll(Reactor)

### 面试提示

> **"Reactor 是'通知你可以读了'（同步），Proactor 是'帮你读完了'（异步）。Linux 主流是 Reactor，因为 epoll 比 AIO 成熟。"**

## 6.1 🟡 网络性能指标

### 四个核心指标

| 指标 | 定义 | 影响因素 | Unity 场景 |
|------|------|---------|-----------|
| 带宽 | 单位时间内传输的最大数据量 | 网卡速率、链路带宽 | 大文件下载 |
| 吞吐量 | 单位时间内实际传输的数据量 | 网络拥塞、协议开销 | 实时对战数据同步 |
| 延迟（Latency）| 数据从发送到接收的时间 | 物理距离、路由跳数、处理时间 | 网络操作响应速度 |
| 并发连接数 | 同时维持的 TCP 连接数量 | fd 上限、内存、协议栈 | MMO 在线人数 |

### 延迟分解

```
总延迟 = 发送延迟 + 传播延迟 + 处理延迟 + 排队延迟

发送延迟 = 数据量 / 带宽（发送第一个 bit 到最后一个 bit 的时间）
传播延迟 = 距离 / 光速（数据在链路中传输的时间）
处理延迟 = 路由器/交换机处理包头的时间（微秒级）
排队延迟 = 在路由器缓冲区排队等待的时间（网络拥塞时严重）
```

### 单位换算

```
1 Byte = 8 bit
1 MB/s = 8 Mbps（注意：运营商说的是 Mbps，下载软件显示的是 MB/s）
1 Gbps = 125 MB/s

例：100 Mbps 宽带 → 理论下载速度 12.5 MB/s
```

### 常见延迟参考

| 场景 | 延迟 |
|------|------|
| 本机进程通信 | < 0.1ms |
| 同城机房 | 1-5ms |
| 跨省（国内）| 10-30ms |
| 跨国（中国-美国）| 150-300ms |
| 4G 移动网络 | 30-100ms |
| 卫星网络 | 500ms+ |

### Unity 关联

```
| 网络类型 | 延迟 | 适合的网络方案 |
|----------|------|---------------|
| 局域网（LAN）| 1-5ms | UNet Mirror, Netcode |
| 同城服务器 | 10-20ms | 实时同步（如 FPS）|
| 跨省服务器 | 30-60ms | 帧同步可接受 |
| 跨国/移动网络 | 100ms+ | 回合制、异步同步 |
```

### 面试提示

> **"带宽决定天花板，延迟决定体验。100Mbps 带宽和 10ms 延迟比，后者对实时游戏更重要。"**

## 6.3 🟢 CPU 与调度

### 负载平均值（Load Average）

```bash
uptime
# 14:32:01 up 5 days, 2:30, 1 user, load average: 2.50, 1.80, 1.20
#                                        分钟   5分钟   15分钟
# 含义：过去 N 分钟内，平均有多少进程在等待 CPU 或处于不可中断 IO

# 判断标准：
# load < CPU核数    -> 空闲
# load = CPU核数    -> 满载
# load > CPU核数    -> 过载（进程在排队）
# load > CPU核数*2  -> 严重过载
```

### CPU 使用率解读

```
top 显示的 CPU 使用率分解：
%us  用户态进程占用
%sy  内核态占用（系统调用、中断处理）
%ni  nice 优先级进程占用
%id  空闲
%wa  IO 等待（等待磁盘/网络 IO）
%hi  硬中断占用
%si  软中断占用
%st  虚拟机被宿主机"偷走"的 CPU（steal time）

%wa 高 = IO 瓶颈
%us 高 = 用户程序计算密集
%sy 高 = 系统调用频繁或内核问题
```

### 上下文切换

```
上下文切换（Context Switch）：
  CPU 从一个进程/线程切换到另一个时，需要保存/恢复寄存器状态
  每次切换开销约 1-10 微秒

  cs（context switch）> 10万/秒 = 可能存在问题

  减少上下文切换的方法：
  1. 减少线程数（线程池）
  2. 绑定 CPU 亲和性（减少跨核切换）
  3. 减少锁竞争（锁导致线程阻塞和唤醒）
```

### Unity 关联

```
Unity 多线程优化：
- Job System + Burst Compiler 减少上下文切换
- 主线程不超过 33ms（30fps 目标）/ 16ms（60fps 目标）
- Profiler 中看 "GFX.WaitForPresent" 表示 CPU 在等 GPU
- Profiler 中看 "WaitForJob" 表示主线程在等工作线程完成
```

### 面试提示

> **"load average 不能只看绝对值——4核机器 load=4 和 64核机器 load=4 完全不同。关键是看 load 和 CPU 核数的比值。"**

## 7.1 🔴 27 高频题速查表

### 内存管理（7题）

| # | 题目 | 速答 |
|---|------|------|
| 1 | 页表是什么？为什么需要 TLB？ | 页表是虚拟地址到物理地址的映射表。TLB 缓存最近使用的映射，避免每次内存访问都查页表（多级页表需要多次内存访问） |
| 2 | 为什么页大小是 4KB？ | 权衡：太小→页表太大；太大→内存浪费（内部碎片）。4KB 适合大多数场景 |
| 3 | 多级页表为什么能节省空间？ | 只在需要时分配页表页。32位系统两级页表：一级1024项，二级1024项。不用的二级页表可以不分配物理内存 |
| 4 | 伙伴系统如何解决外部碎片？ | 将空闲内存按 2^k 分组，分配时找最接近的块，合并时检查伙伴。快速分配大块连续内存 |

### 场景题 2：内存泄漏排查

**问题**：Unity 应用运行一段时间后内存持续增长

**排查思路**：
```
1. Unity Profiler Memory 模块
   - 快照对比：两个时间点的内存差异
   - Mono UsedSize 持续增长 = 托管泄漏

   - AssetBundle 未 Unload

   - 手动触发 GC.Collect()，观察内存是否回落
   - 用 Deep Profile 找到分配热点
```

**答案要点**：
> "内存泄漏分两种：托管堆泄漏（C# 对象未释放）和原生资源泄漏（Unity 原生对象未销毁）。用 Profiler Memory 模块做快照对比，看 Mono UsedSize 还是 Native 增长。托管泄漏常见于事件监听未取消、静态集合；原生泄漏常见于 Texture/AudioClip 未 Destroy。"

## 7.3 🔴 12 模拟面试题

### 基础（4题）

**1. 进程和线程的区别？**
> "进程是资源分配的基本单位，线程是 CPU 调度的基本单位。进程有独立的地址空间，线程共享所属进程的地址空间。切换开销：进程切换需要切换页表、刷 TLB；线程切换只需保存/恢复寄存器和栈指针。多线程可以并行利用多核 CPU，但需要注意同步问题。"

**2. 什么是死锁？如何避免？**
> "死锁是两个或多个进程互相持有对方需要的资源，导致永久等待。四个必要条件：互斥、占有并等待、不可抢占、循环等待。避免死锁的方法：资源有序分配（打破循环等待）、银行家算法（安全状态检测）、超时机制（等待超时后释放资源）。"

**3. 用户态和内核态的区别？如何切换？**
> "用户态只能访问用户空间内存和受限指令，内核态可以访问所有内存和硬件。切换方式：系统调用（自愿，如 open/read）、中断（被动，如时钟中断、IO 完成）、异常（如缺页中断）。切换开销大，需要保存/恢复寄存器、切换栈。"

**4. 虚拟内存的作用？**
> "虚拟内存为每个进程提供独立的虚拟地址空间，实现内存隔离。作用：1) 进程隔离（A 不能访问 B 的内存）。2) 大内存错觉（32位进程可访问 4GB 地址空间，实际物理内存可能只有 1GB）。3) 按需分页（只加载需要的页面，节省物理内存）。4) COW fork（fork 时不复制，写时才复制）。"

### 进阶（4题）

**5. CFS 调度算法如何工作？**
> "CFS（完全公平调度器）使用红黑树维护所有可运行任务，键值是虚拟运行时间（vruntime）。vruntime 小的任务优先执行。每个任务的 vruntime 增长速度与权重成反比——权重高的任务 vruntime 增长慢，获得更多 CPU 时间。默认时间片是 6ms（sched_latency_ns/nr_running），但受 nice 值权重影响。"

**6. epoll 的实现原理？**
> "epoll 内核数据结构：红黑树存储所有监控的 fd，就绪链表存储已就绪的 fd。流程：1) epoll_create 创建实例。2) epoll_ctl 向红黑树添加/删除 fd（注册回调函数）。3) 当 fd 就绪时，回调将其加入就绪链表。4) epoll_wait 直接返回就绪链表中的 fd，O(1) 复杂度。支持 ET（边缘触发）和 LT（水平触发）。"

**7. 页表的作用？为什么需要 TLB？**
> "页表将虚拟地址映射到物理地址。多级页表（如4级）节省空间：只在需要时分配下级页表。但每次内存访问需要查 4 次页表 = 4 次额外内存访问。TLB（Translation Lookaside Buffer）缓存最近使用的页表项，命中时 1 次访问即可，大幅减少地址转换开销。进程切换时需要刷 TLB（或使用 ASID 避免）。"

**8. 零拷贝的实现原理？**
> "传统文件传输：磁盘→Page Cache→用户缓冲区→Socket 缓冲区→网卡，4次上下文切换+2次CPU拷贝。零拷贝方案：1) mmap+write：将 Page Cache 映射到用户地址空间，减少1次CPU拷贝。2) sendfile：数据从 Page Cache 直接到网卡。3) sendfile+SG-DMA：结合 scatter-gather，实现 0 次 CPU 拷贝。Linux 5.x io_uring 进一步优化了异步零拷贝。"

### 深入（4题）

**9. 进程间通信方式有哪些？各自适用场景？**
> "1) 管道（pipe）：父子进程间，半双工。2) 命名管道（FIFO）：任意进程间，基于文件系统。3) 消息队列：内核中维护消息链表，适合异步通信。4) 共享内存：最快的方式，但需要信号量同步。5) 信号量：用于进程间同步。6) 信号：异步通知（如 SIGKILL）。7) Socket：支持网络通信，最通用。Unity 中常用 Socket 做客户端-服务器通信。"

**10. COW 的原理和应用场景？**
> "COW（Copy-On-Write）：fork 时父子进程共享物理页，标记为只读。当任一方写入时触发缺页中断，内核复制该页并更新页表。场景：1) fork 后立即 exec（几乎不复制，直接加载新程序）。2) malloc 大块内存后 fork（避免立即复制）。3) Java/C# 的字符串不可变性（String 优化）。性能关键：缺页中断处理需在内核态完成，频繁写入时 COW 反而更慢。"

**11. 内存分配的层级结构？**
> "应用层：malloc/new → C库：ptmalloc/jemalloc/tcmalloc → 内核：伙伴系统（大块）/slab（小块）→ 硬件：物理内存。层级：1) 用户态分配器管理进程堆。2) 超过阈值通过 brk/mmap 向内核申请。3) 内核用伙伴系统管理物理页面（按 2^k 分组）。4) 小对象用 slab 分配器预分配（避免碎片）。Unity 的托管堆由 Mono/IL2CPP GC 管理，与 OS 分配器配合。"

**12. 作业系统的 IO 模型演进？**
> "1) 阻塞 IO：线程等待数据完成。2) 非阻塞 IO：立即返回 EAGAIN，轮询。3) IO 多路复用：select/poll/epoll 监控多个 fd。4) 异步 IO（AIO）：发起后立即返回，完成时回调。5) io_uring（Linux 5.x）：统一异步 IO 接口，支持批量提交+批量收割，性能最优。Unity 的 async/await 在 Windows 基于 IOCP（异步IO），Linux 基于 epoll（IO多路复用）。"

## 8.1 🔴 Mono / IL2CPP 垃圾回收

### Mono GC（标记-清除）

```
Mono 使用 Boehm GC（非分代、非压缩）

标记阶段：
  从根集合（Root Set）出发，遍历所有可达对象
  根集合包括：静态变量、栈上的引用、寄存器中的引用

清除阶段：
  回收所有未标记的对象（不可达 = 可回收）

问题：
  - 非分代：每次 GC 遍历全部对象（O(N)），暂停时间长
  - 非压缩：不移动对象，内存碎片化
  - Stop-the-World：GC 期间所有线程暂停
```

### IL2CPP GC（增量式）

```
IL2CPP 支持增量式 GC（Incremental GC）

原理：
  将标记阶段分成多个小步，每帧执行一小部分
  每帧暂停时间从 100ms+ 降到 1-5ms

  帧1: 标记 10% 的对象
  帧2: 标记 10% 的对象
  ...
  帧10: 标记完成，执行清除

开启方式：
  Player Settings -> Other Settings -> Incremental GC

注意：
  - 仍然是标记-清除，不是分代
  - 清除阶段仍需 Stop-the-World
  - 对帧率敏感的应用必须开启
```

### Mono vs IL2CPP GC 对比

| | Mono GC | IL2CPP 增量式 GC |
|---|---|---|
| 算法 | Boehm（非分代）| 增量标记-清除 |
| 暂停时间 | 长（100ms+）| 短（1-5ms/帧）|
| 吞吐量 | 较低 | 较高 |
| 内存碎片 | 严重 | 较好（但仍存在）|
| 适用场景 | 原型/小型项目 | 大型/商业项目 |

### 减少 GC 压力的实践

```csharp
// ❌ 错误：每帧分配
void Update()
{
    string msg = "Score: " + score.ToString();  // 每帧 new String
    Vector3[] positions = new Vector3[100];      // 每帧 new 数组
    List<int> tempList = new List<int>();        // 每帧 new List
}

// ✅ 正确：复用 + 预分配

    // 1. StringBuilder 复用
    _sb.Clear();
    _sb.Append("Score: ");
    _sb.Append(score);

    // 2. 数组池复用
    Vector3[] _buffer = ArrayPool<Vector3>.Shared.Rent(100);
    try { /* 使用 _buffer */ }
    finally { ArrayPool<Vector3>.Shared.Return(_buffer); }

    // 3. List 清空复用（不 new）
    _tempList.Clear();  // 不会释放内部数组
```

### 常见 GC 触发场景与对策

| 场景 | 原因 | 对策 |
|------|------|------|
| 字符串拼接 | 每次拼接创建新 String 对象 | StringBuilder / 字符串池 |
| LINQ 查询 | 内部创建临时集合和枚举器 | 手动循环替代 LINQ |

### Unity 关联

```csharp

// - Mono UsedSize: 托管堆当前使用量
// - Mono Heap Size: 托管堆总分配量
// - GC Alloc: 每帧的托管分配量（应尽可能为 0）
// - GC 时间: 每次 GC 的暂停时间
//
// Deep Profile 看 GC.Alloc 热点
```

### 面试提示

> **"Mono GC 是分代式（实际上是 Boehm 非分代），IL2CPP 用增量式 GC。核心问题都是 Stop-the-World 暂停。Unity 2021+ 默认开启增量式 GC，将暂停分摊到多帧，但消除暂停的唯一办法是减少分配。"**

> **"GC 不是定时触发的，而是内存分配达到阈值时触发。如果每帧分配 1KB，100帧后就可能触发一次 GC——这就是为什么'每帧 new'会导致周期性卡顿。"**

## 8.2 🔴 资源生命周期管理

### Unity 内存区域

```
Unity 应用内存布局：

+----------------------------------------------------------+
|                     虚拟内存空间                           |
+----------------------------------------------------------+
| 托管堆（Mono/IL2CPP GC 管理）                            |
|   - C# 对象（class 实例）                                |
|   - 字符串、数组、委托                                    |
|   - 通过 new 分配，GC 自动回收                            |
+----------------------------------------------------------+
| 原生内存（Unity 引擎管理）                                |
|   - Texture2D, AudioClip, Mesh 等原生资源                 |
|   - Physics 碰撞体                                       |
|   - UI 渲染数据                                          |
|   - 通过 Resources.Load / AssetBundle 加载                |
+----------------------------------------------------------+
| 显存（VRAM，GPU 专用）                                    |
|   - 纹理 GPU 数据                                        |
|   - 着色器常量                                           |
|   - 顶点缓冲区                                           |
+----------------------------------------------------------+
```

### 原生资源生命周期

```
加载阶段：
  Resources.Load("prefab")  ->  C# 对象（托管）+ 原生资源（原生）+ GPU 数据（显存）
  AssetBundle.LoadAsset()    ->  同上
  Addressables.LoadAsset()   ->  同上

使用阶段：
  - 原生资源被 C# 对象引用
  - 引用计数 >= 1 时资源保持存活

释放阶段（关键！）：
  1. Destroy()             -> 释放单个原生资源
  2. Resources.UnloadUnusedAssets() -> 释放无引用的原生资源
  3. AssetBundle.Unload(true)       -> 卸载整个 AB 及其所有资源
  4. AssetBundle.Unload(false)      -> 卸载 AB 本身，保留已加载的资源

危险操作：
  - Destroy(gameObject) 后仍持有 Texture2D 引用 -> 内存泄漏！
  - AssetBundle.Unload(true) 后仍使用其资源 -> Missing Reference Exception！
```

### 资源泄漏的三种情况

```
情况1: 托管泄漏（C# 引用未释放）
  持有对象引用 -> 即使资源"释放"，GC 无法回收
  排查：Profiler Memory -> Mono UsedSize 持续增长

情况2: 原生泄漏（Unity 原生对象未 Destroy）
  Texture2D/AudioClip 未 Destroy -> 原生内存持续增长
  排查：Profiler Memory -> Native UsedSize 持续增长

情况3: 显存泄漏（GPU 资源未释放）
  高分辨率纹理未释放 -> 显存占用持续增长
  排查：Frame Debugger / RenderDoc
```

### Addressables 资源管理最佳实践

```csharp
using UnityEngine.AddressableAssets;
using UnityEngine.ResourceManagement.AsyncOperations;

class AddressableManager : MonoBehaviour
{
    // 加载
    AsyncOperationHandle<Texture2D> _texHandle;

    async void LoadTexture(string key)
    {
        _texHandle = Addressables.LoadAssetAsync<Texture2D>(key);
        await _texHandle.Task;
        myImage.sprite = Sprite.Create(
            _texHandle.Result,
            new Rect(0, 0, _texHandle.Result.width, _texHandle.Result.height),
            Vector2.one * 0.5f
        );
    }

    // 卸载（关键！）
    void UnloadTexture()
    {
        if (_texHandle.IsValid())
        {
            Addressables.Release(_texHandle);  // 释放引用计数
        }
    }

    void OnDestroy()
    {
        UnloadTexture();
    }
}
```

### 面试提示

> **"Unity 内存管理的核心是：托管堆靠 GC（减少分配），原生内存靠手动释放（及时 Destroy/Unload），显存靠纹理分级（Mipmap/压缩）。三块内存要分别管理，不能混为一谈。"**

> **"最常犯的错误：Destroy(gameObject) 以为释放了所有内存，实际上 Texture2D 等原生资源的引用还在其他地方，导致原生内存泄漏。"**

## 8.3 🟡 Unity 内存与 OS 虚拟内存的关系

### OS 虚拟内存对 Unity 的影响

| OS 概念 | 对 Unity 的影响 |
|---------|----------------|
| 每个进程有独立虚拟地址空间 | Unity 的托管堆、原生内存都在用户态虚拟地址空间中 |
| 物理内存不够时 OS 换页（Swap）| Unity 资源加载慢可能是 OS 在做 Swap（iowait 高）|
| mmap 文件映射 | AssetBundle.LoadFromFile 底层可能用 mmap |
| OOM Killer | Android 会在内存不足时杀后台 Unity 应用 |
| Page Cache | 重复加载同一资源时受益于 OS 的 Page Cache |

### 内存监控工具对比

| 工具 | 用途 | 层级 |
|------|------|------|
| Unity Profiler | 托管堆 + 原生内存分析 | Unity 层 |
| RenderDoc | GPU 显存分析 | 显存层 |
| Android Studio Profiler | Android 应用内存分析 | OS 层 |
| Instruments (Xcode) | iOS 应用内存分析 | OS 层 |
| /proc/pid/status | Linux 进程内存状态 | OS 层 |
| valgrind / leakcanary | 内存泄漏检测 | OS 层 |

### Unity Profiler Memory 模块

```
关键指标解读：

Total Used Memory:      应用总内存占用
  ├─ Mono UsedSize:     托管堆使用量（C# 对象）
  ├─ Native:            Unity 原生资源（Texture/Mesh/Audio）
  ├─ Profiler:          Profiler 自身开销
  └─ Other:             其他内存

Mono UsedSize:
  - 理想值：< 50MB（中型游戏）
  - 危险值：> 200MB（可能频繁 GC）

Native UsedSize:
  - 与加载的资源量成正比
  - 及时卸载不需要的资源

Reserved Total / Used Total:
  - Reserved: 向 OS 申请的总量
  - Used: 实际使用量
  - 差值越大 = 内存浪费越多
```

### Unity 内存优化检查清单

```
□ 托管堆优化
  □ 避免 Update 中 new 对象
  □ 使用 StringBuilder 替代字符串拼接
  □ 用对象池复用频繁创建的对象
  □ 避免 LINQ 在热路径使用
  □ 开启增量式 GC

□ 原生资源优化
  □ 纹理使用合适压缩格式（ASTC/ETC2）
  □ 使用 Mipmap 减少显存
  □ 及时 Destroy 不再使用的资源
  □ 使用 Addressables 按需加载/卸载
  □ 避免 Resources.Load 同步加载

□ 显存优化
  □ 纹理分级加载（远距离低分辨率）
  □ 精灵图集合并小纹理
  □ 使用 GPU Instancing 减少 Draw Call
  □ 避免全屏特效链过长

□ OS 层面优化
  □ Android: 使用 largeHeap=true
  □ iOS: 控制内存 < 1GB（系统限制）
  □ 监控 Swap 使用（iowat 高 = 内存不足）
  □ 测试不同设备的内存限制
```

### 面试提示

> **"Unity 内存优化的优先级：先用 Profiler 定位瓶颈（是 Mono 还是 Native 还是显存），再针对性优化。不要盲目优化——有时候 100MB 的优化比 10MB 的优化更值得投入。"**
