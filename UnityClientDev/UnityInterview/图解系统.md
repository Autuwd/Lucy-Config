## 02｜硬件结构篇

### 2.1 CPU 是如何执行程序的？

#### 核心概念：冯·诺依曼体系结构

计算机由五部分组成：**运算器、控制器、存储器、输入设备、输出设备**。

CPU 内部关键组件：
- **程序计数器（PC）**：存放下一条指令的内存地址
- **指令寄存器（IR）**：存放当前正在执行的指令
- **算术逻辑单元（ALU）**：执行算术 / 逻辑运算
- **通用寄存器**：暂存操作数和运算结果（速度最快，容量最小）

#### CPU 执行指令的完整流程（指令周期）

```
① 取指（Fetch）
   PC → 内存地址 → 从内存读取指令 → 送入 IR
   PC 自动递增，指向下一条指令

② 译码（Decode）
   控制单元解析 IR 中的指令，识别操作类型和操作数

③ 执行（Execute）
   ALU 根据指令执行运算，结果暂存到寄存器

④ 写回（Write Back）
   将结果写回到寄存器或内存
```

#### ⚠️ 容易混淆：指令 vs 数据

- **程序 = 指令 + 数据**，都存在内存里
- CPU 用 PC 知道去哪里取指令，用指令里的操作数知道去哪里取数据
- 内存里的内容本身没有区别，是"指令"还是"数据"取决于 CPU 如何使用它

#### 🔧 面试高频

**Q：32 位 CPU 和 64 位 CPU 的区别？**
- 32 位 CPU：寄存器宽度 32 位，一次最多处理 32 位数据；寻址空间 2³² = 4GB
- 64 位 CPU：寄存器宽度 64 位；寻址空间 2⁶⁴（理论值），实际 Linux x86_64 用户空间约 128TB

### 2.2 磁盘比内存慢几万倍？

#### 存储器的层次结构（从快到慢，从贵到便宜）

```
CPU寄存器   ~1 时钟周期       容量：<1KB
  ↓
L1 Cache    ~4 周期          容量：32-64 KB / 核心
  ↓
L2 Cache    ~12 周期         容量：256 KB - 1 MB / 核心
  ↓
L3 Cache    ~40 周期         容量：4-64 MB（多核共享）
  ↓
内存 (DRAM)  ~200 周期        容量：GB 级别
  ↓
固态硬盘     ~10万 周期        容量：TB 级别
  ↓
机械硬盘     ~1000万 周期      容量：TB 级别
```

> **关键数字**：内存比 L1 Cache 慢约 50 倍；机械磁盘比内存慢约 5 万倍

#### ⚠️ 为什么需要 Cache？

CPU 速度提升远超内存，形成"内存墙"。Cache 是弥合二者速度差距的关键。

#### CPU 访问 Cache 的工作原理

1. CPU 先看 L1 Cache 有没有 → 没有再看 L2 → 再看 L3 → 最后去内存
2. **缓存命中（Cache Hit）**：直接从 Cache 读取
3. **缓存缺失（Cache Miss）**：从内存加载整个 **缓存行（Cache Line）** 到 Cache（通常 64 字节）
4. 为什么加载一整行？—— 基于**空间局部性**：程序访问某地址后，很可能很快访问相邻地址

### 2.3 如何写出让 CPU 跑得更快的代码？

#### 两种局部性原理

| 局部性类型 | 含义 | 代码示例 |
|------------|------|----------|
| **时间局部性** | 最近访问过的数据很快会再次访问 | 循环体内的变量 |
| **空间局部性** | 访问某地址后，很快访问附近地址 | 顺序遍历数组 |

#### 核心案例：二维数组遍历顺序对 Cache 命中率的影响

```c
// ✅ 按行遍历（利用空间局部性，Cache 友好）
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        sum += a[i][j];   // a[i][0], a[i][1], ... 在内存上连续

// ❌ 按列遍历（Cache 不友好，频繁 Cache Miss）
for (int j = 0; j < N; j++)
    for (int i = 0; i < N; i++)
        sum += a[i][j];   // a[0][j], a[1][j], ... 在内存上不连续，跨行
```

> **原理**：C 语言二维数组按行存储（Row-major），同一行元素在内存中连续，加载进同一个 Cache Line。按行遍历时，每次 Cache Miss 后，整个 Cache Line 被加载，后续同行访问直接命中。

#### 避免 CPU 分支预测失败

```c
// 对无序数组，CPU 分支预测命中率低 → 慢
for (int i = 0; i < N; i++)
    if (data[i] >= 128) sum += data[i];

// 对有序数组，CPU 分支预测命中率高 → 快（先sort再遍历反而更快！）
sort(data, data + N);
for (int i = 0; i < N; i++)
    if (data[i] >= 128) sum += data[i];
```

### 2.4 CPU 缓存一致性（MESI 协议）

#### 为什么会有缓存一致性问题？

多核 CPU 中，每个核心有独立的 L1/L2 Cache。如果两个核同时缓存了同一块内存，其中一个修改了，另一个的 Cache 就"脏了"——出现数据不一致。

#### Cache 写入的两种策略

| 策略 | 写 Cache 时的行为 | 优点 | 缺点 |
|------|-----------------|------|------|
| **写直达（Write Through）** | 同时写 Cache 和内存 | 一致性好 | 内存总线压力大，慢 |
| **写回（Write Back）** | 只写 Cache，标记为脏，等到被替换时再写回内存 | 性能好 | 需要额外的脏标记（Dirty bit） |

> Linux 等现代系统普遍使用**写回**策略，性能更优。

#### MESI 协议——四种缓存行状态

| 状态 | 含义 | 可读 | 可写 | 是否与内存一致 |
|------|------|------|------|--------------|
| **M（Modified 已修改）** | 数据被改过，只在本 Cache 里有最新值 | ✅ | ✅ | ❌（脏数据）|
| **E（Exclusive 独占）** | 只在本 Cache 里有该数据，未被修改 | ✅ | ✅（变为M）| ✅ |
| **S（Shared 共享）** | 多个 Cache 都有该数据，未被修改 | ✅ | ❌（需先广播失效） | ✅ |
| **I（Invalid 已失效）** | 本 Cache 里的数据无效（相当于不存在）| ❌ | ❌ | - |

#### MESI 状态机工作流程（关键场景）

```
场景：核心 A 读 → 核心 B 读 → 核心 A 写

1. 核心 A 读 x：Cache Miss → 从内存加载 → 状态变 E（Exclusive，只有 A 有）
2. 核心 B 读 x：总线嗅探到 A 有 x → A 的状态变 S，B 也变 S（Shared，共享）
3. 核心 A 写 x：
   a. 广播"失效"消息给所有其他核心
   b. B 的缓存行状态变 I（Invalid）
   c. A 的缓存行状态变 M（Modified），写入新值
4. 核心 B 之后再读 x：Cache Miss（状态为 I）→ 需等 A 把脏数据写回内存（或直接转发）
```

#### ⚠️ 容易混淆：MESI 和伪共享（False Sharing）

**伪共享（False Sharing）**：两个不相关的变量恰好在同一个 Cache Line 上，一个核修改时会导致另一个核的整条 Cache Line 失效，即使另一个核根本没改它关心的那个变量。

```c
// ❌ 可能产生伪共享：x 和 y 可能在同一个 64 字节 Cache Line 里
struct { int x; int y; } shared;

// ✅ 解决：填充对齐，让每个变量独占一个 Cache Line
struct { int x; char pad[60]; } var_a;
struct { int y; char pad[60]; } var_b;
```

#### 总线嗅探（Bus Snooping）

各个 CPU 核心通过监听总线上的所有内存操作，来感知其他核心是否修改了自己缓存的数据。这是 MESI 协议的底层实现机制。

### 2.5 CPU 是如何执行任务的？

#### 用户态 vs 内核态

| | 用户态（User Mode） | 内核态（Kernel Mode）|
|---|---|---|
| 权限 | 低（Ring 3） | 高（Ring 0）|
| 可访问资源 | 用户地址空间 | 全部内存、硬件 |
| 触发时机 | 正常程序执行 | 系统调用、中断、异常 |
| 切换代价 | — | 高（保存/恢复上下文）|

#### 上下文切换（Context Switch）

**什么是 CPU 上下文（CPU Context）？**

CPU 执行任何任务前，需要知道**从哪里开始执行（PC）** 和**有哪些数据（寄存器值）**，这两者合称 CPU 上下文。

**切换过程：**
```
保存旧任务的 CPU 上下文（PC + 寄存器）→ 写入该任务的 PCB/TCB
加载新任务的 CPU 上下文（从新任务的 PCB/TCB 读取）
跳转到新任务的 PC 位置继续执行
```

#### 触发上下文切换的场景

1. 时间片耗尽（时钟中断触发）
2. 进程主动睡眠（sleep/wait 系统调用）
3. 进程等待 I/O（I/O 阻塞）
4. 更高优先级进程就绪（抢占式调度）
5. 硬件中断（CPU 被强制切换去执行中断处理程序）

#### 进程上下文 vs 线程上下文 vs 中断上下文

| 类型 | 切换时保存的内容 | 开销 |
|------|---------------|------|
| 进程上下文 | 寄存器、PC、**虚拟内存（页表切换）**、文件描述符等 | **最大** |
| 线程上下文（同进程） | 寄存器、PC、**不需要切换页表（共享虚拟内存）** | **较小** |
| 中断上下文 | 当前 CPU 寄存器（现场保护，极少量数据） | **最小** |

### 2.6 什么是软中断？

#### 中断的完整分类

```
中断
├── 外部中断（硬中断）
│   ├── 可屏蔽中断：网卡、磁盘、键盘等硬件产生（可用 IF 标志位屏蔽）
│   └── 不可屏蔽中断（NMI）：硬件故障，不能被忽略
└── 内部中断（异常）
    ├── 故障（Fault）：可恢复，如缺页中断（Page Fault）
    ├── 陷阱（Trap）：主动触发，如系统调用（int 0x80）
    └── 中止（Abort）：不可恢复，如除零
```

#### 为什么要有软中断？

硬中断处理程序（ISR）**必须极快完成**（一般禁止在 ISR 中睡眠/阻塞），只做最紧急的事（读取硬件数据到内核缓冲区）。

但网络数据包解析、协议处理等任务耗时很长，不适合放在 ISR 里。于是引入**软中断（SoftIRQ）**：

```
硬件触发 → 硬中断处理程序（上半部）
    └── 记录软中断待处理标志
    └── 退出硬中断

内核 ksoftirqd 线程（下半部）
    └── 检测软中断标志
    └── 执行耗时的软中断处理（如网络包处理 NET_RX_SOFTIRQ）
```

#### ⚠️ 软中断 vs tasklet vs 工作队列

| 机制 | 运行上下文 | 能否睡眠 | 适用场景 |
|------|---------|---------|---------|
| **软中断** | 中断上下文 | ❌ | 网络收发、定时器 |
| **tasklet** | 中断上下文（基于软中断实现） | ❌ | 普通设备驱动 |
| **工作队列** | 进程上下文（内核线程） | ✅ | 需要睡眠的耗时任务 |

#### 🔧 实际问题：软中断 CPU 占用过高

```bash
# 查看软中断统计
cat /proc/softirqs

# 如果 NET_RX（网络接收软中断）的某个 CPU 核占比异常高
# 说明网络包处理集中在少数核，可考虑 RSS/RPS 将网络中断分散到多核
```

### 2.7 为什么 0.1 + 0.2 不等于 0.3？

#### IEEE 754 浮点数格式

**单精度（float，32位）：** 1位符号 + 8位指数 + 23位尾数  
**双精度（double，64位）：** 1位符号 + 11位指数 + 52位尾数  

```
(-1)^符号位  ×  1.尾数  ×  2^(指数-偏移量)
```

#### 为什么 0.1 无法精确表示？

将 0.1（十进制）转换为二进制：

```
0.1 × 2 = 0.2  → 0
0.2 × 2 = 0.4  → 0
0.4 × 2 = 0.8  → 0
0.8 × 2 = 1.6  → 1
0.6 × 2 = 1.2  → 1
0.2 × 2 = 0.4  → 0  ← 开始循环！

0.1 (十进制) = 0.00011001100110011... (二进制，无限循环)
```

由于尾数位数有限（double 52位），必须截断，产生**舍入误差**。

#### 计算过程

```
0.1 ≈ 0.1000000000000000055511151231257827021181583404541015625
0.2 ≈ 0.200000000000000011102230246251565404236316680908203125
相加 ≈ 0.3000000000000000444089209850062616169452667236328125
0.3 ≈ 0.299999999999999988897769753748434595763683319091796875

所以 0.1 + 0.2 ≠ 0.3 （差了约 5.5e-17）
```

#### 🔧 实际开发中如何处理？

```python
# Python 中比较浮点数
import math
math.isclose(0.1 + 0.2, 0.3)  # True

# 金融场景：使用 Decimal 精确计算
from decimal import Decimal
Decimal('0.1') + Decimal('0.2')  # Decimal('0.3')
```

## 03｜系统结构篇

### 3.1 Linux 内核 vs Windows 内核

#### 操作系统的内核架构分类

| 架构 | 代表系统 | 特点 | 优点 | 缺点 |
|------|---------|------|------|------|
| **宏内核（Monolithic）** | Linux | 所有内核服务（驱动、内存、文件系统等）都运行在**内核态** | 进程间不需切换特权级，效率极高 | 任一模块崩溃可能导致整个系统崩溃 |
| **微内核（Micro）** | Mach, L4 | 内核只保留最基本功能（IPC、内存映射），其余服务运行在**用户态** | 稳定性强、模块化 | 服务调用需要多次用户态/内核态切换，性能差 |
| **混合内核（Hybrid）** | Windows NT, macOS XNU | 吸收宏内核的高效和微内核的模块化 | 平衡性能与稳定性 | 设计复杂 |

#### Linux 内核架构

```
用户空间
    ↓ 系统调用接口（System Call Interface）
内核空间
  ├── 进程管理（process management）
  ├── 内存管理（memory management）
  ├── 虚拟文件系统 VFS（virtual file system）
  ├── 网络协议栈（network stack）
  └── 设备驱动（device drivers）
    ↓
硬件层（Hardware）
```

#### ⚠️ 关键区别：Linux 内核模块 vs Windows 驱动

- **Linux**：虽是宏内核，但支持**可加载内核模块（LKM）**，驱动可以动态插入/移除内核，无需重编译内核（`modprobe`, `insmod`）
- **Windows**：驱动也在内核态运行，但 Windows 内核更模块化，Hardware Abstraction Layer（HAL）隔离了硬件依赖

## 04｜内存管理篇

### 4.1 为什么要有虚拟内存？

#### 没有虚拟内存时的问题

若所有进程直接操作物理内存：
1. **安全问题**：进程 A 可以任意读写进程 B 的内存
2. **内存碎片**：多进程运行后物理内存变得支离破碎，无法装入新的大进程
3. **容量限制**：进程大小受物理内存限制，无法运行比物理内存更大的程序

#### 虚拟内存的核心思想

每个进程都拥有一个**独立的、连续的虚拟地址空间**（如 64 位系统每个进程都有 128TB 的虚拟空间），通过**页表（Page Table）**将虚拟地址映射到物理地址。

```
进程 A 虚拟地址空间                     物理内存
0x0000 ──────────────┐                 ┌─────── Page Frame 0
  ...               ├─ 页表映射 ──────→ ├─────── Page Frame 1
0xFFFF ──────────────┘                 ├─ ... 
                                       └─────── （部分在磁盘 Swap 上）
进程 B 虚拟地址空间
0x0000 ──────────────┐
  ...               ├─ 不同的页表 ─────→ 不同的物理页
0xFFFF ──────────────┘
```

#### 页表工作原理

**分页（Paging）**：
- 虚拟地址空间 = 虚拟页号（VPN）+ 页内偏移（Offset）
- 物理地址空间 = 物理页框号（PFN）+ 页内偏移
- **页大小（Page Size）**：通常 4KB（Linux 默认）

**TLB（Translation Lookaside Buffer）**：
- 页表查询很慢（需要访问内存），所以有 TLB 作为页表缓存
- **TLB 命中**：直接得到物理地址，极快
- **TLB Miss**：走页表查询（多级页表），再填入 TLB

#### 缺页中断（Page Fault）

当访问的虚拟地址没有对应的物理页时，CPU 触发缺页异常：
1. 操作系统接管，找到一个空闲物理页（或换出一个页到 Swap）
2. 将对应数据从磁盘读到该物理页
3. 更新页表，TLB 刷新
4. 重新执行刚才触发异常的那条指令

#### 🔧 面试高频：虚拟内存的作用（3点）

1. **进程隔离**：每个进程有独立地址空间，互不干扰
2. **内存超配（Memory Overcommit）**：进程"申请"内存时不立即分配物理页，只有真正访问时才通过缺页中断分配（Lazy Allocation）
3. **内存共享**：共享库（如 libc.so）可以映射到多个进程的虚拟空间，但只占一份物理内存

### 4.2 malloc 是如何分配内存的？

#### 进程的内存布局（从低到高地址）

```
高地址
┌─────────────────┐
│   内核空间        │  ← 用户态不可访问
├─────────────────┤ ← 0xC0000000（32位）
│   栈（Stack）     │  ← 向下增长，存放局部变量、函数调用帧
│   ↓              │
│  （空洞）         │
│   ↑              │
│  文件映射区/mmap  │  ← 动态库、mmap 映射的文件
│   ↑              │
│   堆（Heap）      │  ← 向上增长，malloc 申请的内存
├─────────────────┤ ← brk 指针位置
│   BSS 段（未初始化全局/静态变量）│
│   数据段（已初始化全局/静态变量）│
│   代码段（Text）  │  ← 只读，存放程序指令
└─────────────────┘
低地址
```

#### malloc 的分配策略（glibc ptmalloc2）

| 申请大小 | 分配方式 | 释放行为 |
|---------|---------|---------|
| **< 128 KB** | `brk()` 系统调用，移动堆顶指针（brk 指针）向高地址扩展 | `free()` 后**不立即归还系统**，加入内存池缓存，下次 malloc 可复用 |
| **≥ 128 KB** | `mmap()` 系统调用，在文件映射区申请一块匿名映射 | `free()` 后**立即调用 `munmap()` 归还**操作系统 |

> 这个阈值（128KB）在 glibc 中是可以通过 `mallopt(M_MMAP_THRESHOLD, ...)` 调整的。

#### ⚠️ 为什么 free 后内存不一定归还系统？

```c
void *p = malloc(100);   // 分配 100 字节（brk 方式）
free(p);                 // 释放，但只是放回 malloc 的内存池

// 进程从操作系统角度看，占用的虚拟内存没变
// 下次再 malloc，会优先复用内存池里的碎片
```

只有当**堆顶连续的空闲内存足够大**时，glibc 才会调用 `brk()` 缩减堆，真正归还系统。

#### 内存碎片问题

- **内部碎片**：malloc 分配的块比实际需要的大（对齐和最小分配粒度导致）
- **外部碎片**：大量小的空闲块零散分布，总量够但无法满足大块分配

### 4.3 内存满了，会发生什么？

#### Linux 内存水位线机制

```
物理内存总量
  ├── pages_high（高水位线）：内存充足，系统正常运行
  ├── pages_low（低水位线）：内存偏少，唤醒 kswapd 后台异步回收
  └── pages_min（最低水位线）：内存极少，当前进程直接参与同步回收
```

#### 两种内存回收方式

**① 后台异步回收（kswapd）**
- 触发条件：空闲页 < `pages_low`
- 执行者：内核线程 `kswapd`（后台运行，不影响当前进程响应）
- 回收策略：根据改进的 LRU 算法（见 4.5）淘汰页面

**② 直接同步回收（Direct Reclaim）**
- 触发条件：空闲页 < `pages_min`
- 执行者：当前进程本身被阻塞，参与内存回收
- 影响：系统响应严重卡顿

#### 可以被回收的页面类型

| 类型 | 是否可回收 | 说明 |
|------|----------|------|
| 文件缓存页（File-backed pages）| ✅ 直接丢弃 | 可从磁盘重新读取 |
| 脏页（Dirty File-backed pages）| ✅ 需先写回磁盘 | 修改过的文件缓存 |
| 匿名页（Anonymous pages，如 malloc）| ✅ 换入 Swap | 无文件对应，需写到 Swap 分区 |
| 内核不可回收页 | ❌ | 页表、内核代码等 |

#### OOM Killer 机制

当内存回收后依然不足时，OS 启动 **OOM Killer（Out-of-Memory Killer）**，强杀进程释放内存。

**OOM 得分计算（越高越先被杀）**：
```
oom_score = 进程占用物理内存的百分比 × 10 + oom_score_adj
```

- `oom_score_adj` 范围：-1000（永不被杀）~ 1000（优先被杀）
- 查看某进程的 OOM 分：`cat /proc/<pid>/oom_score`
- 保护关键进程：`echo -1000 > /proc/<pid>/oom_score_adj`

#### 🔧 实际场景

**Q：为什么数据库进程配置成不被 OOM Killer 杀死？**  
A：数据库（如 MySQL, Redis）一旦被杀，恢复代价极高。通过设置 `oom_score_adj = -1000` 让其不被 OOM 杀死。但这样其他进程就更容易被杀，需要合理规划内存。

### 4.4 在 4GB 物理内存的机器上，申请 8G 内存会怎么样？

#### 32 位 vs 64 位系统的差异

| 场景 | 结果 | 原因 |
|------|------|------|
| **32 位系统**，用户空间 3GB（或 2GB）| `malloc` 直接返回 NULL（失败） | 虚拟地址空间本身只有 3-4 GB，申请 8G 超出了虚拟空间限制 |
| **64 位系统**，申请 8G（不访问） | `malloc` 成功，返回非 NULL 指针 | 虚拟地址空间 128TB，只是占了虚拟地址，**没有分配物理内存**（Lazy Allocation） |
| **64 位系统**，申请 8G（全部写入）| 进程被 OOM Killer 杀死（无 Swap） | 实际写入触发缺页中断，物理内存不足，触发 OOM |
| **64 位系统**，申请 8G（全部写入，有足够 Swap）| 正常运行，但极慢 | 超出物理内存的部分换页到 Swap，频繁磁盘 I/O |

#### 内存 Overcommit 策略

Linux 内核通过 `/proc/sys/vm/overcommit_memory` 控制：
- `0`（默认）：启发式允许 overcommit，拒绝明显不合理的申请
- `1`：允许所有 overcommit，不限制
- `2`：不允许 overcommit，只能申请 (swap + 物理内存 × overcommit_ratio)% 的内存

### 4.5 如何避免预读失效和缓存污染的问题？

#### 传统 LRU 算法的缺点

**LRU（Least Recently Used，最近最少使用）**：
- 数据结构：双向链表 + 哈希表（O(1) 访问和删除）
- 规则：每次访问把节点移到头部，淘汰时删除尾部

**两大缺陷：**

**① 预读失效（Readahead Miss）**
- Linux 和 MySQL 会**预读**：访问第 N 页时，提前加载第 N+1, N+2 页到缓存
- 如果预读的页实际没被访问，却占据了链表头部，挤掉了真正的热数据

**② 缓存污染（Cache Pollution）**
- 执行 `SELECT * FROM big_table` 这种大范围扫描时，大量冷数据被读取一次后加入链表头部
- 把原本的热点数据全部挤到尾部被淘汰

#### Linux 的改进：双 LRU 链表

```
Active List（活跃链表）：存放经常被访问的热点页
    HEAD → [最近活跃] → ... → [久未活跃] → TAIL

Inactive List（非活跃链表）：存放最近较少访问的页
    HEAD → [最近加入] → ... → [最久未访问] → TAIL
```

**预读页的处理流程：**
```
预读页 → 加入 Inactive List 头部
    ↓
若该页再次被访问 → 从 Inactive 升级到 Active List 头部
    ↓
若该页一直未被访问 → 沿 Inactive List 尾部被淘汰
```

**防污染：提高"升级"门槛（访问第 2 次才升级）**

Linux 规定：只有在 Inactive List 中**被访问了第二次**，才能升级到 Active List。一次性扫描的大数据只被访问一次，永远无法升级。

#### MySQL InnoDB 的改进：young/old 区域划分

```
LRU 链表 = young 区域（63%）+ old 区域（37%）（默认比例）

新读入的页 → 加入 old 区域头部
若 old 区域中的页被再次访问，且在 old 区域停留时间 > 1 秒 → 移入 young 区域
```

> 防止：SELECT * 扫描全表时，每页只被访问一次，无法进入 young 区域，不会污染热点缓存。

### 4.6 & 4.7 深入理解 Linux 虚拟/物理内存管理

#### 进程虚拟地址空间的详细划分（64 位 Linux）

```
高地址（0xFFFFFFFFFFFFFFFF）
  ├── 内核空间（128TB）：内核代码、数据、映射所有物理内存
  ├── 空洞（canonical address 保留）
低地址（0x0000000000000000）
  ├── 用户空间（128TB）
  │   ├── 内核映射区（用户不可访问）
  │   ├── 栈（Stack，8MB 默认限制，向下增长）
  │   ├── 内存映射区（mmap，动态库 .so，共享内存）
  │   ├── 堆（Heap，向上增长，malloc 使用）
  │   ├── BSS 段（未初始化的全局/静态变量，初始为 0）
  │   ├── 数据段（已初始化的全局/静态变量）
  │   └── 代码段（Text，只读，程序指令）
```

#### 物理内存管理：NUMA 和 Zone

**NUMA（Non-Uniform Memory Access）**：多处理器系统中，每个 CPU 有自己的本地内存节点（Node），访问本地内存比访问远端节点快。

**Zone（内存区域）**：每个 Node 的内存按用途划分为 Zone：

| Zone | 地址范围（x86_64）| 用途 |
|------|---------------|------|
| `ZONE_DMA` | 0 ~ 16MB | 老式设备的 DMA 传输 |
| `ZONE_DMA32` | 0 ~ 4GB | 32 位 DMA 设备 |
| `ZONE_NORMAL` | 直接映射的内存 | 内核普通用途 |
| `ZONE_HIGHMEM` | 高端内存（32位） | 32 位系统内核无法直接映射的高内存 |

#### 伙伴系统（Buddy System）——页级内存分配

**目标**：管理物理内存页框的分配与释放，减少外部碎片。

**原理**：将空闲页框按 2^n 大小组织（n = 0, 1, 2, ..., 10，即 1, 2, 4, ..., 1024 页）：

```
申请 3 个页 → 找 4 页（2^2）的块，分配后剩余 1 页放回伙伴系统

释放 2 个页 → 查看其"伙伴"（相邻的同大小块）是否也空闲
              → 若空闲，合并为 4 页的块（递归向上合并）
```

#### Slab/Slub 分配器——对象级内存分配

伙伴系统粒度是页（4KB），但内核经常需要分配几十字节的小对象（如 `task_struct`, `inode`）。

**Slab 分配器**：为常用内核数据结构预先分配一批对象（称为一个 "cache"），分配时从 cache 中取，释放时还回 cache，避免频繁调用伙伴系统，也减少内部碎片。

```bash
# 查看 slab 缓存使用情况
cat /proc/slabinfo
# 或
slabtop
```

## 05｜进程管理篇

### 5.1 进程、线程基础知识

#### 进程（Process）——资源分配的基本单位

**进程 = 程序（静态代码）+ 执行状态（动态）**

进程的 **PCB（Process Control Block）**，在 Linux 中是 `task_struct`，包含：
- 进程 ID（PID）
- 进程状态（运行/就绪/阻塞/停止/僵尸）
- CPU 寄存器快照（上下文切换时保存）
- 内存管理信息（页表地址 `mm_struct`）
- 打开的文件描述符表
- 信号处理信息
- 优先级和调度信息

#### 进程的五种状态及转换

```
创建 → [就绪（Ready）] ←──────────────┐
              ↓  调度                  │ 抢占/时间片到
         [运行（Running）]             │
              │                       │
     等待I/O  ↓                      │
         [阻塞（Blocked）]  → I/O完成 → 就绪
              │
     exit()  ↓
         [僵尸（Zombie）] → 父进程 wait() → [消亡（Dead）]
```

**僵尸进程**：子进程已退出（`exit()`），但父进程还没有调用 `wait()` 读取退出状态，PCB 还残留在系统里。大量僵尸进程会耗尽 PID 资源。

#### 线程（Thread）——CPU 调度的基本单位

**线程的本质**：进程内的一条执行流。同一进程的线程**共享**：代码段、数据段、堆、打开的文件描述符、信号处理等；**独享**：栈、寄存器（包括 PC）、线程 ID。

#### 线程 vs 进程对比

| 维度 | 进程 | 线程 |
|------|------|------|
| 资源拥有 | 独立的虚拟地址空间 | 共享进程资源 |
| 调度单位 | 否（线程才是） | **是** |
| 创建销毁开销 | 大（需分配/释放地址空间等）| 小 |
| 切换开销 | 大（需切换页表）| 小（同进程内不换页表）|
| 数据共享 | 需 IPC | 直接共享内存，但需同步 |
| 崩溃影响 | 只影响自身 | **可能导致整个进程崩溃** |

#### 用户线程 vs 内核线程的三种映射模式

| 模式 | 映射关系 | 优点 | 缺点 |
|------|---------|------|------|
| **多对一（M:1）** | 多用户线程 → 1 内核线程 | 切换快（纯用户态）| 一个线程阻塞，整个进程阻塞；无法利用多核 |
| **一对一（1:1）** | 1 用户线程 → 1 内核线程 | 真并行，阻塞互不影响 | 创建线程开销大（1:1 对应内核线程）|
| **多对多（M:N）** | M 用户线程 → N 内核线程 | 综合优点 | 实现复杂 |

> **Linux 采用 1:1 模型**（pthread 创建的线程对应一个 LWP，直接映射到内核线程）

### 5.2 进程间有哪些通信方式？（IPC）

#### 六种 IPC 机制详解

**① 管道（Pipe）**

```c
// 匿名管道：只能用于父子进程
int fd[2];
pipe(fd);   // fd[0] 读端，fd[1] 写端
// fork 后父进程关闭读端，子进程关闭写端（或反过来）
```

特点：
- **半双工**（数据单向流动）
- **字节流**（无消息边界）
- 基于**内核缓冲区**（默认 64KB）
- 内核缓冲区满时，写端阻塞；空时，读端阻塞
- **命名管道（FIFO）**：存在于文件系统，无血缘关系的进程也可以通信

**② 消息队列（Message Queue）**

- 以**消息（有格式的数据块）**为单位传输，有消息边界
- 克服了管道只能传输字节流的缺点
- 内核管理，持久化（进程退出后消息还在，除非显式删除）
- **缺点**：存在内核到用户空间的拷贝，不适合大数据传输

**③ 共享内存（Shared Memory）**

```
进程 A 虚拟空间                    物理内存
   共享内存区域 ──────────────→  同一片物理页  ←──────── 进程 B 的共享内存区域
```

- **最快的 IPC 方式**：数据不需要在用户空间和内核空间之间拷贝，直接访问共享的物理内存
- **缺点**：多进程同时写可能导致数据竞争，需配合信号量使用

**④ 信号量（Semaphore）**

- 本质是一个**计数器**，用于控制多进程对共享资源的访问
- 两个原子操作：
  - **P 操作（Wait）**：sem - 1；如果 sem < 0，进程阻塞
  - **V 操作（Signal）**：sem + 1；如果 sem ≤ 0，唤醒一个等待进程
- 常配合共享内存使用，解决共享内存的竞争问题

**⑤ 信号（Signal）**

- **唯一的异步通信机制**
- 常见信号：
  - `SIGKILL (9)`：强制终止进程（不可被捕获、忽略）
  - `SIGTERM (15)`：请求进程正常退出（可捕获、可忽略）
  - `SIGSEGV (11)`：段错误（非法内存访问）
  - `SIGALRM`：定时器超时
- `kill -9 pid` 等价于发送 SIGKILL

**⑥ Socket**

- 可跨机器通信的 IPC 方式
- 本地通信使用 **Unix Domain Socket**（AF_UNIX），比 TCP socket 开销小

#### 🔧 面试高频：如何选择 IPC 方式？

| 需求 | 推荐方案 |
|------|---------|
| 父子进程简单数据传递 | 匿名管道 |
| 无血缘进程间有格式消息 | 消息队列 |
| 高吞吐大数据共享 | 共享内存 + 信号量 |
| 异步事件通知 | 信号 |
| 网络跨机器通信 | Socket (TCP/UDP) |
| 本地高性能进程间通信 | Unix Domain Socket |

### 5.3 多线程冲突了怎么办？

#### 竞争条件（Race Condition）深度解析

**为什么 i++ 在多线程下不是原子的？**

```asm
; i++ 在 CPU 层面等价于三条指令：
MOV EAX, [i]   ; 从内存读 i 到寄存器
ADD EAX, 1     ; 寄存器加 1
MOV [i], EAX   ; 写回内存

; 如果两个线程同时执行，时钟中断可以发生在任意两条指令之间！
```

**临界区（Critical Section）**：访问共享资源的代码片段，需要保证互斥访问。

#### 互斥锁的两种实现

**① 自旋锁（Spin Lock）——忙等待锁**

```c
// 基于 Test-And-Set 原子指令实现
void lock(spinlock_t *lock) {
    while (TestAndSet(&lock->flag, 1) == 1)
        ;  // 忙等：一直空转，直到获取锁
}
```

适用场景：**锁持有时间极短**的场景（如内核中断处理），因为自旋期间 CPU 不会切换，适合多核 CPU。

**② 互斥锁（Mutex）——无等待锁（sleeping lock）**

```
获取锁失败 → 将当前线程放入等待队列 → 让出 CPU（进入睡眠状态）
锁释放时 → 唤醒等待队列中的线程
```

适用场景：**锁持有时间较长**的场景，避免忙等浪费 CPU。

#### 自旋锁 vs 互斥锁对比

| | 自旋锁 | 互斥锁 |
|---|---|---|
| 等待方式 | 忙等（占用 CPU）| 睡眠（让出 CPU）|
| 上下文切换 | 无 | 有（开销大）|
| 适合锁持有时间 | 极短（微秒级）| 较长 |
| 适合场景 | 多核 CPU 内核驱动 | 用户态应用程序 |
| 单核 CPU | **危险**（会死锁） | 正常 |

#### 信号量（Semaphore）实现互斥和同步

**互斥（初始值为 1 的二元信号量）：**
```
mutex = 1
进入临界区前：P(mutex) → mutex - 1 = 0
离开临界区后：V(mutex) → mutex + 1 = 1
```

**同步（初始值为 0 的计数信号量）：**
```python
# 生产者-消费者问题需要 3 个信号量：
mutex = Semaphore(1)          # 互斥访问缓冲区
fullBuffers = Semaphore(0)    # 缓冲区中已有数据的槽位数
emptyBuffers = Semaphore(N)   # 缓冲区中空槽位数（N = 缓冲区大小）

# 生产者：
P(emptyBuffers)    # 等待有空槽
P(mutex)           # 加锁
放入数据
V(mutex)           # 解锁
V(fullBuffers)     # 通知消费者有数据了

# 消费者：
P(fullBuffers)     # 等待有数据
P(mutex)           # 加锁
取出数据
V(mutex)           # 解锁
V(emptyBuffers)    # 通知生产者有空槽了
```

#### 经典同步问题

**哲学家就餐问题**（5个哲学家，5把叉子，每人需要左右两把叉子才能吃饭）：
- **方案1（会死锁）**：所有人同时拿左叉 → 全部等待右叉 → 死锁
- **方案2（效率低）**：全局互斥锁 → 同时只有1人能吃
- **方案3（最优）**：奇数号哲学家先拿左叉，偶数号先拿右叉 → 打破环路等待，允许2人同时进餐
- **方案4**：用状态数组 `state[]` 记录每位哲学家的状态（思考/饥饿/进餐），只有两邻都不在进餐时才允许进餐

### 5.4 怎么避免死锁？

#### 死锁的四个必要条件（全部满足才会死锁）

| 条件 | 说明 | 破坏方法 |
|------|------|---------|
| **互斥（Mutual Exclusion）** | 资源一次只能由一个进程占用 | 将资源设计为可共享（通常无法破坏）|
| **持有并等待（Hold and Wait）** | 持有部分资源的进程，还在等待其他资源 | **一次性申请所有资源**；或申请新资源前先释放已有资源 |
| **不可剥夺（No Preemption）** | 进程不能被强制剥夺已持有的资源 | 允许抢占（操作系统强制剥夺）|
| **环路等待（Circular Wait）** | 多个进程形成资源等待环 | **对资源编号，按升序申请锁**（打破环路）|

#### 实际中最常用的死锁预防策略

**① 按固定顺序获取锁（破坏环路等待）**

```python
# ❌ 可能死锁：线程A先锁A再锁B，线程B先锁B再锁A
# ✅ 固定顺序：所有线程都按 lock_A → lock_B 的顺序获取
with lock_A:
    with lock_B:
        ...
```

**② 超时 + 重试（死锁检测后恢复）**

```python
# 尝试获取锁，超时则放弃所有锁，随机等待后重试
if not lock.acquire(timeout=1.0):
    # 放弃已持有的锁，避免死锁
    all_locks.release()
    time.sleep(random.random())
```

**③ 银行家算法（死锁避免）**

操作系统在分配资源前，先模拟"如果分配这些资源，系统是否仍处于安全状态"，如果不安全则拒绝分配。

### 5.5 什么是悲观锁、乐观锁？

#### 核心区别

| | 悲观锁（Pessimistic Lock） | 乐观锁（Optimistic Lock）|
|---|---|---|
| 假设 | 并发冲突频繁 | 并发冲突很少 |
| 方式 | 访问前先加锁，阻塞其他线程 | 不加锁，提交时检查是否有冲突 |
| 实现 | 互斥锁、读写锁 | CAS、版本号、时间戳 |
| 适合 | **写多读少**（写冲突频繁）| **读多写少**（冲突很少）|
| 问题 | 线程挂起/唤醒开销，可能死锁 | 写冲突时需重试（ABA 问题）|

#### 乐观锁：CAS（Compare And Swap）

```c
// 原子操作：
// 如果 *addr == old_val，则将 *addr 更新为 new_val，返回 true
// 否则不更新，返回 false
bool CAS(int *addr, int old_val, int new_val) {
    if (*addr == old_val) {
        *addr = new_val;
        return true;
    }
    return false;
}

// 使用 CAS 实现无锁自增
do {
    old = counter;
    new = old + 1;
} while (!CAS(&counter, old, new));  // 如果被别人改了，重试
```

#### ⚠️ ABA 问题

```
线程 A 读到值为 A
线程 B 把值改为 B，再改回 A
线程 A 的 CAS 检查值还是 A，认为没有冲突 → 错误！
```

**解决方案**：给值加上**版本号**（如 Java 的 `AtomicStampedReference`），CAS 同时检查值和版本号。

#### 读写锁（Read-Write Lock）

```
读锁（共享锁）：多个读操作可以并发持有
写锁（排他锁）：写操作独占，与任何读锁/写锁互斥
```

适用场景：**读多写少**（如配置文件读取、缓存查询）。

### 5.6 一个进程最多可以创建多少个线程？

#### 影响因素分析

**主要限制：线程的栈空间**

每个线程需要独立的栈空间（默认 8MB，通过 `ulimit -s` 查看）：

```
32 位系统：
- 用户虚拟空间 = 3GB（0 ~ 3GB，内核占 1GB）
- 最大线程数 ≈ 3GB / 8MB = 384 个（理论值，实际更少）

64 位系统：
- 用户虚拟空间 = 128TB
- 理论上 128TB / 8MB = 1600 万个线程
- 实际受 /proc/sys/kernel/threads-max 限制（通常几万）
```

#### 🔧 查看和修改线程限制

```bash
# 查看系统最大线程数
cat /proc/sys/kernel/threads-max

# 查看当前进程可创建的最大线程（受虚拟内存限制）
ulimit -s              # 查看线程栈大小（KB）
ulimit -s 1024         # 缩小栈到 1MB，可创建更多线程

# 临时修改系统线程上限
echo 100000 > /proc/sys/kernel/threads-max
```

### 5.7 线程崩溃了，进程也会崩溃吗？

#### 答案：**通常会**（C/C++ 语言），**不一定**（Java 语言）

**C/C++ 中线程崩溃的机制：**

```
线程发生段错误（SIGSEGV）
   ↓
硬件（内存管理单元 MMU）检测到非法内存访问
   ↓
CPU 产生异常，内核将该异常转换为 SIGSEGV 信号
   ↓
信号发送给「进程」（不是某个线程）
   ↓
如果进程没有注册 SIGSEGV 处理函数，执行默认动作：终止进程 + 生成 Core Dump
   ↓
整个进程崩溃（包括所有线程）
```

**Java 中线程崩溃的机制：**

- Java 运行在 JVM 之上，JVM 捕获了底层信号
- Java 线程抛出异常（如 NullPointerException）后，如果没有 `try-catch` 捕获，线程终止
- 但 JVM 不会传播信号给整个进程，其他线程不受影响
- **除非**是 JVM 自身 bug 或 `System.exit()` 被调用

#### ⚠️ 面试陷阱

**Q：线程崩溃一定会导致进程崩溃吗？**

A：不一定。
1. 如果崩溃是由未捕获信号（如 SIGSEGV）导致，且进程没注册信号处理函数 → 整个进程崩溃
2. 如果程序注册了信号处理函数（`sigaction`）来处理 SIGSEGV → 可以不崩溃
3. Java 程序：JVM 处理了异常，其他线程继续运行

## 06｜调度算法篇

### 6.1 进程调度算法

#### 调度的五大原则（目标）

| 原则 | 指标 | 优化方向 |
|------|------|---------|
| CPU 利用率 | CPU 忙碌时间占比 | 越高越好 |
| 吞吐量 | 单位时间完成的进程数 | 越高越好 |
| 周转时间 | 进程从提交到完成的总时间 | 越短越好 |
| 等待时间 | 进程在就绪队列中等待的时间 | 越短越好 |
| 响应时间 | 提交请求到第一次响应的时间 | 越短越好（交互式系统关键指标）|

#### 六种调度算法详解

**① 先来先服务（FCFS，First Come First Serve）**

- **非抢占式**：一个进程运行直到完成或阻塞才切换
- 优点：简单公平
- 缺点：**护航效应（Convoy Effect）**：大量短作业等待一个长作业，平均等待时间长
- 适合：**CPU 密集型**，不适合 I/O 密集型

**② 最短作业优先（SJF，Shortest Job First）**

- 优先运行预计执行时间最短的进程
- 优点：最优平均等待时间（数学可证明）
- 缺点：长作业可能**永远得不到执行（饥饿）**；且实际上无法提前知道执行时间

**③ 高响应比优先（HRRN，Highest Response Ratio Next）**

$$响应比 = \frac{等待时间 + 服务时间}{服务时间} = 1 + \frac{等待时间}{服务时间}$$

- 每次调度时选响应比最高的进程
- 等待时间越长，响应比越高 → 防止长作业饥饿
- 短作业响应比天然高 → 短作业优先
- 缺点：理想算法，实际无法知道进程的服务时间

**④ 时间片轮转（RR，Round Robin）**

```
就绪队列：[P1] → [P2] → [P3] → [P1] → ...
每个进程运行一个时间片（如 20ms），时间片到期则强制切换

时间片大小的取舍：
- 过小 → 频繁上下文切换，CPU 效率降低
- 过大 → 退化为 FCFS，响应时间长
- 通常 20ms ~ 50ms 是合理范围
```

**⑤ 最高优先级（HPF，Highest Priority First）**

- 静态优先级：创建时固定，整个生命周期不变
- 动态优先级：随运行时间增加降低优先级，等待时间越长优先级越高
- 缺点：低优先级进程可能**永远饥饿**

**⑥ 多级反馈队列（MFQ，Multilevel Feedback Queue）——Linux 实际使用**

```
第1队列（优先级最高，时间片最短，如 2ms）
第2队列（优先级次高，时间片稍长，如 4ms）
第3队列（优先级最低，时间片最长，如 16ms）

规则：
1. 新进程进入第1队列，按时间片轮转
2. 时间片用完未结束 → 降级到下一个队列的末尾
3. 如果在低优先级队列等待时间过长 → 升级到高优先级队列（老化机制，防饥饿）
4. 有高优先级进程就绪 → 抢占当前运行的低优先级进程
```

**效果**：短作业在第1队列就能快速完成；长作业逐步降级但最终也能运行，兼顾响应时间和公平性。

### 6.2 页面置换算法

当物理内存不足时，需要把内存中的页换到磁盘（Swap），选择哪个页被换出是**页面置换**的问题。

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **OPT（最佳）** | 替换未来最长时间不会使用的页 | 最优（缺页次数最少）| **无法实现**（需要预知未来）|
| **FIFO** | 替换进入内存最早的页 | 简单 | **Belady 异常**：增加物理帧反而缺页更多 |
| **LRU（最近最少使用）** | 替换最长时间未被访问的页 | 性能接近 OPT | 实现开销大（需维护访问时间戳或链表）|
| **Clock（时钟算法）** | 近似 LRU，用访问位 bit 替代时间戳 | 低开销，实用 | 是 LRU 的近似，不精确 |

**LRU 的精确实现**：双向链表 + 哈希表（O(1) 访问和删除），即 LeetCode 146 题。

### 6.3 磁盘调度算法

寻道时间是磁盘 I/O 最主要的延迟，磁盘调度算法的目标是减少总寻道距离。

| 算法 | 策略 | 问题 |
|------|------|------|
| **FCFS** | 按请求顺序服务 | 磁头可能反复横跳，效率低 |
| **SSTF（最短寻道时间优先）** | 服务距当前磁头最近的请求 | 中间轨道请求可能饥饿 |
| **SCAN（电梯算法）** | 磁头向一个方向扫描到底，再反向扫描 | 两端轨道等待时间不均匀 |
| **C-SCAN（循环扫描）** | 只单向扫描，到底后跳回起点重新扫 | 所有请求等待时间更均匀 |

## 07｜文件系统篇

### 7.1 文件系统全家桶

#### "一切皆文件" ——Linux 的设计哲学

Linux 中，普通文件、目录、设备（`/dev/sda`）、管道（`pipe`）、套接字（`socket`）都被统一抽象为**文件**，通过统一的文件接口（`open/read/write/close`）操作。

#### 核心数据结构：inode 和 dentry

**inode（索引节点）——文件的"身份证"**

```c
// Linux inode 包含（不包含文件名！）：
struct inode {
    unsigned long   i_ino;        // inode 编号（唯一标识）
    umode_t         i_mode;       // 文件类型和权限
    loff_t          i_size;       // 文件大小（字节）
    struct timespec i_atime;      // 最后访问时间
    struct timespec i_mtime;      // 最后修改时间
    struct timespec i_ctime;      // inode 最后修改时间
    unsigned int    i_nlink;      // 硬链接数
    // ... 数据块指针（存储文件实际内容的磁盘块位置）
};
```

**dentry（目录项）——文件的"名牌"**

- 记录文件名到 inode 的映射关系
- **存在于内存**（内核维护的缓存），不在磁盘上（这是与 inode 的关键区别）
- 目录树结构由 dentry 链接起来
- 路径解析（如 `/home/user/file.txt`）就是逐级查找 dentry 的过程

#### ⚠️ inode vs dentry 区别

| | inode | dentry |
|---|---|---|
| 存储位置 | **磁盘** + 内存缓存 | **仅内存** |
| 包含信息 | 文件元数据 + 数据块位置 | 文件名 + inode 号 |
| 与文件的关系 | 一个文件**只有一个** inode | 一个文件可有**多个** dentry（硬链接）|

#### 文件系统基本单位

```
磁盘物理结构：扇区（512B）
文件系统逻辑块（Block）：通常 4KB = 8个扇区
    └── 读写最小单位，一次 I/O 操作至少读写 1 个块
```

#### 文件存储方式

**连续分配（Contiguous Allocation）**：
- 文件占用连续的磁盘块
- 优点：顺序读取极快；随机访问快（直接计算偏移）
- 缺点：外部碎片；文件大小难以动态扩展

**非连续分配——链式（Linked Allocation）**：
- 每个数据块末尾存储下一块的指针（隐式链表）
- 或将所有块的指针集中存储在内存中（FAT，显式链表）
- 优点：无外部碎片，文件可动态增长
- 缺点：随机访问需要顺序遍历

**非连续分配——索引（Indexed Allocation）**：
- 每个文件有一个**索引块**，存储所有数据块的地址
- **Unix/Linux EXT 文件系统**的实现（inode 中包含块指针）：
  - 12 个**直接块指针**（直接指向数据块，适合小文件）
  - 1 个**一级间接指针**（指向一个包含块地址的块）
  - 1 个**二级间接指针**
  - 1 个**三级间接指针**（支持超大文件）

#### 硬链接 vs 软链接

| | 硬链接（Hard Link） | 软链接（Symbolic Link）|
|---|---|---|
| 本质 | 新建一个指向**同一 inode** 的 dentry | 新建一个**独立的文件**，内容是目标路径字符串 |
| inode | 共用同一个 | 有自己独立的 inode |
| 跨文件系统 | ❌ 不支持 | ✅ 支持 |
| 目标删除后 | 仍可访问（inode 引用计数 > 0）| 变成死链接（dangling symlink）|
| 类比 | 同一个人的两个名字 | 一张写着地址的纸条 |

#### VFS（Virtual File System）

VFS 是 Linux 内核的文件系统抽象层，为所有文件系统（EXT4、XFS、FAT32、NTFS）提供**统一接口**：

```
用户程序
   ↓ open/read/write/close（POSIX 接口）
虚拟文件系统（VFS）
   ↓ 根据文件系统类型分发
  ├── EXT4 文件系统驱动
  ├── XFS 文件系统驱动
  └── proc、sysfs、tmpfs（伪文件系统）
   ↓
块设备层 → 具体磁盘设备
```

#### 文件 I/O 的四种维度

**维度1：缓冲 vs 非缓冲 I/O**

| | 缓冲 I/O | 非缓冲 I/O |
|---|---|---|
| 接口 | C 标准库（`fread/fwrite`）| 系统调用（`read/write`）|
| 缓冲层 | 用户态标准库缓冲区 | 无用户态缓冲 |
| 减少系统调用 | ✅ 批量传输 | ❌ 每次都是系统调用 |

**维度2：直接 vs 非直接 I/O**

| | 直接 I/O（`O_DIRECT`）| 非直接 I/O（默认）|
|---|---|---|
| Page Cache | 绕过，直接读写磁盘 | 使用 Page Cache |
| 适合 | 数据库（自管缓存）| 通用文件访问 |

**维度3：阻塞 vs 非阻塞 I/O**

```
阻塞 I/O：调用 read()，线程阻塞直到数据可用
非阻塞 I/O：调用 read()，如果数据未就绪立即返回 EAGAIN
```

**维度4：同步 vs 异步 I/O**

```
同步 I/O：应用程序等待 I/O 操作完成（包括数据拷贝到用户空间）
异步 I/O（AIO）：发起 I/O 请求后立即返回，I/O 完成后内核通知应用程序
```

### 7.2 进程写文件时崩溃，数据会丢失吗？

#### Page Cache 的工作原理

```
write(fd, buf, len)
    ↓
系统调用进入内核
    ↓
数据拷贝到 Page Cache（内核缓冲区）—— 立即返回
    ↓
（异步）脏页由 pdflush/writeback 线程定期刷回磁盘
```

> `write()` 成功返回时，数据**在 Page Cache 里，不在磁盘上**！

#### 进程崩溃 vs 系统崩溃

| 崩溃场景 | Page Cache 状态 | 数据是否丢失 |
|---------|---------------|------------|
| **进程崩溃（系统正常）** | Page Cache 由内核维护，进程退出不影响 | **不丢失**，内核会完成后续刷盘 |
| **系统崩溃 / 断电** | Page Cache 在内存中，掉电全丢 | **丢失**（未刷盘的 dirty page 全部消失）|

#### 如何保证数据持久化？

```c
// 方案1：fsync（刷新特定文件的所有脏页到磁盘）
int fd = open("file.txt", O_WRONLY);
write(fd, data, len);
fsync(fd);       // 阻塞直到数据真正写到磁盘

// 方案2：fdatasync（只刷数据，不刷元数据，比 fsync 快一点）
fdatasync(fd);

// 方案3：O_SYNC（打开文件时设置，每次 write 都强制同步到磁盘）
int fd = open("file.txt", O_WRONLY | O_SYNC);
```

## 08｜设备管理篇

### 8.1 键盘敲入 A 字母时，操作系统期间发生了什么？

#### 完整流程（硬件 → 内核 → 用户程序）

```
1. 物理层：用户按下 A 键
   └── 键盘控制器（8042/USB 控制器）检测到按键
   └── 产生扫描码（Scan Code），如 0x1E（A 键按下）

2. 中断触发：键盘控制器向中断控制器（PIC/APIC）发送 IRQ1 信号
   └── 中断控制器向 CPU 发送 INTR 信号
   └── CPU 在当前指令执行完毕后，检查中断标志

3. 硬中断处理（上半部，极短）：
   └── CPU 保存现场（压栈当前寄存器）
   └── 跳转到键盘中断处理程序（ISR）
   └── ISR 从键盘控制器读取扫描码（一个 I/O 端口读操作）
   └── 将扫描码放入键盘缓冲区（ring buffer）
   └── 标记软中断（键盘输入软中断 TASKLET）
   └── 恢复现场，返回被中断的进程

4. 软中断处理（下半部，稍慢）：
   └── 扫描码转换为键盘码（Key Code，与布局无关）
   └── 键盘码 + 当前修饰键状态（Shift/Ctrl 等）→ 字符 'A'
   └── 字符放入 tty（终端）设备的输入缓冲区

5. 用户程序读取：
   └── Shell（bash）执行 read() 系统调用，从 tty 读取字符
   └── Shell 收到 'A'，做**回显（echo）**，调用 write() 输出 'A' 到终端
   └── 用户看到屏幕上出现字母 A
```

#### 为什么要分"上半部"和"下半部"？

- **上半部（Top Half）**：中断处理程序，必须极快完成（通常微秒级），不能睡眠，只做最紧急的事（读取硬件数据）
- **下半部（Bottom Half）**：延迟处理，在稍后的安全上下文中执行耗时任务（字符转换、协议处理等）

### 9.1 什么是零拷贝？

#### 传统文件传输的问题（以发送文件到网络为例）

```
应用程序调用 read(file) + write(socket)，数据流向：

磁盘                                         网络
 ↓ DMA 拷贝（无 CPU 参与）
内核 Page Cache（内核缓冲区）
 ↓ CPU 拷贝（有 CPU 参与）
用户态应用程序缓冲区
 ↓ CPU 拷贝（有 CPU 参与）
内核 Socket 缓冲区（sk_buffer）
 ↓ DMA 拷贝（无 CPU 参与）
                                             网卡发送
```

**总结：4次上下文切换 + 2次 CPU 拷贝 + 2次 DMA 拷贝**

#### mmap + write（减少 1 次 CPU 拷贝）

```c
buf = mmap(file, len);   // 将 Page Cache 映射到用户地址空间（不拷贝）
write(socket, buf, len); // 从用户态写到 Socket 缓冲区（1次 CPU 拷贝）
```

**总结：4次上下文切换 + 1次 CPU 拷贝 + 2次 DMA 拷贝**

#### sendfile（Linux 2.1+，真正的零拷贝）

```c
sendfile(socket_fd, file_fd, NULL, len);
// 直接在内核空间将 Page Cache 数据送到 Socket 缓冲区
// 完全不经过用户态
```

**不支持 SG-DMA 时（Linux 2.1+）：**  
2次上下文切换 + 1次 CPU 拷贝 + 2次 DMA 拷贝

**支持 SG-DMA 时（Linux 2.4+，网卡支持 scatter-gather）：**

```
Page Cache ──→ SG-DMA 直接读取到网卡（无需拷贝到 Socket 缓冲区）
              只需传递 Page Cache 数据的描述符（地址+长度）给网卡
```

**2次上下文切换 + 0次 CPU 拷贝 + 2次 DMA 拷贝** → **真正的零 CPU 拷贝！**

#### 零拷贝的实际应用

| 场景 | 技术 |
|------|------|
| Nginx 静态文件服务 | `sendfile on` 配置项 |
| Kafka 消息传输 | Java `FileChannel.transferTo()` 底层使用 sendfile |
| 大文件下载服务器 | mmap + sendfile |

### 9.2 I/O 多路复用：select/poll/epoll

#### 问题背景：如何高效处理多个 Socket 连接？

**最朴素的方案：每个连接一个线程**
- 10000 个连接 = 10000 个线程 → 内存爆炸、上下文切换开销极大

**I/O 多路复用**：用**一个线程**监视**多个文件描述符（Socket）**，当某个 Socket 有事件就绪（可读/可写），才通知应用程序处理。

#### select 的原理与缺点

```c
// select 的使用方式
fd_set read_fds;
FD_ZERO(&read_fds);
FD_SET(fd1, &read_fds);
FD_SET(fd2, &read_fds);
select(max_fd + 1, &read_fds, NULL, NULL, NULL);
// 返回后，遍历所有 fd 检查是否在 read_fds 中
```

**缺点：**
1. **每次调用**都要将整个 fd_set 从**用户空间拷贝到内核空间**（开销随 fd 数量线性增长）
2. **内核必须线性遍历所有 fd** 检查是否就绪，时间复杂度 O(N)
3. 最多监视 **1024 个 fd**（`FD_SETSIZE` 限制）
4. 返回后用户程序还需**再次线性遍历**找到就绪的 fd

#### poll 的改进（解决了 1024 限制，但其余问题未解决）

```c
struct pollfd fds[N];
// 可以设置更多 fd（突破 1024 限制）
// 但仍然需要每次全量拷贝和线性遍历
poll(fds, N, timeout);
```

#### epoll 的革命性改进

```c
// 三个系统调用：
int epfd = epoll_create(1);              // 创建 epoll 实例
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &ev); // 注册要监视的 fd（只调用一次）
int n = epoll_wait(epfd, events, MAX, -1); // 等待就绪事件
// 返回的 events[] 里就是就绪的 fd，不需要遍历所有 fd
```

**epoll 的三大核心改进：**

| 改进点 | 实现方式 | 效果 |
|--------|---------|------|
| **不需要每次全量拷贝 fd** | 内核用**红黑树**持久维护监视的 fd 集合 | 只需在 `epoll_ctl` 时拷贝一次 |
| **O(1) 就绪通知** | 用**就绪链表（rdllist）**保存已就绪的 fd | 返回时直接返回就绪的 fd 列表 |
| **无 fd 数量上限** | 红黑树天然无限制 | 可监视数十万 Socket |

#### 水平触发（LT）vs 边缘触发（ET）

| | 水平触发（Level Trigger，LT）| 边缘触发（Edge Trigger，ET）|
|---|---|---|
| 触发条件 | 只要缓冲区有数据，**每次 epoll_wait 都通知** | 只在状态**变化时**通知一次（从无数据变有数据）|
| 读取方式 | 可以分多次读取 | **必须一次性读完所有数据**（否则下次不通知）|
| 性能 | 较低（可能重复通知）| 较高（减少唤醒次数）|
| 编程复杂度 | 低（默认模式）| 高（需配合非阻塞 I/O 循环读取）|

#### 🔧 实际选择

- **简单场景**：select/poll（fd 数量少）
- **高并发服务器**：**epoll + ET + 非阻塞 I/O**（如 Nginx, Redis）
- 使用 ET 模式时，`fd` 必须设置为非阻塞（`O_NONBLOCK`），否则最后一次 `read()` 可能永久阻塞

### 9.3 高性能网络模式：Reactor 和 Proactor

#### Reactor 模式（反应器，同步非阻塞 I/O）

**核心思想**："来了事件操作系统通知你，你来做 I/O"

```
                 ┌─────────────────────────────┐
                 │          Reactor              │
事件源           │   ┌──────────────────────┐   │
Socket ─ 连接事件→│   │    epoll_wait()        │   │
Socket ─ 可读事件→│   │（等待事件就绪）        │   │
Socket ─ 可写事件→│   └──────────┬───────────┘   │
                 │              │ 事件就绪        │
                 │              ↓               │
                 │   ┌──────────────────────┐   │
                 │   │    Dispatcher         │   │
                 │   │（分发给对应 Handler）  │   │
                 │   └──────────────────────┘   │
                 └─────────────────────────────┘
                          ↓            ↓
                    Handler A     Handler B
                   （read + 处理）（write 结果）
```

**三种 Reactor 实现方案：**

**① 单 Reactor 单线程**（Redis 6.0 之前）
```
Reactor ─── 负责所有事情（accept + read + 业务处理 + write）
缺点：单线程无法利用多核 CPU；业务处理耗时影响 I/O 响应
```

**② 单 Reactor 多线程**
```
Reactor ─── accept + read → 分发给线程池处理 → 线程池处理业务 + write
优点：利用多核 CPU
缺点：Reactor 仍是单点，高并发下成为瓶颈
```

**③ 主从 Reactor 多线程**（Nginx, Netty 采用）
```
Main Reactor ─── 只负责 accept 新连接
    ↓ 将新连接分发给
Sub Reactor（多个）─── 负责已连接的 Socket 的 I/O 事件（read/write）
    ↓
线程池 ─── 负责业务逻辑处理
```

#### Proactor 模式（前摄器，异步 I/O）

**核心思想**："我告诉你我要什么，等操作系统做完了你通知我"

```
应用程序发起异步 I/O 请求（aio_read/aio_write）
    ↓
操作系统在后台完成 I/O 并将数据拷贝到应用程序缓冲区
    ↓
I/O 完成后，操作系统通知应用程序（回调 / 信号 / 完成端口）
    ↓
应用程序直接处理数据（数据已在用户缓冲区）
```

| | Reactor | Proactor |
|---|---|---|
| I/O 模型 | 同步非阻塞 I/O | 异步 I/O（AIO）|
| I/O 操作由谁做 | **应用程序**（得到通知后自己 read/write）| **操作系统**（完成后通知应用）|
| 核心通知时机 | fd 就绪（可以读/写了）| I/O 操作完成（数据已在缓冲区）|
| Linux 实现 | epoll | io_uring（新）/ libaio |

> Linux 上异步 I/O（aio）对磁盘 I/O 支持不完善，所以**主流 Linux 高性能服务器基本都用 Reactor 模式**。Windows 的 IOCP 是 Proactor 的经典实现。

### 9.4 什么是一致性哈希？

#### 普通哈希的问题

```python
node = hash(key) % N   # N = 节点数量
```

**问题**：当节点增加或减少时，N 变化，几乎所有 key 都要重新映射 → 缓存大规模失效（雪崩）。

#### 一致性哈希（Consistent Hashing）

**哈希环**：将哈希值空间组织成一个 [0, 2³²-1] 的环：

```
        0
    /       \
  3/4环    1/4环
    \       /
        1/2环

节点 A、B、C 分布在环上
查找 key 时：顺时针找第一个节点 → 该 key 归属于这个节点
```

**节点增减时的影响**：
- 增加节点 D：只有 D 和其前一个节点之间的 key 需要迁移（迁移范围是 1/N）
- 删除节点 A：A 负责的 key 迁移到顺时针下一个节点（也是 1/N 范围）

> 普通哈希增减节点需要迁移 O(N) 的 key，一致性哈希只需迁移 O(1/N) 的 key

#### 虚拟节点——解决数据倾斜

**问题**：三个真实节点可能在哈希环上分布不均，导致负载不均衡。

**解决方案**：每个真实节点对应多个**虚拟节点**：
- 节点 A → 虚拟节点 A-1, A-2, A-3, ..., A-100
- 虚拟节点均匀分布在哈希环上
- key 映射到虚拟节点后，再映射到对应的真实节点

### 10.1 如何查看网络的性能指标？

```bash
# 1. 查看网卡带宽使用和错误
ifconfig eth0
ip -s link show eth0
# 关注：RX/TX bytes（收发字节数），errors（错误数），dropped（丢包数）

# 2. 查看网络实时吞吐
sar -n DEV 1 5           # 每1秒采样一次，共5次
# 关键列：rxkB/s（接收KB/s），txkB/s（发送KB/s）

# 3. 查看 TCP 连接状态统计
netstat -s | grep -i tcp
ss -s                    # 统计各状态连接数

# 4. 查看当前所有连接
ss -ant                  # 显示所有 TCP 连接状态
netstat -ant

# 5. 查看网络延迟
ping -c 10 target_ip     # 平均 RTT
traceroute target_ip     # 路由路径和每跳延迟

# 6. TCP 连接队列情况（排查握手丢包）
ss -lnt                  # 查看监听中的 TCP Socket，Recv-Q / Send-Q
# Recv-Q：全连接队列当前长度；Send-Q：全连接队列最大长度
```

#### 关键指标的解读

| 指标 | 正常范围 | 告警含义 |
|------|---------|---------|
| 丢包率（Packet Loss）| < 0.1% | 网络拥塞、硬件故障 |
| RTT（往返延迟）| 取决于网络距离 | 突增可能是拥塞或路由问题 |
| TIME_WAIT 数量 | 数千~数万 | 过多表示短连接过频繁 |
| CLOSE_WAIT 数量 | 接近 0 | 偏高表示程序有 Socket 未正确关闭 |

### 10.2 如何从日志分析 PV、UV？

假设 Nginx 访问日志格式（`access.log`）：
```
192.168.1.1 - - [01/Jan/2024:00:00:01 +0800] "GET /index.html HTTP/1.1" 200 1234
```

```bash
# 统计 PV（Page View，总请求数）
wc -l access.log

# 统计今日 PV（过滤特定日期）
grep "01/Jan/2024" access.log | wc -l

# 统计 UV（Unique Visitor，独立 IP 数）
awk '{print $1}' access.log | sort | uniq | wc -l

# 统计 UV（更高效的方式）
awk '{print $1}' access.log | sort -u | wc -l

# 找出访问最多的 Top 10 IP
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10

# 找出访问最多的 Top 10 URL
awk '{print $7}' access.log | sort | uniq -c | sort -rn | head -10

# 统计某个接口的 4xx/5xx 错误率
awk '$9 >= 400 {count++} END {print count}' access.log
```

### 进程与线程

| 问题 | 核心答案 |
|------|---------|
| 进程和线程的本质区别？| 进程是资源分配单位；线程是 CPU 调度单位 |
| 线程切换比进程切换快在哪？| 同进程线程不需要切换页表 |

| 线程崩溃进程一定崩溃吗？| C/C++ 通常会（SIGSEGV 信号发给整个进程）；Java 不一定 |

### 网络系统

| 问题 | 核心答案 |
|------|---------|
| sendfile 为什么是零拷贝？| 借助 SG-DMA，Page Cache 数据的描述符直接给网卡，CPU 不参与拷贝 |

| ET 和 LT 的区别？| ET 只在状态变化时通知一次（高效）；LT 只要有数据就一直通知（安全）|
| Reactor 和 Proactor 区别？| Reactor 是"通知你可以读了"（同步非阻塞）；Proactor 是"我帮你读完了"（异步）|
