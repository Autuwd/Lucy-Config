## 1. TCP vs UDP 对比（必考第1题）

### 核心对比表（必背）

| 特性 | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接（需三次握手） | 无连接（直接发） |
| 可靠性 | 可靠（确认+重传） | 不可靠（尽最大努力） |
| 顺序 | 保证数据顺序 | 不保证顺序 |
| 速度 | 较慢 | 快 |
| 头部大小 | 20-60 字节 | 8 字节 |
| 流量控制 | 有（滑动窗口） | 无 |
| 拥塞控制 | 有（慢启动/快重传） | 无 |
| 传输方式 | 字节流（无边界） | 数据报（有边界） |
| 适用场景 | 文件传输、网页、登录 | 音视频、游戏实时同步 |

### 核心原则（一句话记住）

```
数据不能丢 → TCP（登录、匹配、充值）
数据不能卡 → UDP（技能、位置、移动）
```

### 类比记忆

```
TCP = 打电话 📞
  - 先拨号（三次握手）建立连接
  - 说话有顺序，对方听不到会重说（确认重传）
  - 挂电话才断开（四次挥手）

UDP = 寄信 / 发短信 ✉️
  - 直接写地址就寄出去，不用先"连接"
  - 丢了就丢了，对方不一定收得到
  - 快，但不保证顺序和到达
```

### 游戏开发怎么选？

| 游戏功能 | 你怕什么 | 选什么 | 原因 |
|---------|---------|--------|------|
| 登录/注册 | 怕登录失败（数据丢了） | **TCP** | 需要可靠，不能丢 |
| 匹配结果 | 怕没收到通知 | **TCP** | 需要可靠 |
| 释放技能 | 怕按了没反应（卡了） | **UDP** | 延迟比可靠性重要 |
| 角色移动 | 怕瞬移/卡顿 | **UDP** | 位置每秒更新多次，丢了下次更新就行 |
| 买装备/商城 | 怕扣钱没到账 | **TCP** | 必须确保成功 |
| 排行榜 | 怕数据不完整 | **TCP** | HTTP GET 请求 |
| 实时语音 | 怕延迟 | **UDP** | 延迟敏感，偶尔丢帧无所谓 |
| FPS/MOBA 对战 | 怕团战卡住 | **UDP** | 核心玩法用 UDP |

### 面试口述模板

> **"TCP 和 UDP 的核心区别有三点：**
> 1. TCP 是面向连接的，需要三次握手建立连接；UDP 是无连接的，直接发数据
> 2. TCP 可靠，有确认重传机制；UDP 不可靠，丢了就丢了
> 3. TCP 慢但稳，UDP 快但可能丢
>
> **游戏里怎么选？** 登录、匹配、商城这类需要可靠性的用 TCP；FPS、MOBA 这类实时对战用 UDP，因为延迟比可靠性更重要。实际项目中常常两者混合使用，重要消息走 TCP，高频位置同步走 UDP。"

## 2. TCP 三次握手（必考第2题）

### 过程图（必背）

```
    客户端                              服务端
      │                                   │
      │ ① SYN (seq=x)    "敲门"           │  → 客户端进入 SYN_SENT
      │ ────────────────────────────────→ │
      │                                   │
      │ ② SYN+ACK (seq=y, ack=x+1) "开门"│  → 服务端进入 SYN_RCVD
      │ ←──────────────────────────────── │
      │                                   │
      │ ③ ACK (seq=x+1, ack=y+1) "进门"  │  → 双方进入 ESTABLISHED
      │ ────────────────────────────────→ │
      │                                   │
      │         连接建立，可以传数据        │
```

### 敲门类比（面试时这样讲）

```
你敲门：    "有人吗？"          =  SYN    （发起连接请求）
朋友开门：  "有人！你是谁？"     =  SYN+ACK（确认收到+反问）
你进门：    "我是小明！"        =  ACK    （确认，连接建立）
                                  ↑ 注意这是 ACK，不是 SYN
```

### 为什么是三次？（必问追问）

> **"三次握手的目的是防止历史失效的连接请求突然到达服务端，造成资源浪费。"**

**两次握手的风险**：
- 客户端发了一个 SYN，网络延迟了
- 客户端超时重发并完成了通信
- 但那个延迟的 SYN 后来又到了服务端
- 服务端以为是新连接，分配资源等待
- 但客户端根本不认这个连接——造成**服务端资源浪费**

**三次握手的解决**：
- 第三次 ACK 给了客户端机会**告诉服务端**："那个旧的 SYN 我不认了"

### 状态变迁（加分项）

```
客户端：CLOSED → SYN_SENT → ESTABLISHED
服务端：CLOSED → LISTEN → SYN_RCVD → ESTABLISHED
```

## 3. TCP 四次挥手（必考第3题）

### 退出聊天群类比

```
你："我先撤了？"              → FIN    （你停止发言）
朋友："好的收到"              → ACK    （确认你撤了）
朋友："我还有一句没说..."     → 继续说
朋友："说完了，我也撤了"      → FIN    （朋友也停了）
你："好，拜拜"                → ACK    （确认，通话结束）
```

### 过程图（必背）

```
    主动方（客户端）                    被动方（服务端）
      │                                   │
      │ ① FIN (seq=u)                    │  → 主动方进入 FIN_WAIT_1
      │ ────────────────────────────────→ │
      │                                   │
      │ ② ACK (ack=u+1)                 │  → 被动方进入 CLOSE_WAIT
      │ ←──────────────────────────────── │
      │                                   │  → 主动方进入 FIN_WAIT_2
      │     （被动方可能还有数据要发）       │
      │                                   │
      │ ③ FIN (seq=w)                    │  → 被动方进入 LAST_ACK
      │ ←──────────────────────────────── │
      │                                   │
      │ ④ ACK (ack=w+1)                 │  → 主动方进入 TIME_WAIT（等2MSL后关闭）
      │ ────────────────────────────────→ │
      │                                   │  → 被动方关闭
```

### 为什么是四次？（必问追问）

> **"TCP 是全双工的，双方都有自己的发送通道。三次握手时服务端可以把 SYN 和 ACK 合并成一条回，所以三次就够了。但四次挥手时，收到 FIN 的一方可能还有数据没发完，所以先单独回 ACK 确认'收到了你的断开请求'，等自己数据发完再发 FIN。因为不能合并，所以是四次。"**

简化记忆：**分手分两次——你先说分手，等我收拾好行李，我再正式说分手。**

### TIME_WAIT 状态（加分项）

- 主动关闭方发完最后一个 ACK 后进入 TIME_WAIT，等待 **2MSL**（约 1-4 分钟）
- 目的：确保最后一个 ACK 能到达对方（如果丢了，对方会重发 FIN）
- 2MSL 期间端口不能被重用

## 4. HTTP 基础（必考第4题）

### GET vs POST 对比表（必背）

```
查排行榜  →  GET    数据在 URL 里 → 可以收藏分享
登录账号  →  POST   数据在请求体里 → 密码不暴露
```

| 特性 | GET | POST |
|------|-----|------|
| 数据位置 | URL 参数 `?key=value` | 请求体（Body） |
| 安全性 | 参数暴露在 URL 中 | 相对安全 |
| 长度限制 | 有（浏览器限制 2KB-8KB） | 理论上无限制 |
| 缓存 | 可缓存 | 默认不缓存 |
| 幂等性 | 幂等（查100次结果一样） | 不幂等（提交10次创建10个） |
| 用途 | 查询数据 | 提交/修改数据 |

### HTTP 状态码速记

| 范围 | 含义 | 常见状态码 |
|------|------|-----------|
| 2xx | 成功 | 200 OK、201 Created |
| 3xx | 重定向 | 301 永久、302 临时 |
| 4xx | 客户端错误 | 400 Bad Request、403 Forbidden、**404 Not Found** |
| 5xx | 服务端错误 | **500 Internal Error**、503 Service Unavailable |

### 面试口述模板

> **"GET 和 POST 最直观的区别是数据放的位置不同：GET 放在 URL 参数里，POST 放在请求体里。因此 GET 不安全、有限制、可缓存；POST 相对安全、无限制。游戏里登录用 POST，查排行榜用 GET。"**

## 5. Socket 编程基础（了解即可）

### TCP vs UDP Socket 对比

```
TCP Socket = 打电话
  socket() → connect() → send()/recv() → close()
  必须先连接，再收发

UDP Socket = 寄信
  socket() → sendto()/recvfrom() → close()
  直接发，不用连接
```

### C# TCP 客户端

```csharp
using System.Net.Sockets;

TcpClient client = new TcpClient();
await client.ConnectAsync("127.0.0.1", 7777);  // 拨号（三次握手）

NetworkStream stream = client.GetStream();

// 发送
byte[] data = Encoding.UTF8.GetBytes("Hello Server");
await stream.WriteAsync(data);

// 接收
byte[] buffer = new byte[1024];
int bytesRead = await stream.ReadAsync(buffer);
```

### C# UDP 客户端

```csharp
using System.Net.Sockets;

UdpClient udp = new UdpClient();

// 直接发送，不需要 connect
byte[] data = Encoding.UTF8.GetBytes("Hello");
udp.Send(data, data.Length, "127.0.0.1", 7777);

// 接收
IPEndPoint remoteEP = new IPEndPoint(IPAddress.Any, 0);
byte[] recv = udp.Receive(ref remoteEP);
```

## 6. 粘包问题（面试常问）

### 什么是粘包？

往水管里扔乒乓球：

```
扔了两个球：[球A][球B]
           ↓ 水流（TCP 流式协议）
对方收到可能是：
  情况1：[球A球B]           → 两个球粘在一起（粘包）
  情况2：[球A的一半]        → 球被拆开了（拆包）
         [球A剩下一半+球B]
```

### 解决方案

| 方案 | 原理 | 适用 |
|------|------|------|
| 固定长度 | 每条消息 N 字节 | 简单但浪费 |
| 特殊分隔符 | 用 `\n` 分隔 | 文本协议 |
| **长度前缀 ⭐** | 消息头4字节存长度 | **最常用** |

### 长度前缀格式

```
┌──────────────┬──────────────────────┐
│  消息头(4B)  │     消息体(变长)      │
│  存消息长度   │   实际数据内容        │
└──────────────┴──────────────────────┘

例：
[0x00000010][{"hp":100,"x":1.5}]
   ↑ 长度=16    ↑ 16字节数据
```

### 面试口述模板

> **"TCP 是字节流协议没有消息边界，所以会出现粘包问题。最常见的解决方案是长度前缀：每条消息前面加 4 个字节存放消息体长度，接收方先读 4 字节知道有多长，再精确读取对应长度的数据。"**

## 1. 帧同步 vs 状态同步（游戏面试必考题）

### 一句话区分

```
帧同步  = 只同步"你按了什么键"，大家各自算结果
状态同步 = 同步"你最终跑到哪了"，服务器算好告诉所有人
```

### 场景理解

**帧同步**（格斗游戏 / 街霸 / RTS / 星际争霸）：

```
玩家A按了"右+B拳" → 服务器广播给所有人 → 所有客户端各自计算
玩家B按了"左+防御" → 服务器广播给所有人 → 各自计算
→ 大家算出来的结果必须完全一样（确定性）
```

**状态同步**（FPS / MMO / 王者荣耀）：

```
玩家A按下移动键 → 客户端发指令 → 服务器计算新位置
                  → 服务器把最终位置广播给所有人
                  → 其他客户端直接显示"A在(10,5)"
```

### 核心对比表（必背）

| 特性 | 帧同步 | 状态同步 |
|------|--------|----------|
| 同步内容 | 玩家输入（按键） | 游戏状态（位置、血量等最终结果） |
| 计算位置 | **所有客户端各自算** | **服务端算完发结果** |
| 带宽占用 | 小（只传按键） | 大（传完整状态） |
| 反作弊 | 难（客户端有完整逻辑） | 易（服务端权威） |
| 回放录制 | 容易（只录输入序列） | 难（录完整状态流） |
| 网络要求 | 高（延迟敏感） | 中等 |
| 实现难度 | 高（需要确定性） | 中等 |
| 代表游戏 | 街霸、星际争霸、魔兽争霸 | 守望先锋、LOL、魔兽世界 |

### 面试官追问："为什么选择帧同步/状态同步？"

**选帧同步**：
- 需要精确的同步操作（格斗连招、RTS微操）
- 带宽有限（32人RTS，不可能同步所有单位状态）
- 需要完整的回放功能

**选状态同步**：
- 需要防作弊（服务端权威计算，拒绝恶意修改）
- 玩家数量多，不需要精确同步（MMO有上百人）
- 实现相对简单，不需要考虑确定性

### 面试口述模板

> **"帧同步只同步玩家的输入操作，比如按了什么键，然后广播给所有人，每个客户端各自计算结果，所以带宽小、回放容易。但要求游戏逻辑有确定性——所有客户端输入相同、算出的结果必须完全相同，实现难度高。适合格斗游戏、RTS这类操作精确、单位多的游戏。**
>
> **状态同步是服务端做权威计算，算好位置、血量这些最终状态再同步给客户端。防作弊好、实现简单，但带宽大、延迟感明显。适合 FPS、MMO 这类需要防作弊、玩家数量多的游戏。"**

## 3. KCP 概念（加分项）

KCP 是一个**可靠 UDP 协议**。它是个加分项，不是必考，但能说上会很加分。

### 为什么要用 KCP？（TCP 有什么问题）

```
TCP 对游戏来说最大的问题：
1. 队头阻塞：丢一个包，后面的所有包都得等这个重传
2. 重传慢：TCP 默认要等 200ms 才重传
3. 拥塞控制：发现丢包会自动降速

KCP 的改进：
1. 快速重传：收到一个包立刻发确认，不等定时器
2. 选择性重传：只重传真正丢了的包，不影响后面的
3. 不降速：以最低延迟为目标
```

### KCP 在游戏中的位置

```
UDP（不可靠）
  └── KCP（可靠 UDP，低延迟）
        └── 你的游戏协议（自定义消息）
```

### 一句话说清楚

> **"KCP 是在 UDP 之上实现的可靠传输协议，比 TCP 响应更快、延迟更低。它解决了 TCP 队头阻塞和重传慢的问题，适合实时竞技游戏的网络传输。"**

## 4. 心跳 + 断线重连（实际项目必问）

### 为什么要心跳？

```
网络连接可能突然断了（拔网线、WiFi断开），但服务端不知道。
TCP 要等超时才发现，可能要好几分钟。
心跳就是定期告诉对方："我还活着"。
```

### 心跳机制

```
客户端 ── 每5秒发一个心跳包 ──→ 服务端
                                ↓
                         服务端记录最后心跳时间
                                ↓
                         如果超过15秒没收到 → 判定断开
```

### 断线重连流程

```
① 检测到断线
    │
    ├──→ 方案A：显示重连中...（自动尝试）
    │     尝试间隔：1秒 → 2秒 → 4秒 → 8秒（指数退避）
    │
    ├──→ 重连成功
    │     客户端发送"我回来了" → 服务端下发当前状态
    │
    └──→ 重连失败（超过最大次数）
          提示"连接断开，请检查网络"
```

### 指数退避

```
第1次重试：等 1 秒
第2次重试：等 2 秒
第3次重试：等 4 秒
第4次重试：等 8 秒
...
最多 N 次后停止
```

### 断线重连的关键问题

**① 断线期间发生了什么？**
- 如果是位置游戏：服务端用 AI 托管角色
- 如果是回合制：服务端等待玩家操作，超时判负
- 如果是卡牌：服务端保留当前牌局状态

**② 重连后怎么恢复？**
- 客户端告诉服务端："我断线时的状态ID是 xxx"
- 服务端找出断线以来的所有状态变化，一次性发给客户端
- 客户端快速追赶所有变化

### 面试口述模板

> **"心跳是客户端定时发一个小包给服务端，告诉对方'我还活着'。如果服务端超过一定时间没收到心跳，就判定连接断开，回收资源。断线重连采用指数退避策略：1秒、2秒、4秒逐步增加重试间隔，避免频繁重试加重服务器负担。重连成功后，服务端会把断线期间的状态变化一次性同步给客户端。"**

## 5. 延迟与抖动处理（加分项）

### 什么是延迟？

```
你按了攻击键 → 网络传输 → 服务器处理 → 广播 → 对方收到
              ↑               延迟时间               ↑
```

### 常见优化手段

| 技术 | 原理 | 效果 |
|------|------|------|
| **客户端预测** | 不等服务器，先本地执行 | 减少感知延迟 |
| **服务器回滚** | 收到确认后和服务器对比，纠正错误 | 解决预测错误 |
| **插值** | 在两个已知位置之间平滑过渡 | 减少卡顿感 |
| **延迟补偿** | 服务器回溯到玩家发出指令的时间点做判定 | 公平判定 |

### 一句话说清楚

> **"客户端预测是不等服务器确认，先本地执行操作，让操作马上有反馈。服务器回滚是当服务器发来的状态和本地预测不一致时，纠正到正确状态。这两种技术组合使用，可以大大减少玩家感知到的延迟。"**

## 1. 序列化方案对比（面试常问）

### 什么是序列化？

```
序列化 = 把游戏对象（C# 对象）变成二进制/文本数据 → 通过网络发送
反序列化 = 把收到的数据变回游戏对象
```

### 核心对比表（必背）

| 方案 | 格式 | 大小 | 速度 | 可读性 | 游戏用途 |
|------|------|------|------|--------|----------|
| **JSON** | 文本 | 大 | 慢 | ✅ 可读 | 配置、登录接口 |
| **XML** | 文本 | 很大 | 慢 | ✅ 可读 | 旧项目配置 |
| **Protobuf** | 二进制 | 小 | 快 | ❌ 不可读 | **游戏协议主流** |
| **MessagePack** | 二进制 | 小 | 快 | ❌ 不可读 | 替代 JSON 做高性能场景 |
| **自定义二进制** | 二进制 | **最小** | **最快** | ❌ 不可读 | 极致性能场景 |

### 面试一句话

> **"游戏项目中最常用的是 Protobuf，因为它是二进制格式、体积小、序列化速度快，适合高频游戏消息传输。JSON 一般用于登录注册、配置读取这些低频场景。如果对性能要求极致，可以用自定义二进制协议。"**

---

## 2. Protobuf 核心概念（加分亮点）

### 什么是 Protobuf？

Protocol Buffers（Protobuf），Google 出的序列化框架，**游戏行业协议设计的标准方案**。

### 定义消息

```protobuf
// login.proto
message LoginRequest {
    string username = 1;   // 字段编号，不是值
    string password = 2;
}

message LoginResponse {
    int32 code = 1;        // 0=成功，1=失败
    string message = 2;
    PlayerInfo player = 3; // 嵌套消息
}

message PlayerInfo {
    int32 playerId = 1;
    string nickname = 2;
    int32 level = 3;
}
```

### 为什么游戏用 Protobuf 而不是 JSON？

```
JSON 协议：（76 字节）
{"playerId":12345,"nickname":"小明","level":10,"hp":100}

Protobuf 协议：（约 18 字节）
[0x08 0xB9 0x60 0x12 0x06 0xE5 0xB0 0x8F 0xE6 0x98 0x8E 0x18 0x0A ...]
     ↑ playerId=12345  ↑ nickname="小明"     ↑ level=10
```

**Protobuf 胜出**：体积小 4 倍、快 3-10 倍

### 面试口述模板

> **"Protobuf 是游戏行业最常用的序列化方案。先用 .proto 文件定义消息结构，然后用工具生成 C# 代码，序列化后的二进制数据体积小、速度快。相比 JSON，Protobuf 体积小 3-5 倍，解析速度快 10 倍左右，非常适合游戏的高频消息传输。"**

---

## 3. 消息协议设计（实际项目必问）

### 完整的消息结构

一条完整的游戏消息一般包含三层：

```
┌─────────────────────────────────────────┐
│ 消息头（固定长度，16-24 字节）           │
│  ├─ 消息长度（4字节）                    │
│  ├─ 消息ID / 协议号（4字节）             │
│  ├─ 序列号/时间戳（4字节）               │
│  └─ 可选：用户ID/校验码（4-12字节）       │
├─────────────────────────────────────────┤
│ 消息体（变长，Protobuf 或 JSON）         │
│  ├─ 具体消息内容                        │
│  └─ 如：LoginRequest、MovePacket 等     │
└─────────────────────────────────────────┘
```

### 消息 ID 设计

```csharp
// 消息ID枚举（客户端+服务端共用）
public enum MessageID : ushort
{
    // 登录模块 (1000-1999)
    LoginRequest     = 1001,
    LoginResponse    = 1002,
    LogoutRequest    = 1003,
    
    // 玩家模块 (2000-2999)
    PlayerMove       = 2001,  // 客户端→服务端：移动
    PlayerSyncPos    = 2002,  // 服务端→客户端：同步位置
    PlayerAttack     = 2003,
    
    // 匹配模块 (3000-3999)
    MatchStart       = 3001,
    MatchSuccess     = 3002,
    MatchCancel      = 3003,
}
```

### 完整的收发流程

```
客户端发送：
  LoginRequest 对象 → Protobuf 序列化 → 加上消息头 → 长度前缀 → TCP/UDP 发送

服务端接收：
  读取长度前缀 → 读取完整消息体 → 解析消息头 → 根据消息ID反序列化 → 业务处理

服务端回复：
  LoginResponse 对象 → Protobuf 序列化 → 加消息头 → 发送

客户端接收：
  ...
```

### 面试口述模板

> **"游戏消息设计一般分消息头和消息体。消息头固定长度，包含消息长度、消息ID、序列号等关键信息；消息体用 Protobuf 序列化。消息ID用枚举管理，按模块分组（1000登录、2000玩家、3000匹配），方便扩展和维护。"**

## 4. 带宽优化（加分项）

### 为什么需要优化？

```
一个 100 人同时在线的 MOBA 游戏，每秒可能产生：
- 10 个玩家的位置更新 × 每秒 20 次 × 每次 100 字节
= 每分钟约 1.2MB 上行流量
- 10 个玩家的广播 × 每秒 20 次 × 每次 100 字节 × 9 个其他人
= 每分钟约 10.8MB 下行流量
```

### 优化手段

| 手段 | 原理 | 效果 |
|------|------|------|
| **差量更新** | 只传变化的数据，不传完整状态 | 减少 50-80% 数据量 |
| **频率控制** | 降低远距离对象的更新频率 | 减少 30-50% |
| **位压缩** | 用 bits 代替 bytes | 减少 50-80% |
| **裁剪视野** | 只同步视野内的对象 | 最有效的优化 |

### 差量更新示例

```csharp
// ❌ 完整状态（每次传所有字段）
message PlayerFullState {
    int32 playerId = 1;
    float x = 2;
    float y = 3;
    float z = 4;
    int32 hp = 5;
    int32 mp = 6;
    int32 level = 7;
    string name = 8;
}

// ✅ 差量更新（只传变化的部分）
message PlayerDelta {
    int32 playerId = 1;
    optional float x = 2;     // 没变化就不传
    optional float y = 3;
    optional float z = 4;
    optional int32 hp = 5;    // 扣血了才传
}
```

### 面试口述模板

> **"带宽优化主要用三个手段：差量更新（只传变化数据）、频率控制（远距离对象更新频率降低）、视野裁剪（只同步玩家视野范围内的对象）。其中视野裁剪是最有效的，因为大多数情况下，你只需要知道周围几十米内的其他玩家在做什么。"**

## 5. C# 网络编程完整示例（面试手写预备）

### 简单的 TCP Echo 客户端

```csharp
using System.Net.Sockets;
using System.Text;

class GameClient
{
    private TcpClient _client;
    private NetworkStream _stream;
    private byte[] _recvBuffer = new byte[4096];

    public async Task ConnectAsync(string ip, int port)
    {
        _client = new TcpClient();
        await _client.ConnectAsync(ip, port);
        _stream = _client.GetStream();
        Debug.Log("连接成功");
    }

    public async Task SendAsync(byte[] data)
    {
        // 长度前缀：先发4字节表示消息长度
        byte[] lenPrefix = BitConverter.GetBytes(data.Length);
        await _stream.WriteAsync(lenPrefix);
        await _stream.WriteAsync(data);
    }

    public async Task<byte[]> ReceiveAsync()
    {
        // 先读4字节长度
        int read = await _stream.ReadAsync(_recvBuffer, 0, 4);
        int msgLen = BitConverter.ToInt32(_recvBuffer, 0);
        
        // 再读取完整消息体
        byte[] msgBody = new byte[msgLen];
        int totalRead = 0;
        while (totalRead < msgLen)
        {
            read = await _stream.ReadAsync(msgBody, totalRead, msgLen - totalRead);
            totalRead += read;
        }
        return msgBody;
    }

    public void Disconnect()
    {
        _stream?.Close();
        _client?.Close();
    }
}
```

### 面试能说清楚这段代码的意思

```
ConnectAsync  → 连接服务器（三次握手发生在这一步）
SendAsync     → 长度前缀 + 消息体（解决粘包）
ReceiveAsync  → 先读4字节长度 → 再读消息体（解决拆包）
```

## 6. 网络安全基础（了解即可）

### 常见安全问题

| 问题 | 表现 | 解决方案 |
|------|------|----------|
| **篡改封包** | 修改内存数值、伪造封包 | 服务端权威校验、参数校验 |
| **加速外挂** | 移动速度异常 | 服务端校验移动距离 |
| **内存修改** | CE（Cheat Engine）修改本地数据 | 关键数据放服务端 |
| **DDoS 攻击** | 大量无效请求 | 防火墙、限流、验证码 |

> **"客户端发来的任何数据都是不可信的。关键逻辑必须放在服务端做权威计算，客户端只负责展示和输入。比如玩家的金币数量，服务端才是真实值，客户端只是一个显示。"**

### 场景 2：回合制卡牌

**"如果做一个 1v1 回合制卡牌游戏，网络方案和 MOBA 有什么不同？"**

**思考方向**：

```
1. 传输层：TCP 就够（不需要实时，卡牌操作不能丢）
2. 同步方案：状态同步（服务端验证出牌合法性）
3. 不需要客户端预测（不是实时操作）
4. 断线重连：保留当前牌局状态，重连后恢复
5. 简化了很多 MOBA 需要的优化
```

### 场景 3：格斗游戏

**"做一个 1v1 格斗游戏，像街霸那样搓招的，网络怎么做？"**

**思考方向**：

```
1. 传输层：UDP 或 KCP（帧同步对延迟极其敏感）
2. 同步方案：帧同步
   - 只传玩家的按键输入
   - 每个客户端各自计算结果
   - 需要确定性（相同输入必须相同输出）
3. 回滚机制：
   - 预测对方行动
   - 收到实际输入后不一致就回滚纠正
4. 回放：只录制输入序列
```

## 4. 模拟面试题 — 完整答案版

### 高频 15 题完整答案

按面试概率排序，每题给出可直接背诵的标准回答：

---

**Q1：TCP 和 UDP 的区别？**

> "TCP 和 UDP 有三个核心区别：第一，TCP 是面向连接的，需要三次握手建立连接；UDP 无连接，直接发数据。第二，TCP 可靠，有确认重传机制保证数据不丢；UDP 不可靠，丢了就丢了。第三，TCP 慢但稳，UDP 快但可能丢。
>
> 游戏开发中登录、充值、匹配这些不能丢数据的场景用 TCP；技能释放、位置同步这些实时玩法用 UDP，因为延迟比可靠性更重要。实际项目中常常两者混合使用。"

---

**Q2：TCP 三次握手的过程？**

> "三次握手分三步：
> 第一步，客户端发 SYN 包给服务端，表示想建立连接，进入 SYN_SENT 状态。
> 第二步，服务端收到后回 SYN+ACK，确认收到并也发起连接请求，进入 SYN_RCVD 状态。
> 第三步，客户端收到后回 ACK，双方进入 ESTABLISHED 状态，连接建立。
>
> 之所以需要三次，是为了防止历史失效的连接请求到达服务端造成资源浪费。比如客户端发了一个 SYN 但网络延迟了，客户端超时重发并完成了通信。那个延迟的 SYN 后来到了服务端，三次握手中客户端可以在第三次确认或否认这个旧的连接。"

---

**Q3：帧同步和状态同步的区别？**

> "帧同步只传玩家的输入操作，服务器转发给所有人，每个客户端各自计算结果，所以带宽小、回放容易，但需要确定性，实现难度高。
>
> 状态同步是服务器做权威计算，算好血量、位置这些最终状态再同步给客户端，防作弊好、实现简单，但带宽大、延迟感明显。
>
> 格斗游戏和 RTS 适合帧同步，FPS 和 MMO 适合状态同步。"

---

**Q4：粘包问题怎么解决？**

> "TCP 是字节流协议没有消息边界，所以会出现粘包问题。最常见的解决方案是长度前缀：每条消息前面加 4 个字节存放消息体长度，接收方先读 4 字节知道有多长，再精确读取对应长度的数据。除了长度前缀，还有固定长度和特殊分隔符两种方案，但游戏开发中最常用的是长度前缀。"

---

**Q5：游戏里为什么 UDP 比 TCP 更常用？**

> "对实时游戏来说，UDP 有三个核心优势。
>
> 第一，TCP 有队头阻塞问题——丢一个包，后面的所有包都得等这个重传；UDP 没有这个问题。
>
> 第二，TCP 重传慢，默认超时重传要等 200ms，游戏等不起；UDP 可以自己控制重传策略。
>
> 第三，TCP 有拥塞控制，发现丢包会自动降速，但游戏需要持续的速率；UDP 不需要，应用层自己控制。
>
> 所以 FPS、MOBA、格斗这类实时对战游戏的核心玩法都用 UDP，只在登录、匹配等需要可靠性的场景用 TCP。"

---

**Q6：TCP 四次挥手的过程？**

> "四次挥手分四步：
> 第一步，主动方发 FIN 包，表示自己不再发数据了，进入 FIN_WAIT_1 状态。
> 第二步，被动方回 ACK，确认收到断开请求，进入 CLOSE_WAIT 状态。主动方收到后进入 FIN_WAIT_2。
> 第三步，被动方发完所有数据后，发 FIN 包表示自己也停止发送，进入 LAST_ACK 状态。
> 第四步，主动方回 ACK 确认，进入 TIME_WAIT 状态等待 2MSL 后关闭。
>
> 之所以需要四次而不是像握手那样合并，是因为收到 FIN 的一方可能还有数据没发完，所以先单独回 ACK，等数据发完再发自己的 FIN。三次握手时双方可以同时打招呼，但挥手是一方先停另一方后停，不能合并。"

---

**Q7：GET 和 POST 的区别？**

> "最直观的区别是数据位置不同：GET 把数据放在 URL 参数里，POST 放在请求体里。因此 GET 不安全（参数可见）、有长度限制、可缓存、幂等；POST 相对安全、无长度限制、不缓存、不幂等。游戏开发中查排行榜用 GET，登录注册用 POST。"

---

**Q8：心跳机制有什么用？怎么实现？**

> "心跳有三个作用：第一，快速检测死连接，不用等 TCP 超时；第二，保活 NAT 映射，防止路由器的地址映射超时关闭；第三，附带时间戳可以计算延迟。
>
> 实现上，客户端每隔 5 秒发一个心跳包给服务端，服务端记录最后心跳时间。如果超过 15 秒没收到，就判定连接断开，回收资源。"

---

**Q9：Protobuf 是什么？为什么用它？**

> "Protobuf 是 Google 出的序列化框架，游戏行业的标准方案。先用 .proto 文件定义消息结构，工具自动生成 C# 代码，序列化后的二进制数据体积小、速度快。相比 JSON，Protobuf 体积小 3-5 倍，解析速度快 10 倍左右。而且 .proto 文件本身就是协议文档，客户端和服务端共用一份，一致性有保障。"

---

**Q10：怎么设计游戏消息协议？**

> "游戏消息分消息头和消息体两层。消息头固定长度，包含消息长度（解决粘包）、消息ID（区分消息类型）、序列号等。消息体用 Protobuf 序列化。消息ID 按模块分组管理，比如 1000 段给登录、2000 段给玩法、3000 段给匹配。这样结构清晰、方便扩展。"

---

**Q11：HTTP 状态码 200/301/404/500 是什么意思？**

> "200 表示请求成功；301 表示永久重定向；404 表示资源找不到；500 表示服务器内部错误。游戏开发中最常见的是 200 和 404。"

---

**Q12：KCP 是什么？**

> "KCP 是在 UDP 之上实现的可靠传输协议。它比 TCP 响应更快、延迟更低，因为 KCP 收到包后立刻发确认不等定时器、只重传真正丢了的包不影响后面的、而且不会像 TCP 那样丢包后自动降速。KCP 解决了 TCP 队头阻塞和重传慢的问题，适合实时竞技游戏。"

---

**Q13：服务端怎么处理高并发连接？**

> "高并发服务端的核心是 I/O 多路复用。Linux 用 epoll，核心思想是一个线程可以同时监控成百上千个连接，哪个连接有数据来了就处理哪个，没有数据就等待，不需要为每个连接开一个线程。配合 Reactor 反应器模式，把连接事件分发给不同的处理器。这种方案可以支持上万并发连接。"

---

**Q14：断线重连怎么实现？**

> "断线重连分三个阶段：
> 短时间断线（几秒内），角色原地不动等待重连。
> 中等时间（几十秒），用简单 AI 托管角色撤退到安全位置。
> 长时间断线，判负踢出但保留数据。
>
> 重连机制采用指数退避策略：1秒、2秒、4秒、8秒逐步增加重试间隔，避免频繁重试冲击服务器。重连成功后，客户端发送断线时的状态 ID，服务器把这段时间的所有变化一次性下发，让客户端快速追上来。"

---

**Q15：防作弊怎么做？**

> "防作弊的核心原则是：客户端不可信，关键数据必须服务端权威计算。
>
> 帧同步架构本身就有天然优势——客户端只传按键输入，没有血量、位置这些关键数据可改。服务器会校验每帧输入是否合理（比如同一帧不能按两个相反方向），同时检测多个客户端的计算结果是否一致。
>
> 状态同步架构中，服务器本身就是权威计算端，客户端只是一个终端显示。改客户端的血量只是自欺欺人，因为服务器根本不认。
>
> 除了这些，还要配合封包加密、输入宏检测、匹配分惩罚系统等多层防线。"

### 面基础：6 问快速问答

**Q1：TCP 和 UDP 的区别？**

> "TCP 面向连接、可靠、慢；UDP 无连接、不可靠、快。游戏里登录用 TCP，实时对战用 UDP。"

**Q2：三次握手是什么？为什么不是两次？**

> "三次握手是 SYN → SYN+ACK → ACK。不是两次是为了防止历史失效连接请求到达服务端造成资源浪费。"

**Q3：四次挥手是什么？为什么是四次？**

> "四次挥手是 FIN → ACK → FIN → ACK。因为收到 FIN 的一方可能还有数据要发，不能像三次握手那样合并，所以要多一步。"

**Q4：GET 和 POST 的区别？**

> "GET 数据在 URL 里、不安全、可缓存、幂等；POST 数据在请求体里、相对安全、不缓存、不幂等。游戏里查排行榜用 GET，登录用 POST。"

**Q5：什么是粘包？怎么解决？**

> "TCP 是流式协议没有消息边界，所以发多条消息可能粘在一起。最常用解决方案是长度前缀：消息头 4 字节存长度 + 消息体。"

**Q6：HTTP 状态码 404 和 500 是什么意思？**

> "404 是资源找不到，客户端请求了一个不存在的地址。500 是服务器内部错误，服务器在处理请求时出问题了。"

### 面游戏：6 问深度问答

**Q1：帧同步和状态同步的区别？你做过哪个？**

> "帧同步传输入，客户端各自算结果，适合格斗/RTS。状态同步服务器算完发结果，适合 FPS/MMO。我目前对帧同步和状态同步都有理论理解，但实践上更倾向于先说清楚它们的本质区别和适用场景。"

**Q2：怎么为你的游戏选网络库？**

> "中小型项目用 Mirror，免费开源、上手快。快速原型用 Photon PUN2，开箱即用。竞技游戏用 Photon Fusion 或 Netcode for GO，UDP 传输延迟低。自研框架可以用 LiteNetLib，轻量灵活。选型主要看项目规模、实时性要求和团队技术栈。"

**Q3：心跳机制怎么实现？断了怎么重连？**

> "客户端每 5 秒发心跳包，服务端超过 15 秒没收到就判定断开。重连采用指数退避：1→2→4→8 秒递增重试。重连成功后端下发断线期间的状态变化，客户端快速追上。"

**Q4：怎么设计消息协议？**

> "消息头（长度+消息ID+序列号）+ 消息体（Protobuf）。消息ID 按模块枚举，1000 段登录、2000 段玩法、3000 段匹配。长度前缀解决粘包，消息ID 区分消息类型。"

**Q5：防作弊怎么做？**

> "核心原则是客户端不可信、服务端权威。帧同步通过输入校验和计算结果一致性检测防作弊；状态同步天然由服务器权威计算。配合封包加密、输入宏检测和惩罚系统。"

**Q6：Protobuf 好在哪里？**

> "二进制格式体积小（比 JSON 小 3-5 倍）、解析快（快 10 倍）、.proto 文件自动生成代码、协议文档代码合一。所以是游戏行业序列化的标准方案。"

### 场景题：完整答案

**场景 1：设计一个 10 人吃鸡游戏的网络系统**

> "我会选状态同步，因为吃鸡需要防作弊，而且场景复杂做不了确定性。
>
> 具体方案：传输层用 UDP，技能和位置同步延迟优先。同步方案是状态同步，服务器做权威计算，包括射击判定、伤害计算。带宽优化上，核心是视野裁剪——只同步玩家视野范围内的其他玩家和道具，这是吃鸡最有效的优化手段。消息协议用 Protobuf，消息头带长度和消息ID。断线重连用指数退避，重连后服务端下发当前游戏状态。"

**场景 2：玩家反馈延迟高，你怎么排查？**

> "第一步先区分是网络延迟还是渲染卡顿。ping 服务器看延迟，如果 ping 正常但帧率低，那是渲染问题。
>
> 如果是网络延迟，进一步看 p90/p99 延迟分布——大部分用户在 50ms 以内还是 200ms 以上？丢包率超过 2% 就会有明显卡顿。对比不同地区的延迟数据，看是不是特定区域的问题。
>
> 工具层面可以用 Wireshark 抓包分析实际网络交互，Unity 的 Profiler 看 Network 开销。排查出问题后针对性优化：降低更新频率、启用差量更新、或者增加节点部署。"
