## 01 基础篇

### 1.1 MySQL 架构

MySQL 架构分为两层：

```
客户端
    ↓
┌──────────────────────────────────────────┐
│            Server 层（通用）              │
│  连接器 → 查询缓存 → 解析器 → 优化器     │
│  → 执行器（调用存储引擎接口）             │
└──────────────────────────────────────────┘
    ↓ 存储引擎接口（可插拔）
┌──────────────────────────────────────────┐
│        存储引擎层（可插拔）               │
│   InnoDB（默认）/ MyISAM / Memory / …    │
└──────────────────────────────────────────┘
    ↓
  磁盘（数据文件 .ibd）
```

**各组件职责**：
- **连接器**：管理连接（TCP 握手、身份验证、权限加载）。`show processlist` 查看连接状态
- **查询缓存**：SQL 结果缓存（8.0 已删除，命中率极低，任何表更新都全量失效）
- **解析器**：词法 + 语法分析，生成解析树（Parse Tree）
- **预处理器**：语义检查（表/字段是否存在）、`*` 展开为实际字段名
- **优化器**：选择最优执行计划（索引选择、JOIN 顺序、子查询改写）
- **执行器**：调用存储引擎 API，逐行返回结果

> ⚠️ **查询缓存为什么被删除？**  
> 查询缓存以 SQL 文本为 key，任何涉及该表的**写操作**都会使该表所有缓存失效。写多读少的场景下维护缓存的开销远大于收益，且大多数应用层已有应用级缓存（Redis）。

### 1.2 InnoDB vs MyISAM

| 对比项 | InnoDB（5.5+ 默认）| MyISAM |
|--------|------------------|--------|
| 事务 | ✅ ACID | ❌ |
| 外键 | ✅ | ❌ |
| 行级锁 | ✅ | ❌（仅表锁）|
| 崩溃恢复 | ✅ redo log | ❌（崩溃后需完整修复）|
| 全文索引 | ✅（5.6+）| ✅ |
| Count(*) | 需扫全表（无法利用事务）| 直接读取元数据 |
| 聚簇索引 | ✅ 索引即数据 | ❌ 独立数据文件 |
| 适用场景 | 读写混合、事务型应用 | 只读/读多写少（已基本淘汰）|

---

### 1.3 一条 SQL 查询语句的执行流程

```sql
SELECT name FROM user WHERE id = 1;
```

1. 客户端发起连接（连接器验证权限）
2. 查询缓存（8.0 已删，跳过）
3. 解析器：词法解析 → 语法解析 → 生成解析树
4. 预处理器：检查 `user` 表和 `name`、`id` 字段是否存在
5. 优化器：选择 `id` 主键索引，生成执行计划
6. 执行器：调用 InnoDB 存储引擎接口，按索引查找 `id=1` 的记录
7. 存储引擎从 Buffer Pool（或磁盘）读取数据页，返回结果

---

### 1.4 一条 UPDATE 语句的执行流程

```sql
UPDATE user SET name = 'xiaolin' WHERE id = 1;
```

1. 连接器 → 解析器 → 优化器（选 id 主键索引）→ 执行器
2. 存储引擎从 Buffer Pool 找到 id=1 的记录（缓存命中或从磁盘读入）
3. **写 undo log**（记录修改前的旧值，用于事务回滚和 MVCC）
4. 更新内存中的数据页（Buffer Pool 中的脏页）
5. **写 redo log**（记录物理修改，prepare 状态）
6. 执行器通知 Server 层，Server 层**写 binlog**
7. 提交事务：redo log 进入 **commit 状态**（两阶段提交完成）
8. 事务提交后，脏页在合适时机刷入磁盘

## 02 索引篇

### 2.1 索引的底层数据结构

#### 为什么选 B+ 树而不是其他？

**哈希表**：O(1) 点查，但不支持范围查询、排序、前缀匹配 → 不适合数据库通用索引

**二叉搜索树/AVL/红黑树**：树高 O(log N)，但 N 很大时树高很高，每层一次磁盘 I/O → 磁盘 I/O 次数太多

**B 树**（多路平衡搜索树）：非叶子节点也存数据，导致每个节点能存的索引条数更少，树更高；且范围查询需要中序遍历，需要多次回溯

**B+ 树**（最终选择）：

```
                    [30 | 60]                 ← 非叶子节点，只存索引键
                   /    |    \
           [10|20]   [30|50]   [60|80]        ← 非叶子节点
          /  |   \    ...      ...
[1|5|10] [15|20] [25|30]  ...  [75|80] [90]   ← 叶子节点（存数据+指针串联）
    ↕       ↕        ↕              ↕    ↕
  （所有叶子节点构成双向链表，支持范围查询）
```

**B+ 树的核心优势**：
1. **非叶子节点只存索引键**（不存数据），同样大小的节点能存更多键 → **树更矮**（通常只有 3~4 层）
2. **叶子节点用链表串联**，范围查询定位到起点后，顺序扫描链表即可（无需回溯）
3. 磁盘友好：InnoDB 页大小 16 KB，每次读取一个页，B+ 树一次磁盘 I/O 读一个节点

> 💡 **为什么 B+ 树能存千万数据只需 3~4 层？**  
> 非叶子节点页大小 16 KB，假设索引键 8 字节 + 指针 6 字节 = 14 字节，每个非叶子节点存约 16384/14 ≈ **1170 个索引**。  
> - 2 层 B+ 树：1170 × 16 = **18,720** 条记录  
> - 3 层 B+ 树：1170 × 1170 × 16 ≈ **2,190 万**条记录  
> - 4 层 B+ 树：约 **256 亿**条记录  
> 所以**千万级数据，B+ 树只需约 3 层，最多 3 次磁盘 I/O 即可定位到数据**。

---

### 2.2 InnoDB 索引类型

#### 聚簇索引（Clustered Index）

- **InnoDB 表必须有且只有一个聚簇索引**
- 优先选主键作为聚簇索引；无主键则选第一个 NOT NULL UNIQUE 列；都没有则 InnoDB 内部生成隐藏 6 字节的 rowid
- **叶子节点直接存储完整的行数据**（索引即数据，数据文件就是索引文件 `.ibd`）

```
聚簇索引（主键索引）：
叶子节点 → [主键值 | 整行数据]
```

#### 二级索引（Secondary Index，非聚簇索引）

- 叶子节点存储 **索引列的值 + 对应行的主键值**（不存完整行）
- 查询时若需要非索引列，必须先通过二级索引找到主键，再回主键索引查完整行，称为**回表**

```
二级索引（如 name 索引）：
叶子节点 → [name 值 | 主键 id]
           ↓（回表）
聚簇索引  → [id | 完整行数据]
```

> ⚠️ **回表的代价**：回表意味着需要访问两棵 B+ 树（二级索引 + 主键索引），可能产生随机 I/O。若查询频繁且数据量大，回表是性能瓶颈。

---

### 2.3 联合索引与最左匹配原则

联合索引 `(a, b, c)` 的 B+ 树按 a → b → c 的顺序排列，即**先按 a 排序，a 相同再按 b 排序，b 相同再按 c 排序**。

**最左匹配原则**：使用联合索引时，必须从最左侧的字段开始匹配，且不能跳过中间字段。

```sql
-- 索引 (a, b, c)
WHERE a = 1                       ✅ 命中 a
WHERE a = 1 AND b = 2             ✅ 命中 a, b
WHERE a = 1 AND b = 2 AND c = 3  ✅ 命中 a, b, c
WHERE b = 2 AND c = 3            ❌ 不命中（缺少 a）
WHERE a = 1 AND c = 3            ⚠️ 只命中 a（b 缺失导致 c 无法用索引）
WHERE a = 1 AND b > 2 AND c = 3  ⚠️ 命中 a, b（b 是范围查询，c 的索引失效）
```

> 💡 **范围查询后字段失效的原因**：b > 2 时，在 b 的范围内 c 的值不是有序的，无法利用 c 的索引顺序加速查找。

---

### 2.4 覆盖索引（Covering Index）

**定义**：查询所需的所有字段都在索引中，**无需回表**。

```sql
-- 索引 (name, age)
SELECT age FROM user WHERE name = 'xiaolin';
-- name 在索引，age 也在索引 → 覆盖索引，不回表 ✅
```

- `EXPLAIN` 中 `Extra = Using index` 表示使用了覆盖索引

> ⚠️ **覆盖索引 vs 索引覆盖**：两者是同一概念，说法不同而已。

---

### 2.5 索引下推（Index Condition Pushdown，ICP）

**5.6+ 优化特性**：在存储引擎层就过滤部分 WHERE 条件，减少回表次数。

**没有 ICP 的流程（旧）**：  
存储引擎 → 用索引找到所有满足最左字段条件的记录 → 全部回表 → Server 层再过滤其余 WHERE 条件

**有 ICP 的流程（新）**：  
存储引擎 → 用索引找到满足最左字段条件的记录 → **在存储引擎层就用联合索引中的后续字段过滤** → 只有通过过滤的记录才回表

```
-- 索引 (name, age)，查询：
SELECT * FROM user WHERE name LIKE '小%' AND age = 18;

-- 旧：找所有 name LIKE '小%' 的记录（可能很多）→ 全部回表 → Server 层过滤 age = 18
-- ICP：找所有 name LIKE '小%' 的记录 → 存储引擎层同时检查 age = 18 → 只回表通过的记录
```

- `EXPLAIN` 中 `Extra = Using index condition` 表示使用了 ICP

---

### 2.6 索引失效的常见场景

| 场景 | 示例 | 失效原因 |
|------|------|---------|
| 对索引列使用函数 | `WHERE YEAR(create_time) = 2023` | 函数改变了列值，无法直接用索引顺序 |
| 对索引列做类型转换 | `WHERE phone = 13812345678`（phone 是 varchar） | 隐式转换，等于对字段加了 CAST 函数 |
| 对索引列做运算 | `WHERE id + 1 = 2` | 表达式改变了列值 |
| LIKE 前缀通配符 | `WHERE name LIKE '%xiaolin'` | 前缀不确定无法用 B+ 树有序性（但 `LIKE 'xiaolin%'` 可以）|
| OR 连接非索引字段 | `WHERE id = 1 OR age = 18`（age 无索引）| OR 中有一个字段无索引，全表扫描更划算 |
| 联合索引不遵循最左匹配 | （见 2.3）| — |
| 数据分布导致全表扫描更快 | `WHERE status = 1`（99% 的记录 status=1）| 优化器判断索引代价 > 全表扫描 |
| != / NOT IN / NOT EXISTS | `WHERE id != 1` | 范围太大，结果集大，索引收益低 |

> ⚠️ **索引失效并非绝对**：优化器基于成本（Cost）估算选择执行计划。即使 WHERE 中使用了函数，如果强制用 FORCE INDEX，仍然会走索引（虽然低效）。反之，即使条件很匹配，优化器也可能认为全表扫描更快（如数据集极小）。

---

### 2.7 主键的选择

- **推荐使用自增主键**（AUTO_INCREMENT INT/BIGINT）
  - 保证 B+ 树页的顺序插入，**不会导致页分裂**
  - UUID/随机 ID：插入时需要找到合适位置，可能导致大量**页分裂**（内存 + 磁盘 I/O 消耗大）
- **主键不宜过长**：二级索引叶子节点存主键值，主键越长，二级索引越大，内存占用越多

---

### 2.8 索引优化实战

**前缀索引**：对长字符串字段取前 N 个字符建索引，节省空间（但无法利用覆盖索引）
```sql
ALTER TABLE user ADD INDEX idx_email(email(10));  -- email 前 10 个字符
```

**查看索引效率（EXPLAIN 关键字段）**：

| 字段 | 重要值 | 含义 |
|------|--------|------|
| `type` | `const` > `ref` > `range` > `index` > `ALL` | 越靠左越好，ALL 是全表扫描 |
| `key` | 实际用的索引名 | NULL 表示未用索引 |
| `rows` | 预计扫描行数 | 越少越好 |
| `Extra` | `Using index`（覆盖索引）/ `Using index condition`（ICP）/ `Using filesort`（文件排序，慢）/ `Using temporary`（临时表，慢）| — |

## 03 事务篇

### 3.1 事务的 ACID 特性

| 特性 | 含义 | InnoDB 实现 |
|------|------|------------|
| **原子性（Atomicity）** | 事务中的操作要么全成功，要么全回滚 | **undo log**（记录旧值，回滚时还原）|
| **一致性（Consistency）** | 事务前后数据库从一个合法状态转到另一个合法状态 | 原子性+隔离性+持久性共同保障 |
| **隔离性（Isolation）** | 并发事务互不干扰 | **MVCC + 锁** |
| **持久性（Durability）** | 提交后即使宕机，数据也不丢失 | **redo log**（崩溃恢复）|

> 💡 **一致性是目的，原子性+隔离性+持久性是手段**。数据库的 AID 三性的实现共同保障 C（一致性）。

---

### 3.2 四种事务隔离级别

**并发问题**：

| 问题 | 定义 |
|------|------|
| **脏读（Dirty Read）** | 读到了另一个**未提交**事务修改的数据 |
| **不可重复读（Non-Repeatable Read）** | 同一事务内两次读同一行，另一事务在中间**提交了修改**，两次结果不同 |
| **幻读（Phantom Read）** | 同一事务内两次范围查询，另一事务在中间**插入/删除了满足条件的行**，两次结果行数不同 |

**四种隔离级别及解决的并发问题**：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|-----------|------|
| **读未提交（Read Uncommitted）** | ✅ 可能 | ✅ 可能 | ✅ 可能 |
| **读提交（Read Committed，RC）** | ❌ 解决 | ✅ 可能 | ✅ 可能 |
| **可重复读（Repeatable Read，RR）InnoDB 默认** | ❌ 解决 | ❌ 解决 | ⚠️ 基本解决（见 3.4）|
| **串行化（Serializable）** | ❌ 解决 | ❌ 解决 | ❌ 解决 |

> ⚠️ **InnoDB 默认隔离级别是可重复读（RR）**，而非 SQL 标准推荐的读提交（RC）。原因是 MySQL 的 binlog 早期只支持 statement 格式，RC 级别下 binlog 记录不准确，会导致主从不一致。

---

### 3.3 MVCC（多版本并发控制）

MVCC 通过 **Read View + undo log 版本链** 实现非阻塞读，是 InnoDB RR 和 RC 隔离级别的核心机制。

#### 每行记录的三个隐藏字段

| 字段 | 作用 |
|------|------|
| `trx_id` | 最近一次修改该行的事务 ID |
| `roll_pointer` | 指向 undo log 中该行上一个版本的指针（构成版本链）|
| `row_id` | 无主键时 InnoDB 自动生成的行 ID（有主键时无需此字段）|

#### undo log 版本链

每次对行的修改，旧版本通过 roll_pointer 串联成链：
```
当前最新版本 → [trx_id=50, name='xiaolin'] → roll_pointer
                                               ↓ undo log
                      旧版本 [trx_id=30, name='xiaohua'] → roll_pointer
                                                           ↓
                           更旧版本 [trx_id=10, name='xiaoming']
```

#### Read View（读视图）

Read View 是事务**开始读取时**生成的快照，包含四个关键字段：

| 字段 | 含义 |
|------|------|
| `creator_trx_id` | 创建该 Read View 的事务 ID |
| `m_ids` | 创建时**活跃事务的 ID 列表**（已开启但未提交的事务）|
| `min_trx_id` | m_ids 中最小的事务 ID |
| `max_trx_id` | 下一个将要分配的事务 ID（即当前已分配的最大 ID + 1）|

#### 可见性判断规则

遍历版本链，对每个版本的 `trx_id` 按以下规则判断是否可见：

```
① trx_id == creator_trx_id          → 可见（自己修改的，当然能看到）

② trx_id < min_trx_id               → 可见（在 Read View 创建前已提交）

③ trx_id >= max_trx_id              → 不可见（在 Read View 创建后才开启的事务）

④ min_trx_id <= trx_id < max_trx_id → 进一步判断：
   - trx_id 在 m_ids 中              → 不可见（活跃事务，未提交）
   - trx_id 不在 m_ids 中            → 可见（在 Read View 创建前已提交）
```

若当前版本不可见，沿 roll_pointer 找上一个版本，重复判断，直到找到可见版本或到达最旧版本。

#### RC 和 RR 的 Read View 创建时机差异

| 隔离级别 | Read View 创建时机 | 效果 |
|---------|-----------------|------|
| **RC（读提交）** | **每次 SELECT 前**重新创建 Read View | 能看到 SELECT 时已提交的最新数据 → 解决脏读，但仍有不可重复读 |
| **RR（可重复读）** | **事务第一次 SELECT 时**创建 Read View，整个事务复用 | 整个事务看到的是事务开始时的快照 → 解决不可重复读 |

> 💡 **记忆要点**：RC 每次语句创建新快照，RR 事务开始时创建一次，快照不变。

---

### 3.4 可重复读如何解决幻读（以及它的局限）

#### 快照读（普通 SELECT）——通过 MVCC 解决
事务 A 开始后，其 Read View 不变，其他事务插入的新行的 trx_id > max_trx_id，不可见 → **快照读不会看到幻读**

#### 当前读（锁定读）——通过 next-key lock 解决
`SELECT ... FOR UPDATE` / `SELECT ... LOCK IN SHARE MODE` / `INSERT` / `UPDATE` / `DELETE` 会读取最新数据（不走 MVCC），需要用 **next-key lock** 锁住查询范围，防止其他事务插入 → **当前读通过锁解决幻读**

#### ⚠️ RR 下的幻读特殊场景（重要！）

```sql
-- 表中只有 id=1,2,3,4 的记录
-- 事务 A：
BEGIN;
SELECT * FROM t WHERE id > 3;  -- 快照读，结果：[4]，生成 Read View

-- 事务 B（另一会话）：
INSERT INTO t VALUES(5, 'xiaomei', 18);
COMMIT;

-- 事务 A（继续）：
UPDATE t SET name = 'xiaolin' WHERE id = 5;   -- 当前读，实际写入，导致版本链 trx_id 变为 A 的事务 ID
SELECT * FROM t WHERE id > 3;  -- 快照读，id=5 的 trx_id 现在等于 creator_trx_id → 可见！

-- 结果：事务 A 看到了 id=5 的记录，发生了幻读！
```

**本质**：先快照读 → 再当前读写入操作修改了被其他事务插入的行（导致 trx_id 变为自己）→ 再快照读看见了这条"本不该看见"的行。

## 04 锁篇

### 4.1 MySQL 锁的分类

```
MySQL 锁
├── 全局锁（FTWRL，锁整个数据库）
├── 表级锁
│   ├── 表锁（LOCK TABLES）
│   ├── 元数据锁（MDL，防止查询期间 DDL 改表结构）
│   ├── 意向锁（IS/IX，表级别，标记表中有行锁，避免表锁和行锁冲突检测）
│   └── AUTO-INC 锁（自增锁）
└── 行级锁（InnoDB 特有）
    ├── 记录锁（Record Lock）
    ├── 间隙锁（Gap Lock）
    └── 临键锁（Next-Key Lock = Gap Lock + Record Lock）
```

---

### 4.2 全局锁

```sql
FLUSH TABLES WITH READ LOCK;  -- 加全局读锁，整个数据库只读
-- 用于全库逻辑备份
UNLOCK TABLES;
```

> ⚠️ **逻辑备份推荐方式**：`mysqldump --single-transaction`（InnoDB），利用 MVCC 快照读，不需要全局锁即可保证备份一致性。全局锁期间所有写操作被阻塞，生产环境慎用。

---

### 4.3 表级锁

#### 表锁（Table Lock）
```sql
LOCK TABLES t READ;    -- 共享读锁（所有会话可读，不可写）
LOCK TABLES t WRITE;   -- 独占写锁（仅本会话可读写，其他会话阻塞）
UNLOCK TABLES;
```

#### 元数据锁（MDL，Metadata Lock）
- **MySQL 5.5 自动加**，无需手动控制
- 执行 DML（SELECT/INSERT/UPDATE/DELETE）时，自动加 **MDL 读锁**（可并发）
- 执行 DDL（ALTER TABLE）时，自动加 **MDL 写锁**（独占，阻塞所有读写）
- **MDL 锁在事务提交后释放**（不是语句结束后）

> ⚠️ **MDL 锁导致的线上问题**：  
> 1. 长事务持有 MDL 读锁
> 2. 另一个 DDL 申请 MDL 写锁被阻塞（等待）
> 3. 后续所有 DML 请求也被 DDL 写锁排队阻塞（因为 MDL 写锁先于读锁）
> → 连接积累 → 数据库崩溃  
> **解决**：执行 DDL 前先 `KILL` 相关长事务；DDL 操作设置 `lock_wait_timeout`。

#### 意向锁（Intention Lock）
- **InnoDB 自动添加**，对行加共享/排他锁前，先在表上加 IS/IX 意向锁
- 用于快速检测"表中是否存在行锁"，避免为加表锁而扫描所有行
- IS（意向共享锁）与 IS/IX 兼容；IX 与 IX 兼容；IS/IX 与表级写锁（X）冲突

#### AUTO-INC 锁（自增锁）
- 插入时对自增列加锁，插入完成后立即释放（不等事务提交）
- MySQL 8.0 默认使用轻量级的**轻量互斥锁**（`innodb_autoinc_lock_mode=2`），并发性更好，但 binlog 必须是 ROW 格式

---

### 4.4 行级锁

#### 记录锁（Record Lock）
锁定索引中的**某一条记录**，防止其他事务修改或删除该行。

```sql
SELECT * FROM t WHERE id = 1 FOR UPDATE;  -- 在 id=1 的索引记录上加 X 型记录锁
```

#### 间隙锁（Gap Lock）
锁定**两个索引记录之间的间隙**（不包含端点记录本身），防止其他事务在这个范围内插入新记录。

```sql
-- 假设表中 id 有 1, 5, 10
SELECT * FROM t WHERE id BETWEEN 3 AND 7 FOR UPDATE;
-- 加 Gap Lock (1, 5) 和 (5, 10) → 其他事务无法插入 id=2,3,4,6,7,8,9
```

> ⚠️ **间隙锁只在 RR 隔离级别下存在**。RC 下没有间隙锁（所以更容易产生幻读）。  
> 间隙锁之间**不互斥**（两个事务可以同时持有同一范围的间隙锁），但间隙锁和**插入意向锁互斥**（阻止插入）。

#### 临键锁（Next-Key Lock = 间隙锁 + 记录锁）
锁定**某个索引记录及其前面的间隙**，是 InnoDB 默认的行锁形式，形如 `(a, b]`（左开右闭）。

> 💡 **InnoDB 加行锁的默认粒度就是 Next-Key Lock**，在某些条件下会退化：
> - 唯一索引等值查询（命中）→ 退化为记录锁
> - 唯一索引等值查询（未命中）→ 退化为间隙锁
> - 非唯一索引等值查询（命中）→ 记录锁 + 向右扫描的第一个不满足条件的间隙锁

#### 插入意向锁（Insert Intention Lock）
- 是间隙锁的一种特殊形式，INSERT 操作在插入前检查该位置是否有间隙锁（两者冲突则等待）
- 多个事务向**同一间隙的不同位置**插入时，插入意向锁之间**不互斥**（可并发插入）

---

### 4.5 加锁规则详解（InnoDB RR 级别）

**规则原则**（小林总结）：
1. InnoDB 行锁以 **next-key lock** 为基础
2. **唯一索引等值查询**：
   - 命中记录 → next-key lock **退化为记录锁**（只锁该行）
   - 未命中记录 → next-key lock **退化为间隙锁**（只锁间隙）
3. **非唯一索引等值查询**：
   - 命中记录 → 对命中记录加 next-key lock + **对右边第一个不满足条件的记录加间隙锁**（防止右边插入）
   - 未命中记录 → 退化为间隙锁
4. **唯一索引范围查询**：精确到范围两端
5. **非唯一索引范围查询**：范围内所有记录的 next-key lock

**示例**（表 t，主键 id 有记录：1, 5, 10, 15, 20）：

| 查询 | 加锁范围 |
|------|---------|
| `WHERE id = 5 FOR UPDATE` | 记录锁（只锁 id=5）|
| `WHERE id = 7 FOR UPDATE`（不存在）| 间隙锁 (5, 10)|
| `WHERE id >= 5 FOR UPDATE` | next-key lock (?, 5] ∪ (5, 10] ∪ (10, 15] ∪ (15, 20] ∪ (20, +∞] |
| 非唯一索引 `WHERE age = 18 FOR UPDATE`（18 存在）| next-key lock (上一个age值, 18] + 间隙锁 (18, 下一个age值) |

---

### 4.6 死锁

**死锁产生的条件**（同 OS 死锁四要素，见操作系统笔记）：互斥、持有并等待、不可剥夺、环路等待。

**InnoDB 死锁检测**：
- InnoDB 会自动检测死锁（等待图中的环），检测到后选择**代价最小的事务回滚**（`ERROR 1213: Deadlock found`）
- 检测算法代价 O(N²)，高并发场景可能成为瓶颈

**死锁预防策略**：
1. **按固定顺序加锁**（不同事务以相同顺序访问多个表/行，打破环路等待）
2. **减小事务范围**（事务尽可能短，减少锁持有时间）
3. **设置锁等待超时**（`innodb_lock_wait_timeout`，默认 50 秒）
4. **开启死锁检测**（`innodb_deadlock_detect=ON`，默认开启）

---

### 4.7 两阶段锁协议（2PL）

InnoDB 中行锁在**需要时才加**，但在**事务提交/回滚时统一释放**（不是语句结束后释放）。

**重要推论**：如果事务中需要修改多行，把**最可能产生锁冲突的行放到最后加锁**，可以减少锁等待时间。

```sql
-- 购票场景：需要更新 电影院账户（热点）和 用户账户
-- 推荐顺序：先更新用户账户（非热点），再更新电影院账户（热点）
-- 这样电影院账户的锁持有时间最短
BEGIN;
UPDATE user_account SET balance = balance - 100 WHERE user_id = 1;  -- 先
UPDATE cinema_account SET balance = balance + 100 WHERE cinema_id = 1;  -- 后
COMMIT;  -- 此时才释放两个锁
```

## 05 日志篇

### 5.1 三种日志的核心定位

| 日志 | 所属层 | 作用 | 格式 |
|------|--------|------|------|
| **undo log** | InnoDB 层 | 事务回滚 + MVCC 版本链 | 逻辑日志（记录行的旧值）|
| **redo log** | InnoDB 层 | 崩溃恢复（保证持久性）| 物理日志（记录数据页的物理修改）|
| **binlog** | Server 层 | 数据归档 + 主从复制 | 逻辑日志（记录 SQL 语句或行变化）|

> ⚠️ **redo log vs binlog 的本质区别**：
> - redo log：**循环写**（固定大小，写满后覆盖旧内容），只保存最近一段时间内未刷盘的数据，不能用于全量恢复
> - binlog：**追加写**（文件写满后新建文件），保存从某时间点起的所有变更，可用于数据库全量+增量恢复

---

### 5.2 undo log（回滚日志）

**写入时机**：事务对数据页做修改**之前**，先写 undo log（记录旧值）

**两大作用**：
1. **事务回滚**：事务需要 ROLLBACK 时，读 undo log 将数据恢复为旧值
2. **MVCC 版本链**：undo log 保存了历史版本，MVCC 通过 roll_pointer 串联，供快照读遍历

**undo log 的存储**：
- 写入 Buffer Pool 中的 **Undo 页面**
- Undo 页面的修改也会记录到 redo log，保证 undo log 本身的持久性

**undo log 的删除时机**：
- 当**没有任何活跃事务**需要访问该版本时（即该版本对所有活跃 Read View 不可见），undo log 才可以被 **purge 线程**清理删除

---

### 5.3 redo log（重做日志）

**为什么需要 redo log？**（WAL = Write-Ahead Logging）

直接将每次修改刷盘代价极高（随机 I/O）。InnoDB 策略：修改先在 Buffer Pool 内存中完成，同时将修改顺序写入 redo log（顺序 I/O，快得多）。若宕机，下次启动时通过 redo log 重放未刷盘的修改，保证数据不丢。

```
写请求 → 修改 Buffer Pool（内存）→ 写 redo log buffer → 按策略刷 redo log 到磁盘
                                          ↓（异步）
                              脏页由后台线程刷到磁盘
```

#### redo log 的刷盘时机（`innodb_flush_log_at_trx_commit`）

| 参数值 | 行为 | 安全性 | 性能 |
|-------|------|--------|------|
| `0` | 每秒一次，后台线程将 redo log buffer → 磁盘（主线程不参与）| 最低（宕机丢最多 1 秒数据）| 最高 |
| **`1`（默认）** | 每次事务提交，redo log buffer → **磁盘**（fsync）| 最高（不丢数据）| 最低 |
| `2` | 每次事务提交，redo log buffer → **OS Page Cache**（write 不 fsync）；每秒刷一次 Page Cache → 磁盘 | 中（宕机不丢，OS 崩溃丢最多 1 秒）| 中 |

> ⚠️ **参数值 1 保证数据不丢，但每次提交都有 fsync 开销，高并发下成为瓶颈**。可通过 `innodb_flush_log_at_trx_commit=2` + `sync_binlog=1` 在较高安全性和较好性能间权衡。

#### redo log 的大小限制与检查点机制

```
redo log 是循环写的：
write pos ──→ [redo log]──→ checkpoint
   ↑                              ↑
当前写入位置              已刷盘的最旧位置

write pos 追上 checkpoint → redo log 满 → 必须阻塞写请求，刷脏页到磁盘，推进 checkpoint
```

- redo log 大小由 `innodb_log_file_size × innodb_log_files_in_group` 决定
- redo log 越大，宕机恢复时间越长（需重放更多日志）；越小，checkpoint 频率越高（I/O 压力大）

---

### 5.4 binlog（归档日志）

**三种格式**：

| 格式 | 内容 | 优点 | 缺点 |
|------|------|------|------|
| `STATEMENT` | 原始 SQL 语句 | 日志量小 | 不确定函数（NOW()/UUID()）主从结果可能不同 |
| `ROW`（推荐）| 每行数据的变化（before/after）| 主从一致性最好 | 日志量大（批量更新每行都记录）|
| `MIXED` | 混合模式，大多数情况 STATEMENT，不安全情况自动切 ROW | 兼顾 | 逻辑稍复杂 |

**binlog 的写入时机**：
- 事务提交时将 binlog cache 写入 binlog 文件
- `sync_binlog=1`：每次提交都 fsync 到磁盘（最安全）；`sync_binlog=0`：由 OS 决定（可能丢失）

---

### 5.5 两阶段提交（2PC，Two-Phase Commit）

**问题背景**：redo log 和 binlog 是两个独立的日志，若只提交其中一个，主从/备份就会不一致。

**两阶段提交流程**：

```
执行器              InnoDB                 Server 层（binlog）
    |                  |                         |
    |—— 写 undo log → |                         |
    |—— 修改内存页  → |                         |
    |                  |—— 写 redo log ─────────→|
    |                  |   (prepare 状态)         |
    |                  |←─ 写 binlog ───────────|   ← 写入 binlog
    |                  |                         |
    |—— 提交 ────────→|                         |
    |                  |—— redo log commit ──────|   ← commit 状态
```

**崩溃恢复逻辑**（在 redo log 和 binlog 之间崩溃时）：

| 崩溃时机 | redo log 状态 | binlog | 恢复策略 |
|---------|-------------|--------|---------|
| 写 redo log prepare 后、写 binlog 前崩溃 | prepare | 无 | **回滚**（binlog 没有，主从不一致）|
| 写 binlog 后、redo log commit 前崩溃 | prepare | 有且完整 | **提交**（binlog 已有，两者应一致）|

> ⚠️ **判断标准**：binlog 完整 + redo log 是 prepare 状态 → 提交；其他情况 → 回滚。

---

### 5.6 三种日志的配合使用场景

**误删数据恢复（Point-in-Time Recovery）**：
1. 恢复到最近的全量备份（RDB/逻辑备份）
2. 通过 binlog 回放从备份时间点到误操作时间点之间的所有变更
3. 跳过误操作那条 SQL（如 DROP TABLE/DELETE）继续回放后续 binlog
→ 实现精确恢复到指定时刻

---

## 06 内存篇（Buffer Pool）

### 6.1 Buffer Pool 是什么？

Buffer Pool 是 InnoDB 在内存中维护的**缓存池**，缓存数据页（默认 16 KB/页）和索引页，减少磁盘 I/O。

**Buffer Pool 的大小**：`innodb_buffer_pool_size`，推荐设置为物理内存的 **50%~75%**

**Buffer Pool 的内容**：
- **缓存页**：磁盘数据页的内存副本（包括数据页、索引页、undo 页等）
- **控制块**：每个缓存页对应一个控制块，记录页的元数据（所属表空间 ID、页号、是否脏页等）

---

### 6.2 Buffer Pool 的三个链表

| 链表 | 作用 |
|------|------|
| **Free 链表** | 空闲页链表，存放可被分配的空缓存页 |
| **Flush 链表** | 脏页链表，存放被修改但尚未刷盘的缓存页 |
| **LRU 链表** | 按最近使用时间管理缓存页的淘汰 |

---

### 6.3 改进版 LRU（young/old 分区，防预读失效和缓存污染）

**传统 LRU 的问题**：
1. **预读失效**：InnoDB 预读机制（顺序预读/随机预读）将未必被用到的数据页提前载入 LRU 头部，挤出真正的热点页
2. **缓存污染**：全表扫描（如 `SELECT *` 无条件查询）将大量冷页放入 LRU 头部，将热点页全部挤出

**InnoDB 的改进方案（young/old 双区域）**：

```
LRU 链表：
┌──────────────────────────────────────────────────────┐
│         young 区（热数据，约 63%）  │  old 区（冷数据，约 37%）│
│  最近被访问 ← ← ← ← ← ← ← ← ← ← ← ← ← ←  新加入 │
└──────────────────────────────────────────────────────┘
                                         ↑
                                     分割点（midpoint）
```

**规则**：
1. **新读入的页**（包括预读的页）放入 **old 区头部**（而非整个 LRU 的头部）
2. old 区的页被再次访问，且与**首次访问的间隔 > 1 秒**，才升级到 **young 区头部**

**效果**：
- 预读的页若未被实际访问，停留在 old 区，自然被淘汰，不影响 young 区热点数据
- 全表扫描时，每页只被访问一次（间隔 < 1 秒），无法升级到 young 区，热点数据得以保留

> ⚠️ **InnoDB 的改进 LRU 与 Redis 的改进 LRU 的关键区别**：
> - InnoDB：新数据进 old 区头部，需要**再次访问且间隔 > 1 秒**才升 young 区
> - Redis：新数据和预读数据先进 inactive 链表，在 inactive 中再次被访问才升 active 链表（无时间要求）
> 两者思路相同（双链表防污染），触发条件不同。

---

### 6.4 Change Buffer（写缓冲）

**适用场景**：对**非唯一普通索引**的写操作（INSERT/UPDATE/DELETE），若对应的数据页不在 Buffer Pool 中。

**原理**：
- 写操作时，不立即把数据页从磁盘读入内存（避免随机 I/O），而是将变更记录到 Change Buffer
- 下次该数据页被读入 Buffer Pool 时，将 Change Buffer 中的变更合并（Merge）到数据页 → **将随机写变为顺序写**

**为什么只支持非唯一索引？**  
唯一索引在写入时必须先将数据页读到内存检查唯一性，既然数据页已在内存，就没有必要用 Change Buffer。

---

### 6.5 Double Write Buffer（双写缓冲）

**解决问题**：**partial page write（部分页写失效）**问题

**背景**：InnoDB 数据页 16 KB，OS 写的原子单位是 4 KB（一个扇区），所以写一个 InnoDB 数据页需要 4 次 OS 写。若其中一次写被中断（宕机），数据页残缺（部分旧部分新），redo log 也无法修复（redo log 以完整页为前提）。

**Double Write 机制**：
```
脏页写磁盘的流程：
1. 将脏页 copy 到内存中的 doublewrite buffer（2 MB）
2. 将 doublewrite buffer 顺序写入磁盘的 doublewrite file（系统表空间的两个连续区，共享页可保证写入原子性）
3. 再将脏页写入对应的数据文件位置

崩溃恢复时：
- 若数据页不完整 → 从 doublewrite file 中读取备份页 → 再用 redo log 重放 → 恢复完整
```

> 💡 **Double Write 代价**：每个脏页实际写了两次（doublewrite 区 + 数据文件），但两次写同一块连续区域（顺序 I/O），实际性能影响只有约 5%~10%。

---

### 6.6 脏页刷盘时机

| 时机 | 说明 |
|------|------|
| redo log 满 | write pos 追上 checkpoint → 强制刷脏页推进 checkpoint（会阻塞写请求）|
| Buffer Pool 空间不足 | Free 链表耗尽 → 通过 LRU 淘汰 old 区页，若是脏页则先刷盘再淘汰 |
| MySQL 空闲时 | 后台线程在 MySQL 相对空闲时异步刷脏页 |
| MySQL 正常关闭 | 将所有脏页刷盘 |

## 07 主从复制与分库分表

### 7.1 主从复制原理

```
主库（Master）                                      从库（Slave）
    │                                                   │
    │（执行 DDL/DML）                                   │
    │                                                   │
    │  ① 写入 binlog ───────────────────────────────→  │ ② I/O 线程读取 binlog
    │                                                   │   写入本地 relay log（中继日志）
    │                                                   │  ③ SQL 线程回放 relay log
    │                                                   │   执行 DDL/DML 修改数据
```

**三个线程**：
- 主库：**binlog dump 线程**（发送 binlog）
- 从库：**I/O 线程**（接收 binlog 写入 relay log）+ **SQL 线程**（回放 relay log）

**主从延迟的原因与解决**：

| 原因 | 解决方案 |
|------|---------|
| 从库机器性能较弱 | 升级从库硬件 |
| 主库 DML 量大，从库单线程回放 | **并行复制**（`slave_parallel_workers`，5.7+ 组提交并行复制）|
| 大事务（如批量 INSERT 数百万行）| 拆分大事务为小事务 |
| 网络延迟 | 优化网络 |

**主从数据一致性验证**：`pt-table-checksum` 工具

---

### 7.2 读写分离

- **主库**：处理写操作（INSERT/UPDATE/DELETE）
- **从库**：处理读操作（SELECT）
- **路由方式**：代理中间件（MyCat/ProxySQL）或应用层路由（ShardingJDBC）

> ⚠️ **读写分离引入的主从延迟问题**：  
> 写完主库后立即读从库，可能读到旧数据（从库还没同步完）。  
> **解决方案**：
> 1. 关键读强制走主库（如下单后立即查订单详情）
> 2. 读主库后等待从库追上（`WAIT_FOR_EXECUTED_GTID_SET`）
> 3. 业务层做缓冲（写完后延迟一段时间再读从库）

---

### 7.3 分库分表

**什么时候考虑分库分表？**
- 单表数据量超过 **千万级** 或 **体积超过 20GB**，B+ 树层高增加，查询变慢
- 单库 QPS 达到上限，需要分散写压力
- 单机磁盘空间不足

**分表策略**：

| 策略 | 说明 | 优缺点 |
|------|------|--------|
| **哈希分表**（Hash Sharding）| `shard_id = hash(user_id) % 分片数` | 数据均匀，但扩容时需要数据迁移（取模变化）|
| **范围分表**（Range Sharding）| 按时间、ID 范围分表（如 2020年一张表）| 范围查询友好，但热点不均（新数据集中在新表）|
| **一致性哈希** | 虚拟节点，扩容时迁移量最少 | 实现复杂 |

**分库分表的挑战**：
1. **跨库 JOIN**：需在应用层合并，或冗余数据减少 JOIN
2. **分布式事务**：跨库事务无法用本地事务，需 2PC / TCC / SAGA 等方案
3. **全局唯一 ID**：自增 ID 不再唯一，需用分布式 ID（雪花算法 Snowflake / Redis INCR / 数据库号段）
4. **排序和分页**：跨分片排序需每个分片各自排序后再归并（类似归并排序）
5. **数据迁移**：分库分表后历史数据迁移复杂

**雪花算法（Snowflake ID）结构**：
```
64位 = 1位符号（0）+ 41位时间戳（毫秒级，约69年）+ 10位机器ID（5位数据中心+5位机器）+ 12位序列号（每毫秒4096个）
```

## 08 附录：面试速查表

### 索引高频考点

| 问题 | 一句话答案 |
|------|-----------|
| B+ 树为什么适合数据库索引？ | 非叶子节点只存索引（树更矮）+ 叶子节点链表（支持范围查询）+ 磁盘友好 |
| 聚簇索引叶子节点存什么？ | 完整行数据 |
| 二级索引叶子节点存什么？ | 索引列值 + 主键值 |
| 什么是回表？ | 二级索引找到主键，再去主键索引查完整行 |
| 什么是覆盖索引？ | 查询所需字段全在索引中，不需要回表 |
| 索引下推的作用？ | 在存储引擎层过滤非最左字段条件，减少回表次数 |
| 最左匹配失效的场景？ | 跳过最左字段、最左字段是范围查询后面的字段 |
| 为什么推荐自增主键？ | 顺序插入不触发页分裂，减少 I/O 和内存消耗 |

### 事务高频考点

| 问题 | 一句话答案 |
|------|-----------|
| InnoDB 默认隔离级别？ | **可重复读（RR）**（SQL 标准默认是 RC，InnoDB 不同）|
| RC 和 RR 的 Read View 区别？ | RC 每次语句创建，RR 事务启动时创建一次不变 |
| MVCC 的三要素？ | 版本链（roll_pointer）+ undo log（历史版本）+ Read View（可见性规则）|
| 快照读 vs 当前读？ | 快照读走 MVCC 不加锁；当前读（FOR UPDATE）读最新版本 + 加锁 |
| RR 下幻读完全解决了吗？ | 快照读通过 MVCC 解决；当前读通过 next-key lock 解决；先快照读再 UPDATE 仍可能看到幻行 |

### 锁高频考点

| 问题 | 一句话答案 |
|------|-----------|
| 记录锁/间隙锁/临键锁区别？ | 记录锁锁行；间隙锁锁行间间隙（不含端点）；临键锁=间隙锁+记录锁（左开右闭）|
| 间隙锁的存在意义？ | 防止其他事务在锁定范围内插入新记录，解决当前读幻读 |
| 唯一索引等值查询命中时加什么锁？ | **退化为记录锁**（只锁一行，不锁间隙）|
| 两阶段锁的要点？ | 加锁在需要时，释放锁统一在事务提交时（不是语句结束时）|
| MDL 锁导致线上故障的场景？ | 长事务持有 MDL 读锁 → DDL 等待写锁 → 后续所有 DML 排队 → 连接耗尽 |
| 死锁如何自动处理？ | InnoDB 自动检测环路等待，回滚代价小的事务 |

### 日志高频考点

| 问题 | 一句话答案 |
|------|-----------|
| redo log 和 binlog 最大的区别？ | redo log：InnoDB 层循环写，用于崩溃恢复；binlog：Server 层追加写，用于归档和主从 |
| 两阶段提交解决什么问题？ | 保证 redo log 和 binlog 的一致性（防止一个写了另一个没写）|
| innodb_flush_log_at_trx_commit=1 的含义？ | 每次事务提交都 fsync redo log 到磁盘，最安全但最慢 |
| undo log 什么时候被删除？ | 没有任何活跃事务需要读该版本时，由 purge 线程异步清理 |
| binlog 哪种格式最推荐？ | **ROW 格式**，记录行变化，主从一致性最好 |

### Buffer Pool 高频考点

| 问题 | 一句话答案 |
|------|-----------|
| InnoDB 改进 LRU 如何防预读失效？ | 新页进 old 区（37%），需再次访问且间隔 > 1 秒才升 young 区 |
| Change Buffer 适用于什么场景？ | 对**非唯一普通索引**的写操作，数据页不在内存时缓存变更 |
| Double Write 解决什么问题？ | 防止 partial page write（页写到一半宕机导致数据页损坏）|
| 脏页何时强制刷盘？ | redo log 写满时，检查点需要推进 |

### 主从与分库分表高频考点

| 问题 | 一句话答案 |
|------|-----------|
| 主从复制三个线程？ | 主库 dump 线程，从库 I/O 线程（写 relay log）+ SQL 线程（回放）|
| 主从延迟如何解决？ | 并行复制（多个 SQL 线程）+ 拆分大事务 + 升级从库硬件 |
| 读写分离引入的新问题？ | 主从延迟导致读到旧数据，关键读走主库 |
| 雪花 ID 的组成？ | 1位符号 + 41位时间戳 + 10位机器 ID + 12位序列号，共 64 位 |
| 分库分表最大的技术挑战？ | 跨库 JOIN + 分布式事务 + 全局唯一 ID + 数据迁移 |
