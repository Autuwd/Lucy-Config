## 一、深入方向（同主题更深）

### 1. TCP 的拥塞控制算法

| 算法 | 原理 | 游戏影响 |
|------|------|----------|
| **CUBIC** | Linux 默认，丢包后立方降速再恢复 | 游戏流量突然升高时会被限速 |
| **BBR** | Google 算法，基于带宽测量而非丢包 | 更适合游戏，延迟稳定 |
| **Reno** | 经典算法，丢包后减半 | 最老，游戏中基本不用 |

**为什么游戏开发者需要理解这个？**

> 用 TCP 传游戏数据时，网络出现一个丢包，TCP 的拥塞控制会自动降低发送速度——哪怕你的游戏正在团战！这就是为什么实时对战不用 TCP 的原因之一。不只是延迟问题，TCP 本身就不适合"突发流量"。

**建议学习资料**：
- 📖 《计算机网络：自顶向下方法》第 3 章 — 最清晰的 TCP 拥塞控制讲解
- 📹 YouTube: TCP Congestion Control Explained (with BBR)

### 2. QUIC 协议（HTTP/3）

**QUIC 为什么是游戏网络的未来？**

```
传统 TCP：
  ① TCP 三次握手（1 RTT）
  ② 内部再 TLS 加密（1 RTT）
  = 连接需要 2 次来回

QUIC 在 UDP 之上：
  ① 连接 + TLS 一步完成（0-RTT）
  ② 连接迁移（换 WiFi 不断线）
  ③ 无队头阻塞（丢一个流不影响其他流）
  = 适合移动游戏
```

**QUIC 在游戏中的潜力**：

| 场景 | TCP | QUIC |
|------|-----|------|
| 首次连接 | 2 次 RTT | 0-1 次 RTT |
| WiFi 切 4G | 断开重连 | 连接迁移，不断 |
| 一个流丢包 | 所有数据等重传 | 其他流不受影响 |
| 手机游戏 | 切换网络必卡 | 无缝切换 |

**实际案例**：Roblox 已经在用 QUIC，Unity 正在集成 QUIC 支持。

### 3. GGPO Rollback 细节

面试讲到街霸的 Rollback，你能说概念。但真正深入要理解它的算法：

```
每帧循环：
  ① 收集本地玩家输入
  ② 输入未到的其他玩家 → 假设他们重复上一帧的输入
  ③ 用（真实+预测）输入推进一帧
  ④ 收到远程输入 → 如果猜对了 → 继续
                      如果猜错了 → 回滚到错误帧 → 纠正输入 → 快进回来
```

**三个关键技术难点**：

| 难点 | 解决方案 | 实现关键 |
|------|----------|----------|
| **状态保存** | 每帧保存完整游戏快照 | 序列化速度必须 < 1ms |
| **确定性** | 固定帧率 + 定点数 + 无随机 | 浮点运算在不同CPU结果不同 |
| **同步校验** | 帧序号 + 定期校验和 | 防止不同步漂移 |

### 4. NAT 穿透（P2P 游戏的基础）

**问题**：你家路由器的 IP 是内网的，对方怎么直接连到你？

```
你的电脑 192.168.1.5
    ↓
路由器 NAT（网络地址转换）
    ↓
公网 IP: 120.xxx.xxx.xxx:55555
    ↓
对方怎么知道你的公网 IP 和端口？
```

**解决方案：STUN / TURN / ICE**

```
STUN： "告诉我我的公网 IP 是什么"
        → 帮你找到你的公网地址

TURN： "我没法直连，你帮我转发"
        → 当 STUN 失败时，服务器做中继

ICE：   "先试 STUN，不行再试 TURN"
       → 综合方案，先直连，直连不了再中继
```

**游戏中的应用**：
- 主机游戏（P2P 联机）必须做 NAT 穿透
- Unity 的 Netcode 内置了 NAT 穿透方案
- Photon 等云服务直接帮你解决这个

### 5. KCP vs ENet vs RakNet 对比

面试能说 KCP 已经是加分项，但真正项目选型需要知道更多：

| 库 | 语言 | 特点 | 适用 |
|----|------|------|------|
| **KCP** | C (有C#移植) | 快速重传、不降速 | 多人竞技，偏实时 |
| **ENet** | C | 轻量、可靠UDP、分通道 | 中小型游戏 |
| **RakNet** | C++ | 完整方案(语音/匹配/NAT穿透) | 老项目，大而全 |
| **SteamNetworkingSockets** | C++ | Valve出品，QUIC-like | Steam 游戏 |
| **LiteNetLib** | C# | .NET 的 ENet 等价 | Unity C#项目 |

## 二、广泛方向（新主题拓展）

### 1. WebSocket（Unity 游戏最常用的通信方式）

**为什么很多 Unity 游戏用 WebSocket 而不是裸 TCP？**

```
裸 TCP 在浏览器/WebGL 上不支持
WebSocket 在浏览器、移动端、PC 全部支持

而且 WebSocket 天然是"消息"协议（不是字节流）
→ 不需要自己处理粘包！
```

**C# 示例：**

```csharp
using WebSocketSharp;

var ws = new WebSocket("ws://game-server.com/ws");
ws.OnMessage += (sender, e) => {
    Debug.Log("收到消息: " + e.Data);
};
ws.Connect();
ws.Send("Hello Server");
```

### 2. 游戏匹配系统设计

**匹配系统的核心问题**：

```
一个玩家点击"开始匹配"→ 发生了什么？

① 进入匹配队列
② 系统找段位接近、延迟低的其他人
③ 凑齐人数后创建房间
④ 通知所有人"匹配成功"
⑤ 启动游戏实例
```

**优化方向**：

| 问题 | 方案 |
|------|------|
| 匹配太慢 | 放宽段位/延迟要求 |
| 段位差距大 | 限制最大段位差 |
| 延迟高 | 按区域分服 |
| 有人取消 | 超时补人机制 |

### 3. 服务端架构：从单服到分布式

```
小游戏：单服架构
  [游戏服务器] ← 所有玩家连进来
  优点：简单
  缺点：最多 100-200 人同服

中型：分服架构
  [登录服] → 分配到你所在的大区
  [大区1] [大区2] [大区3] ← 每个大区独立
  优点：水平扩展
  缺点：大区之间不通

大型：微服务架构
  [网关] → 路由到不同服务
  [匹配服] [战斗服] [聊天服] [社交服] [排行榜服]
  优点：弹性伸缩，各服务独立更新
  缺点：复杂度高
```

### 4. 游戏服务器的帧率循环

**和客户端一样，服务器也有自己的 Update 循环**：

```csharp
// 游戏服务器主循环（Tick）
while (isRunning)
{
    var startTime = DateTime.UtcNow;
    
    ReceiveMessages();    // 收玩家的消息
    UpdateGameState();    // 更新游戏状态（物理/AI/碰撞）
    SendMessages();       // 把状态变化广播给玩家
    
    var elapsed = (DateTime.UtcNow - startTime).TotalMilliseconds;
    int sleepTime = Math.Max(0, (int)(TICK_INTERVAL - elapsed));
    Thread.Sleep(sleepTime);  // 保持帧率稳定
}
```

核心区别：

| | 客户端 | 服务端 |
|---|--------|--------|
| 帧率 | 60 FPS（16ms） | 10-30 TPS（33-100ms） |
| 渲染 | 要渲染画面 | 不需要渲染 |
| 输入 | 键盘鼠标 | 网络消息 |
| 计算量 | 轻 | 重（可能要算 100 人的物理） |

### 5. 游戏网络 Debug 实战

**当玩家说"好卡"时，你怎么排查？**

```
① 先看是延迟还是掉帧
   ping 服务器 → 如果 ping 高 → 网络问题
   FPS 低 → 渲染问题

② 网络问题进一步排查
   看延迟分布（p90/p99）：90% 的人在 50ms 以下还是 200ms？
   看丢包率：超过 2% 就会有明显卡顿
   对比不同地区：中国到美西 ≈ 180ms，到华东 ≈ 30ms

③ 工具
   Wireshark：抓包分析实际延迟
   Wireshark 显示的是真实的网络交互
   在 Unity 中可以用 Profiler 看 Network 开销
```

## 三、学习路线推荐

### 第一阶段（面试后 1-2 周）：深入基础

```
1. 读《计算机网络：自顶向下方法》第3章（TCP拥塞控制）
2. 读《计算机网络：自顶向下方法》第8章（网络安全）
3. 用 Wireshark 抓包观察三次握手和四次挥手
4. 写一个简单的 C# TCP Echo Server + Client
```

### 第二阶段（3-4 周）：动手实践

```
1. 用 LiteNetLib 写一个简单的 P2P 聊天室
2. 用 Unity + Mirror 做一个小型联机游戏原型
3. 用 Protobuf 定义消息 + TCP 传输
4. 实现心跳 + 断线重连机制
```

### 第三阶段（5-8 周）：完整项目

```
1. 设计并实现一个简单的帧同步格斗游戏
   - 帧锁定循环
   - 输入队列管理
   - 状态保存和回滚
2. 或者做一个状态同步的 2v2 对战游戏
   - 服务端权威计算
   - 客户端预测
   - 服务器回滚
```
